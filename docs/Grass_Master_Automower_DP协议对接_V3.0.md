## 0. 三分钟速览

| 项 | 结论 |
|---|---|
| DP 数量 | **26 个**（下发用 14 个、上报用 12 个，部分双向） |
| 下发结果怎么判 | **只看 DP115 `command_results`**：`code=0` 成功，非 0 = 拒绝理由码 |
| 开关（DP2）能不能启动割草 | **不能**。待机时 `DP2=true` 一律拒绝，启动必须走 **DP3 选模式** |
| 模式（DP3）语义 | **每次下发 = 启动新任务** ⇒ 隐藏旧计划、按 `DP119 工作时间` 重建 |
| 停止 / 取消 | `DP3=standby`（取消任务回待机）；`DP2=false` = **进急停**（保留现场，可"继续工作"） |
| 故障态下发 | **自带清理**：能清 ⇒ 先清再执行；不能清 ⇒ 回 `26` |
| 电量口径 | 面板与 APP **同一个函数** `battery_percent_get()`，舍去小数，逐值一致 |
| 在桩充电等待中发割草 | 电量 **≥70% 且无雨** ⇒ **放行出桩**；<70% ⇒ 拒 `54`；有雨 ⇒ 拒 `35` |
| **剩余工作时间怎么算** | 固件只发 **DP121** 的 `{计划起, 计划止, 现在, 类型}` ⇒ **App 自己算 `et−now` 并本地倒计时**（固件不按倒计时上报）|
| **当前这单是定时计划还是手动启动** | 看 **DP121 的 `t` 字段**：`1`=定时计划（闹钟到点）、`2`=手动（面板/APP 启动、定点、恢复补建）、`0`=无计划 |

## 2. 下发类 DP 逐条

### 2.1 DP2 `switch_go`（工作开关）

> 判定顺序很重要，下表按**代码实际执行顺序**排列。

| 当前状态 | 下发 `true` | 下发 `false` |
|---|---|---|
| 已关机 | `16 REJ_POWER_OFF` | `16 REJ_POWER_OFF` |
| **故障态（ABNORMAL）** | 门禁①不过 ⇒ `26`；过 ⇒ 有继续位则**按继续位恢复**（`code=0`，回显 1）；无继续位则落"待机启动"⇒ `52`/`48` | `26`（**拒绝且不做任何事**，"暂停"不承担清除职责） |
| 急停中 | 清硬件锁存 + 门禁：未松开 ⇒ `23`；升级为故障 ⇒ `26`；盖开 ⇒ `21`；通过 ⇒ **按继续位恢复** | `19 REJ_ESTOP`（已在急停） |
| **待机 + NORMAL**（含盖开） | ❌ **拒绝**：上次任务被"取消"过 ⇒ `52`；否则 ⇒ `48`<br>⚠️ 此判定**先于**盖子检查 ⇒ 待机时盖开也是 `48`/`52`，不是 `21` | 待机分支内按序：`16` 关机 / 静音 / `19` 已在急停 / `17` 自检期 / `21` 等关盖 / `48` 其余 |
| 盖子开（**非待机**） | `21 REJ_COVER_OPEN` | `21 REJ_COVER_OPEN` |
| 割草 / 绕边 / 定点 / 回充中 | ✅ **幂等成功**（`code=0`，回显开关=1） | 进急停（记停机点，可继续工作） |
| 定点中 | 同"作业中"（幂等） | **等同 standby**：取消计划回待机，**不进急停** |
| **在桩等待（等充电/等雨停）** | ⚠️ **幂等成功 `code=0`**，但开关回显 `0`（APP 控件自动弹回） | ❌ `49 REJ_ON_PILE_WAIT` + 静音 |
| 其它未覆盖模式/半状态 | — | `19` 急停 / `21` 等关盖 / `53` 其余 |

> **要点**：`DP2=true` 不是启动通道。想启动请发 `DP3`。
> 拒绝时固件**会回显真实开关值**（`0`），APP 靠这个把控件弹回关。

### 2.2 DP3 `mode`（工作模式）

**白名单**：只接受 `0/1/2/3`。`4~7`（edge_mowing / secondary / wait_charge / wait_rain）为平台占位值，下发 ⇒ `64 REJ_BAD_ENUM`。

**语义**：**每次 DP3 下发 = 启动一个新任务** ⇒ 会先终止旧计划，再由自检链按 `DP119 工作时间` 重建。
（**幂等情形除外** —— 已在割草中再发 `smart`、已在回充中再发 `goto_charge`、已待机再发 `standby` 都**不动计划**，见下表。）

| 设备当前状态 | 下发 | 结果 | 计划 |
|---|---|---|---|
| 割草 / 沿边中 | `1 smart` | ✅ 幂等成功 | 不动 |
| 割草 / 沿边中 | `2 spot` | ✅ 转定点 | **新建**（旧计划终止） |
| 定点中 | `1 smart` | ✅ 转割草 | **新建** |
| 回充中（未触桩）+ 低电回桩 | `1`/`2` | ❌ `34 REJ_LOW_CHARGE` | 不动 |
| 回充中（未触桩）+ 雨天回桩 | `1`/`2` | ❌ `35 REJ_RAIN` | 不动 |
| 回充中（未触桩）+ 手动/计划完成回桩 | `1 smart` | ✅ 转割草 | **新建** |
| **待机（野外）** | `1 smart` | ✅ 新建任务开工 | **新建** |
| 待机（野外）+ 界外（双外确认） | `1 smart` | ❌ `33 REJ_OFF_BOUNDARY` | 不动 |
| 待机（野外） | `2 spot` | ✅ 定点开工 | **新建** |
| 待机 / 作业中 | `0 standby` | ✅ 取消回待机 | **清空** |
| **在桩 + 电量 <70%** | `1 smart` | ❌ `54 REJ_ON_PILE_LOW_SOC`，**机器仍会进"在桩等待充电"** | 不动 |
| **在桩等待（充电等待）+ 电量 ≥70% + 无雨** | `1 smart` | ✅ **放弃等待，出桩割草**（2026-10-22 新增） | **新建**（按工作时间） |
| **在桩等待 + 有雨** | `1 smart` | ❌ `35 REJ_RAIN` | 不动 |
| **在桩等待** | `0 standby` | ❌ `49 REJ_ON_PILE_WAIT`（不打断等待状态机） | 不动 |
| **在桩**（充电会话建立 `is_pile`） | `2 spot` | ❌ `32 REJ_ON_PILE`（**先于**一切硬门判断） | 不动 |
| **在桩等待但 `is_pile` 为假**（如已充满仅挂桩） | `2 spot` | ❌ `49 REJ_ON_PILE_WAIT` | 不动 |
| 线外 / 骑线（左右传感器非全 INSIDE） | `2 spot` | ❌ `33 REJ_OFF_BOUNDARY`（先于硬门） | 不动 |
| 在桩（已触桩 / 待机在桩） | `3 goto_charge` | ❌ `32 REJ_ON_PILE` | 不动 |
| 作业中 | `3 goto_charge` | ✅ 取消作业回桩 | **清空** |
| 等关盖（半启动） | `0 standby` | ✅ 取消待启动 | **清空** |
| 已待机 | `0 standby` | ✅ 幂等成功 | 不动 |
| 急停中 | `0/1/2/3` | ✅ **先退急停再按该模式执行** | 见各分支 |

**DP3 上报值**（设备状态 → DP3）：`MODE_IDLE → 0`、`WORK_START/WORK → 1`（去副区 → `5`）、`SPOT → 2`、`CHARGE_START/PILE → 3`、`EDGE_START/EDGE → 4`、**`KEEPP_PILE → 6（等充电）/ 7（等雨停）`**。

> ⚠️ 注意区分：**DP3 的在桩等待是 6/7**，而 **DP5 的在桩等待是 9/10**，两套枚举不同。

### 2.3 DP101 `mow_schedule`（割草计划，88 字节）

**布局**：8 组 × 11 字节，组索引 `0` = "全部设置"，`1~7` = 周一~周日。

| 组内偏移 | 长度 | 含义 |
|---|---|---|
| 0~1 | uint16 LE | 时段 1 开始（分钟数，0~1440） |
| 2~3 | uint16 LE | 时段 1 结束 |
| 4~5 | uint16 LE | 时段 2 开始 |
| 6~7 | uint16 LE | 时段 2 结束 |
| 8 | 1 | 沿边割草标志（1=该天绕边） |
| 9 | 1 | 时段 1 有效位 |
| 10 | 1 | 时段 2 有效位 |

**两种形态，不可混用**：

| 形态 | 要求 |
|---|---|
| **全部设置**（组 0） | 组 0 有任一时段有效 ⇒ 广播到周一~周日（忽略组 1~7）；组 1~7 必须全 0 |
| **按天设置**（组 1~7） | 组 0 必须全 0；各组独立配置 |

**校验与拒绝码**

| 情况 | 码 |
|---|---|
| 长度 ≠ 88 | `65 REJ_BAD_LENGTH` |
| 帧解析失败 | `66 REJ_PARSE_FAIL` |
| 组 0 标志置位但两个时段都不合法（起止倒置/越界） | `64 REJ_BAD_ENUM` |
| 某个有效时段时长 ≤ 10 分钟（**整包拒绝，不半写入**） | `65 REJ_BAD_LENGTH` |

**特殊值**：**整包全 0 = 清空全部计划**。
**成功回读**：成功后固件会**全量回读 DP101**，APP 直接用它刷新 UI。

**DP110 "恢复默认计划"的实际默认值**（以代码为准）：

```
每天  08:30 - 12:00  +  14:00 - 18:00
绕边  仅 周一 / 周三 / 周五
形态  按天设置（组 0 全 0，组 1~7 全填）
```

> 旧文档（含 `tuya_protocol.h` 的注释）写的"09:00-11:30 + 13:30-17:30"**已过期**。

### 2.4 DP103 `zone_config`（区域配置，25 字节）

**布局**：5 区 × 5 字节。

| 组内偏移 | 长度 | 含义 |
|---|---|---|
| 0 | 1 | 区号 1~5 |
| 1 | 1 | 百分比 0~100 |
| 2~3 | uint16 LE | 距离（米） |
| 4 | 1 | valid 有效位 |

**校验与拒绝码**

| 情况 | 码 |
|---|---|
| 长度 ≠ 25 | `65 REJ_BAD_LENGTH` |
| 解析失败 | `66 REJ_PARSE_FAIL` |
| 区号不在 1~5 | `64 REJ_BAD_ENUM` |
| 各区百分比之和 > 100 | `64 REJ_BAD_ENUM` |

**成功回读**：成功后全量回读 DP103。

### 2.6 DP114 `device_time`（设备时间）

载荷：**10 位十进制 UTC 秒字符串**（如 `"1761113012"`）。

| 情况 | 码 |
|---|---|
| 长度 ≠ 10，或首位为 `'0'` | `65 REJ_BAD_LENGTH` |
| 含非数字字符 | `66 REJ_PARSE_FAIL` |
| 数值溢出（> 429496729） | `66 REJ_PARSE_FAIL` |
| 时间过早（< 2001-09 对应值） | `64 REJ_BAD_ENUM` |
| **DP106 自动同步开关关闭** | `69 REJ_TIME_SYNC_OFF` |

**限频**：⚠️ **固件当前没有做限频**（`dp_download_device_time_handle` 收到即 `rtc_set_timestamp()` 并回显）。旧文档里的"≥60 秒限频"是设计意图，未落地 —— APP 端请自行节流。

## 3. 上报类 DP 逐条

### 3.1 上报时机模型

| 类型 | 周期 | 说明 |
|---|---|---|
| **变化即报** | 见各 DP | 检测到值变化立即上报 |
| **兜底重报** | DP5/3/118/2：**1 秒**<br>DP13/18/111：**60 秒**<br>四层全 0 时：**300 秒**<br>**DP121：有计划 60 秒 / 无计划 300 秒** | 丢帧自愈 |
| **边沿事件** | — | DP120，只在位翻转时报，无兜底 |
| **全量上报** | 触发式 | 云端 `0x08` 查询 / 连云首报，**共 24 步**（`REPORT_STEP_NUM`），每批 8 块、批间隔 25ms |
| **单次事件** | — | DP112/DP113/DP116 等 |

> **OTA 期间全部静默**（`READY/RECEIVING/FINALIZING`）：5 个上报通道一律不发，只有 OTA 自身的 DP116 例外。

### 3.2 DP5 `status`（工作状态）

优先级：**关机 > 急停 > 故障 > 陷坑脱困 > 回充行驶 > 在桩等待 > 沿边 > 定点 > 割草**。

**2026-10-24 平台新增 3 值**（追加在末尾，`0~11` 索引不变）：

| 值 | 名称 | 判据 | 补充 |
|---|---|---|---|
| **12** | `escaping` | 陷坑脱困状态机运行中 | 仅出现在 割草/沿边/回充 这 6 种作业模式；脱困失败（超时 180s 或 6 轮）转 `fault`(6) |
| **13** | `goto_charge_low_pwr` | **低电**回充 | 电量低触发的回充 |
| **14** | `goto_charge_rain` | **雨滴**回充 | 雨检触发的回充 |

> 普通回充（计划结束 / 面板手动回桩 / APP 下发回桩 / 丢信号自动回桩）仍是 **`4 goto_charge`**。
> 到桩之后仍按原因报 **`9 wait_charge`** / **`10 wait_rain`**（与 `13`/`14` 一一对应）。

**`escaping` 与其它值的关系**

| 情况 | DP5 |
|---|---|
| 割草中触发陷坑，正在脱困 | `12 escaping` |
| 脱困成功 | 回到 `1 mowing`（或原作业类型） |
| 脱困失败（困死） | `6 fault` |
| 脱困中按急停 | `7 stop`（急停优先级更高） |

> 事件通道的对应关系：脱困开始/结束在 **DP120 报 `41` / `141`**，与这里的 `12` 天然配对。

### 3.3 DP13 `battery_percentage`（电量）

- 数据源：`battery.soc_displayed` 三层平滑值
- 取整：**舍去小数**（与面板 LCD 完全一致，同一函数 `battery_percent_get()`）
- 上报：变化 ≥1% 即报；60 秒兜底

### 3.4 DP111 `fault_alarm`（四层位域 JSON）

```json
{"device":0,"error":0,"function":0,"circularize":0}
```

- 键值 = 各层 EventGroup 的 **32 位原始位域**（位定义见 `alarm.h`）
- 任一层变化 ⇒ **全量重报四条**
- 无告警 ⇒ 四键全 0
- **`circularize` 层已过滤**：20 个有效位（`alarm.h` 另有 `CIRCULARIZE_NO`=0，共 21 条枚举）只保留 **4 位** ⇒ `0x002` RAIN / `0x004` LOW_CHARGE / `0x800` BLADE_OTMP / `0x1000` MOWER_LIFT
  - 其余 16 位（刀盘电流分级、密草停顿、前上坡、停止确认期、与 error 层重复的超时位、死位）**不再进 DP111**
  - ⇒ 若 APP 需要"正在被抬起"的实时提示，读 `circularize` 的 bit12（`0x1000`）

### 3.5 DP18 `fault`（故障位图，13 位）

### 3.6 DP120 `alarm_event`（事件码）

- **发生码 = N（1~99）**，**恢复码 = N + 100**，`0` 保留
- **事件型**（fire-and-forget）：只承载"发生了什么"，状态仍看 DP18/DP111
- 两次发送最小间隔 **1 秒**；**不进全量上报步表**

| 码 | 事件 | 层 |
|---|---|---|
| 1~6 | 电池 / IMU / FLASH / 左电机 / 右电机 / 刀盘电机 | device（严重） |
| 11~24 | 位姿 / 抬起 / 边界 / 左过流 / 左过温 / 左霍尔 / 右过流 / 右过温 / 右霍尔 / 刀盘过温 / 刀盘霍尔 / 刀盘堵转 / 圈外 / 定点出界 | error（严重） |
| 31 | 陷坑困死 | function（严重） |
| 41~46 | 陷坑脱困 / 丢信号 / 圈外自恢复 / 抬起通知 / 积水 / 低电 | circularize（轻微/通知） |
| **51~53** | **开始回充：`51` 普通 / `52` 低电 / `53` 雨滴**（恢复码 **151 / 152 / 153** = 回充结束）| **动作事件（2026-10-24 新增）** |

#### 51~53 详解（与 DP5 的 `4`/`13`/`14` 一一对应）

| 发生码 | 含义 | 触发时机 | 恢复码 |
|---|---|---|---|
| **51** | 开始回充 · **普通** | 计划结束 / 面板手动回桩 / APP 下发回桩 / 丢信号自动回桩 | **151** |
| **52** | 开始回充 · **低电** | 电量低触发（先有 `46` 低电通知，持续 5 秒后才真回充） | **152** |
| **53** | 开始回充 · **雨滴** | 雨检触发（先有 `45` 积水通知） | **153** |

**关于恢复码 151/152/153**：它的作用是**把 DP120 的值"翻回去"**，使下一次同类回充能再次触发平台"值变化才推"的规则 —— **不代表"到桩成功"**。
"到桩"请用 **DP5 变为 `9 wait_charge` / `10 wait_rain`** 判断。

**为什么不复用 45/46**：`45`(积水) / `46`(低电) 是**告警通知**（告警层事件），与"是否真的开始回充"不同源 —— 雨检开关关掉时 45 不产生，而回充也不会发生；低电通知后可能被 APP 打断而不回充。⇒ **两者不能互相替代**。

### 3.7 DP112 / DP113 / DP116 / DP117 / DP118

| DP | 上报时机 | 说明 |
|---|---|---|
| **112 fw_version** | 连云首推一次 + 全量兜底 | MCU 版本字符串；OTA 成功确认靠它 |
| **113 shutdown_report** | 关机瞬间 `true`（100ms 重发约 9 帧，直到断电） | 开机连云首推 `false`，复位云端残留 |
| **116 ota_status** | OTA 流程内自报 | `"7"`=拒绝（非待机）；`"20"`=失败 |
| **117 charging** | 变化即报 + 60s 兜底 | `0` 未充 / `1` 充电中 / `2` 已充满（等雨停挂桩算 `1`） |
| **118 cover_status** | 变化即报（200ms 防抖）+ 1s 兜底 | `1`=合盖 |

### 3.8 DP121 `schedule_current`（机器当前计划）

**字符型 JSON，只上报。** 发的是**基准量**，不是"剩余秒" —— App 用 `et − now` 自己算剩余并本地倒计时。

> **【V3.1 变更 2026-10-30】新增 `t` 字段（计划类型）。**
> 固件生效版本：**MCU_VER ≥ 1.3.5**。当前量产固件（1.3.4 及更早）**没有 `t`** ⇒ **App 必须把"缺字段"当成 `0`**，不能当解析失败。

```json
{"st":1761451200,"et":1761465600,"now":1761454500,"t":1}   // 定时计划触发
{"st":1761451200,"et":1761458400,"now":1761454500,"t":2}   // 手动启动（按"工作时间"开的 2h 窗）
{"st":0,"et":0,"now":1761454500,"t":0}                     // 无计划
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `st` | u32 | 计划开始时间（**UTC 秒**）。无计划时 **0** |
| `et` | u32 | 计划结束时间（**UTC 秒**）。无计划时 **0** |
| `now` | u32 | **本帧构建瞬间的机器 UTC 秒**（无计划时也照发，供 App 对齐时钟）|
| `t` | u8 | **计划类型**（V3.1 新增）：`0`=无计划/未知，`1`=定时计划，`2`=手动计划。**无计划时必为 `0`** |

#### `t` 取值与语义

| `t` | 含义 | 触发来源 | App 建议展示 |
|---|---|---|---|
| `0` | 无计划 / 未知 | 计划已完成或已终止；**或固件 < 1.3.5（字段缺失）** | 不显示计划行，剩余时间归 0 |
| `1` | **定时计划** | ① 用户配置的割草计划到点，闹钟自动唤醒（固件从当天计划队列取出）② **定时计划被中断后"继续工作"**（沿用原性质，见下表） | 显示"计划任务" + 计划时段 |
| `2` | **手动计划** | ① 面板按键启动 ② APP 远程启动 ③ 定点割草 ④ **手动计划被中断后"继续工作"**（沿用原性质） | 显示"手动任务"，剩余 = `et − now` |

**几个必须知道的行为边界**

| 场景 | `t` | 为什么 |
|---|---|---|
| 定时计划进行中**暂停 → 继续** | 仍 `1` | 计划未被终止，原计划对象原样保留，不会重建窗口 |
| 定时计划中途**急停 → 继续工作**（计划还在） | 仍 `1` | 同上，不重建 |
| **定时计划已被取消**后继续工作 | **仍 `1`** | **沿用原任务性质** —— 固件记着"这是定时任务"，恢复后依旧报定时 |
| **手动计划已被取消**后继续工作 | **仍 `2`** | 同上，沿用原性质 |
| **绕边割草中** | `0` | 绕边作业不产生"计划"对象。若 App 需要显示"绕边中"，请读 **DP5/DP111**，不要指望 DP121 |
| 计划存在但当前时刻不在 `[st, et)` 内 | `0` | 固件把 `st/et` 归零时类型同步归零，保证三字段语义一致 |

> **"沿用原性质" ≠ "就地改成手动"**：早期方案曾打算把"恢复后重建的窗口"一律标成手动，**该做法已否决**。
> 现行语义：**定时计划恢复后仍报 `1`，手动计划恢复后仍报 `2`**。
>
> ⚠️ 但要注意：恢复时如果原计划已被取消，固件必须**重新建一个窗口**（按 `DP119 工作时间` 从当前时刻重算，且不超过当日 24:00）⇒ 这个新窗口的 `st/et` **可能与用户配置的定时窗不同**。类型表达的是"这单活的性质"，不是"窗口是否等于配置表"。App 若要判断"当前窗口是否就是配置的定时窗"，请拿 `st/et` 去和 **DP101** 的计划表比对。

> ⚠️ **`t` 会与 `st/et` 同时变化**：手动启动与定时计划**完全可能撞出相同的 `(st, et)`**（例：定时计划 08:30–10:30，用户 08:30 手动启动 2h）。所以 **App 判断"计划变化"必须用 `(st, et, t)` 三元组**，只看 `(st, et)` 会漏掉"类型变了"这一整类变化。

#### 上报时机（**不随倒计时上报**）

| # | 时机 | 判据 |
|---|---|---|
| 1 | **App 打开 / 设备连云 / 0x08 查询** | 在全量上报步表里（第 **24** 步）|
| 2 | **计划变化**（新建 / 闹钟唤醒换计划 / 手动启动 / 终止 / 完成）| **`(st, et, t)` 三元组**变化，且**连续 2 拍一致**才认（防跨任务读撕裂）|
| 3 | **机器时钟跳变**（校时 / 改时区 / 改夏令时）| 实测经过秒与 tick 经过秒之差 **≥ 10s** |
| 4 | **兜底重报**（丢帧自愈）| 有计划 **60s**，无计划 **300s** |

#### 为什么发"基准"而不是"剩余"

| | 发剩余秒 | **发 st/et/now/t** |
|---|---|---|
| 固件是否需要按倒计时周期上报 | 要（否则 App 不知道变了）| **不要** —— App 自己算 |
| 校时后 | App 无法感知 | App 用新的 `now` 重算即可 |
| 能否显示计划起止 | ❌ | ✅ |
| 扩展字段 | 要改语义 | JSON 加字段即可 |

> ⚠️ **绝不能按"值变化"上报**：载荷里 `now` 每秒都在变，按值比较会变成**一秒一帧**。
> 固件的判据是"计划身份"和"时钟是否被跳变"，不是"载荷是否不同"。

**上报量估算**

| 状态 | 帧数 |
|---|---|
| 有计划、稳定作业 | 1 帧/分钟 |
| 无计划（空闲）| 1 帧/5 分钟 |
| 计划变化 / 校时 | +1 帧（立即）|

对比现有 DP5/DP3/DP118/DP2 的 1 秒兜底组（4 帧/秒 = 34.5 万帧/天），本 DP 约 **690 帧/天**，占现网流量 **<1%**。

#### App 侧处理

```
收到帧 → 解析 st / et / now / t      // t 缺字段(V3.0固件) ⇒ 按 0 处理, 不报错
        → 剩余 = max(0, et - now)          // 无计划时 et=0 ⇒ 剩余 0
        → 之后本地每秒递减，收到新帧才重置基准
        → 去重只看 (st, et, t)：now 变化不代表计划变；t 变化必须当"计划变了"处理
```

**推荐的分支写法（倒计时优先）**

```
if (剩余 == 0) {
    显示"今日计划";            // 无计划 / 未开始 / 已结束 / 旧固件，全部走这里
    return;
}
switch (t) {
    case 2:  显示"手动计划";  break;   // 面板/APP 启动、定点、恢复补建
    case 1:  显示"今日计划";  break;   // 定时计划正在执行
    default: 显示"今日计划";  break;   // t=0 理论上到不了这里(剩余>0 必有计划)，兜底
}
```

> **`t` 实际只有 2 个分支会被读到**（`1` 与 `2`）：`t=0` 那条路径已被"剩余==0 提前 return"截掉。
> 但**协议仍保留 `t=0` 这个取值**，原因：① 机器日志/云端历史/后续"手动 vs 自动作业时长"统计需要真实值（无计划时伪装成 `1` 会让统计全错且不可反推）；② 字节成本相同（`"t":0` 与 `"t":1` 都是 6 字节、块成本同为 3 块）；③ 让"缺字段 = 0 = 无计划"这条兼容规则语义自洽。

**两个必须做对的点**

| # | 要点 | 不做的后果 |
|---|---|---|
| 1 | **去重键必须是 `(st, et, t)` 三元组** | 手动启动与定时计划可能撞出相同时段（例：定时 08:30–10:30，用户 08:30 手动启动 2h）⇒ 只按 `(st, et)` 会认为"没变化"而不刷新，**界面永停在"今日计划"**，且 60s 兜底发的还是同一帧、同样不刷新 |
| 2 | **缺 `t` 字段当 `0`，不能当解析失败** | 老设备（MCU_VER ≤ 1.3.4）整块计划信息显示不出来 |

**两个对你有利的固件事实（跨天自愈）**

| 事实 | 依据 | 意义 |
|---|---|---|
| **手动计划的结束时间被截到今日 24:00** | 固件 `system.c`：`end_timestrap > today_end_timestrap` 时截断 | 手动计划**不跨午夜** ⇒ 倒计时必然当天归零 ⇒ 每天自然回落到"今日计划" |
| **定时计划同样不跨午夜** | `schedule_slot_sane()` 保证 `end > start` 且同日 | 同上 |

- 断网/丢帧期间本地倒计时照常走（因为是绝对时间戳，**不是相对秒数**）
- `now` 与 **DP114** 同为 UTC 秒，可用于交叉校验机器时钟
- **`t` 只在"计划身份变化"时才会变**（含 1⇄2 的类型切换），不会每帧抖动 —— 所以「`t` 变了」可以安全地当天花板事件用（例如刷新标题为"计划任务/手动任务"、写一条操作日志）

## 5. DP115 命令结果契约

**载荷**：

```json
{"code":0,"seq":12,"dp":3,"val":1}
```

| 字段 | 含义 |
|---|---|
| `code` | **结果/理由码。`0` = 成功，非 0 = 拒绝**（码表见《拒绝理由与文案 V1.0》） |
| `seq` | 每次下发 +1，0~255 循环（防云端同值去重） |
| `dp` | 被处理/被拒的 DP 号 |
| `val` | 可选。bool/enum/value 类回**下发数值**；raw/string 类回**载荷长度**（绝不回内容） |

**上报时机**：
1. **每条下发处理完立即 1 帧**
2. 云端 `0x08` 查询 / 连云首报 ⇒ 回读**最后一条**（内容与 `seq` 都不变 ⇒ APP 可识别为旧结果）
3. 本次上电从未下发过 ⇒ **不发**（不产生"初值"）

**APP 处理建议**：
- 用 `seq` 去重，只处理比上次大的
- `code != 0` ⇒ 按码表出文案（见配套文档）
- `code == 26` ⇒ **必须读 DP111 的 `device` + `error` 两层**定位残留故障，不要只提示"机器故障"

## 6. 典型流程走查

### 6.1 APP 启动割草（野外待机）

```
DP3=1 (smart)
  ↓
固件：校验 → 终止旧计划 → 按 DP119 工作时间新建计划 → 自检 → 等关盖 → 出桩
  ↓
DP115: {"code":0,"seq":n,"dp":3,"val":1}
DP2:   1（开关变"作业中"）
DP5:   0 → 1（mowing）
```

### 6.2 APP 在桩充电等待中启动割草（2026-10-22 新行为）

| 电量 | 结果 |
|---|---|
| **≥70% 且无雨** | `code=0`，放弃等待，按工作时间重建计划出桩；DP3 从 `6` 变 `1` |
| **<70%** | `code=54`，机器继续等待充电 |
| **有雨** | `code=35`，机器继续等待雨停 |

### 6.3 APP 暂停

```
DP2=false
  ↓
固件：作业中 ⇒ 进急停（记停机点、停轮关刀）
  ↓
DP115: {"code":0,...,"dp":2,"val":0}
DP5:   7（stop）
DP2:   0
```

恢复：`DP2=true` ⇒ 从急停恢复并按"继续工作"流程接着干。

### 6.4 APP 取消任务

```
DP3=0 (standby)
  ↓
固件：清工作事件 + 终止计划 + 停轮关刀 + 回主页
  ↓
DP115: {"code":0,"seq":n,"dp":3,"val":0}
DP3:   0（standby）
```

### 6.5 故障态下发

```
任意启动类命令
  ↓
固件：先跑门禁①（故障还在吗？）
  ├─ 能清 ⇒ 内部清理后照常执行 ⇒ code=0
  └─ 不能清 ⇒ code=26，并保持 ABNORMAL
                APP 应读 DP111 的 device/error 两层，指出"具体哪一项没排除"
```

## 7. 已知限制与注意点

| # | 项 | 说明 |
|---|---|---|
| 1 | `DP2=true` 不能启动 | 待机时一律拒绝（`48`/`52`）。启动请用 DP3 |
| 2 | **APP 无法取消在桩等待** | 在桩等待中 `DP3=standby` 被拒 `49`；只有**面板**能取消（等待页 BACK → "Cancel schedule?" → OK） |
| 3 | DP105 / DP119 不报越界 | 限幅后回 `code=0`，以回读值为准 |
| 4 | DP111 的 `circularize` 层只有 4 位 | 需要其它通知位请改读 DP120 事件码 |
| 5 | DP120 无兜底重报 | 丢帧即丢事件；状态类以 DP18/DP111 为准 |
| 6 | OTA 期间无任何 DP 上报 | 升级页会看到数据"冻结"，属预期；升级失败后自动恢复 |
| 7 | DP115 需平台隐藏 | 否则设备页会显示裸 JSON |
| 8 | DP3 与 DP5 的在桩等待枚举不同 | DP3 = `6/7`，DP5 = `9/10` |
| **9** | **DP120 的 `45`(积水) / `46`(低电) 是告警通知，不是回充动作** | 要判断"是否正在回充、因为什么回充"请看 **DP5 的 `4`/`13`/`14`**，或 DP120 的 **`51`/`52`/`53`** |
| 10 | 时间写入**未做限频** | 固件收到即写 RTC 并回显；APP 端需自行节流（旧文档说的 60s 限频未实现） |
| 11 | 盖子必须合上 | 开盖时所有启动类命令一律 `21` |
| **12** | **DP121 不按倒计时上报** | 只在"计划变化 / 时钟跳变 / 兜底(60s·300s)"时发。App **必须本地倒计时**；只显示静态数字会越来越不准 |
| **13** | **DP121 的 `now` 每次兜底都不同** | App 判断"计划是否变化"**只看 `(st, et, t)` 三元组**（V3.1 起加 `t`）；若拿整帧比较，会每分钟误判一次变化 |
| **14** | **DP121 的 `t` 字段在旧固件（< 1.3.5）不存在** | App 必须把"缺 `t`"当 `0`（未知），**不能当解析失败**；否则老设备会整块计划信息显示不出来 |
| **15** | **`t` 变了但 `(st, et)` 没变是正常现象** | 手动启动与定时计划可能撞出同一时段。**只按 `(st, et)` 去重的 App 会漏掉类型变化**（表现为"已经是手动任务了但还显示计划任务"）|
