# 上传图片改成设备口径（Baseline 4:2:0 / 320×240 / 500KB）、DP165 按 2 字节

> 文档类型：Historical Change Record
> 日期：2026-09-17
> 环境：SSH 开发机（Project Hub 分发）
> 分支与起始版本：main / 99e85bd
> 范围：`lib/src/shared/media/upload_image.dart`、`lib/src/features/devices/presentation/`、
> `lib/src/tuya/`、`test/`、`tools/`、`docs/`
> 当前权威文档：`docs/PRODUCT_RULES.md` §4.3 / §4.5、`AI_CONTEXT.md`

## 背景与目标

固件 **1.0.12** 带来两件事，App 侧同步：

1. **图片下载**（花盆自己按 DP142 `dl_url` 把图下载下来显示）。设备解码器只吃一种图，
   产品给了四条硬要求：**JPG Baseline（不能 Progressive）／4:2:0 采样／尺寸 ≤ 320×240
   （任意宽高比，设备居中显示，小图不放大）／文件 ≤ 500 KB**。
   这覆盖了 2026-09-16 那版「总像素 ≤ 480,000、≤ 1 MB」的上传口径。
2. **DP165（空气湿度日历史）的点从「1 字节整数 %」改成与 DP164 对称的「2 字节大端 ×10」**，
   产品口径：「App 按 2B 解析即可」。

## 变更内容

### 1. 上传前处理改成设备口径（`UploadImage`）

- 上限从「总像素 480,000 + 1 MB」换成 **`maxWidth` 320 / `maxHeight` 240 / `maxBytes` 500 KB**。
  `targetSize` 从「按总像素等比缩」改成 **按框等比缩**：两个方向的余量取小的那个，长边贴边、
  短边留白，宽高各自不超过一边；**已经在框里的原样返回（小图不放大）**；极端长宽比用
  `math.max(1, …)` 兜住 0、用 `math.min(max…, …)` 兜住浮点误差。
- 编码显式指定 **`chroma: img.JpegChroma.yuv420`**。`encodeJpg` 的默认值是 `yuv444`，
  漏传就是 4:4:4，设备不收。Baseline 由编码器本身保证——`package:image` 的 JPEG 编码器只写
  `SOF0`，没有渐进模式（已对 `image` 4.10.1 源码核实：`jpeg_encoder.dart` 的 `_writeSOF0`，
  4:2:0 时 Y 分量采样因子写 `0x22`、UV 写 `0x11`）。
- **去掉了「原图已经够小就原样返回」的快路径**：选图器交上来的那张是什么采样、是不是
  Progressive，App 看不出来，只有过一遍自己的编码器才能保证格式。重编一张 320×240 只有几毫秒。
- **Skia 给大了的尺寸在 isolate 里再收一次**：`instantiateCodec` 有时按整数倍采样给出比请求值
  大一点的图，以前只是「像素略超」，现在 320×240 是设备的硬框，所以 `_encodeJpeg` 里再算一遍
  `targetSize`，超了就 `img.copyResize`（`Interpolation.average`）。
- **做不出合格的图就返回 null**（原来是「压不动传原图」）：解码失败、编码失败、最低质量档仍超
  500 KB，三种情况都返回 null。两处调用改为提示「图片处理失败，换一张图片再试」并中止上传：
  `animations_page.dart` 返回 `ActionResult(false, …)`，`memorial_edit_page.dart` 弹
  `showAppMessage(..., tone: AppMessageTone.error)` 后直接 return。

### 2. DP165 按 2 字节解（`TuyaConfig` / `TuyaHistoryCodec`）

- **代码没有行为改动**：09-16 那轮按实时 DP 量程（114 是 0–1000）推的就是 uint16 BE ×10，
  `historySampleBytes['humidity'] = 2`、`historyScale['humidity'] = 10` 本来就是这个值。
  1.0.12 把推断坐实，注释从「推的，待真机确认」改成「固件 1.0.12 确认」。
- **帧头仍然按帧长自动判**，没有收紧成固定 3 字节头：1.0.12 说「与 164 对称」，对称口径下 165
  就是 3 字节头，但 `09_16` 导出那一行仍写着 4 字节头，设备上装的是哪版固件也不由 App 说了算。
  按帧长判在点宽 2 时是精确判定（`3+2N` 恒奇、`4+2k` 恒偶），两种帧都解得出，代价为零。
- `test/tuya/status_page_dps_test.dart` 的 165 样帧换成 **1.0.12 的对称形态**（3 字节头
  `1a0910` + `0229 01f4 0258`，解出 55.3 / 50 / 60，与原断言一致）；4 字节头那种帧的覆盖留在
  `tuya_history_codec_test.dart`。

## 关键决策

- **按框缩，不按总像素。** 09-16 是「总像素 ≤ 480,000」，那是后端存储口径；这一版的 320×240
  是**设备屏幕**。一张 240×320 的竖图总像素没超，高度却超出屏幕一截，设备居中显示只能裁掉
  上下两头——所以这次必须按框。两版口径互相矛盾，不是调数字那么简单，`PRODUCT_RULES` 里
  两条都写明了「换了」。
- **压不出合格的图就不传，覆盖 09-16 的「不许挡上传」。** 那条规则成立的前提是「压缩只是
  优化」；现在格式是设备解码器的硬要求，传一张 Progressive 或超框的图上去，App 显示一切正常、
  花盆上是空白，用户和联调都看不出问题在哪。宁可当场报错。
  ⚠️ 这是**推翻了一条写在 §4.3 里的产品口径**，要是产品坚持「宁可传上去也不要挡」，
  把 `prepare` 的三处 `return null` 换回 `return sourcePath` 即可。
- **165 不按固件版本分叉。** 产品口径就是「按 2B 解析即可」。1.0.12 以下的固件报 1 字节点，
  App 解出来是错位曲线——帧长分不出 1B / 2B（`3+N` 和 `3+2N` 都可能是任意长度），兜不了，
  写进文档，靠设备升级。

## 未完成项与风险

- **压缩整条链仍未在真机跑过**（09-16 就没跑过）。真机上要确认的是：压完的图确实能被花盆下载
  并显示；一张 3:4 的竖图压成 180×240 之后在屏幕上是居中留白，不是被拉伸或裁切。
- **「图片处理失败」这条新的失败路径没跑过**。正常图片走不到它，要造一张坏图或者用非图片文件试。
- **165 的帧头形态没真机确认**。1.0.12 的设备如果真按对称口径发 3 字节头，联调日志里那行
  「日 DP165 hex N字节/M点」的字节数应该是奇数；是偶数就说明它仍带点数字节，两种 App 都能解，
  但要不要把文档收紧成固定帧头得看真机。
- 旧固件（< 1.0.12）设备的湿度日曲线会是错位数据，这是已知且接受的（产品口径）。
