# 屏蔽 AP 配网，只走蓝牙双模（为确认设备是否支持）

> 文档类型：Historical Change Record
> 日期：2026-09-11
> 环境：SSH（本机无 Flutter / Android 工具链）
> 分支与起始版本：main / `fd763b0`
> 范围：`lib/src/features/devices/pairing_gate.dart`（新增）、搜索页 / 配网页 / 失败页、`lib/src/state.dart`、Android 桥接、`test/`
> 当前权威文档：`AI_CONTEXT.md`

## 背景与目标

产品要求：**先把 AP（热点）配网整条屏蔽掉，只走蓝牙双模**，目的是在真机上确认
**设备端到底支不支持**蓝牙配网——不支持就由设备方去改固件。配套三条：

1. 页面上要**标注清楚**现在用的是什么方式、报错原因是什么；
2. 搜索结果要能看出**是不是用的蓝牙搜索**；
3. **先不做任何过滤**，蓝牙扫到什么就全部展示出来。

## 为什么必须屏蔽而不是"优先"

上一轮是「BLE 优先、AP 回落」。那套在**验证**场景下是有害的：用户一旦落到 AP 上并配网
成功，「设备支不支持蓝牙」这个结论就被一次成功盖掉了。所以这一轮把每一条通往 AP 的路
都关死，宁可当场失败并说清楚原因。

## 变更内容

### 1. 一个总闸：`PairingGate`

新增 `lib/src/features/devices/pairing_gate.dart`，两个开关：

- `apEnabled = false`：AP 整条关掉；
- `showUnfilteredBleScan = true`：蓝牙结果不过滤。

⚠️ **是门禁，不是删除。** AP 那整条（`pairViaHotspot` / `connectDeviceHotspot` /
`_joinHotspotForPairing` / 原生 `joinDeviceHotspot` / 失败页的「改用热点方式」/ 搜索页的
热点列表与真扫节奏）代码原样留着，翻回 `true` 全部回来。

⚠️ 两个开关**不是 `const`**：用例要两头都跑得起来——关着时验这一轮的行为，开着时验
**AP 那套代码仍然完好**。那才是「屏蔽不是删除」这句话真正的守护。

### 2. 关掉的入口（逐条）

| 入口 | 处置 |
| --- | --- |
| 搜索页设备列表 | `_foundDevices` 只返回 BLE，热点一行不列；`preferHotspot` 不再成立 |
| 搜索页主动 Wi-Fi 扫描 | **不再发 `startScan`**——它唯一的用途是发现设备热点。顺带省下那条「2 分钟 4 次」的配额 |
| 搜索页读缓存 | **保留**：它维持 `wifiScan.current`（手机连的哪个路由器），下一页要拿它把 Wi-Fi 名填好 |
| 搜索页「扫到热点就停扫」 | 跳过，否则会把 BLE 那条的扫描线一起掐掉 |
| iOS 的「下一步」 | 不画——它是 AP 专用入口（iOS 列不出附近 Wi-Fi，只能按前缀直连热点），AP 关着时点下去只会在下一页报错 |
| 失败页「改用热点方式配网」 | 不画。给了退路、用户一退就用 AP 配成了，结论又被盖掉 |
| 配网页拿不到 BLE uuid | **直接进失败页报 `ap_disabled`**，不许悄悄退回 AP —— 悄悄退回是这一轮最要命的错 |

### 3. 不过滤：扫到什么就展示什么

- **Dart**：`bleDevices` 不再剔除 `bound` 的设备。设备若因故被报成已绑定，过滤后页面上
  就是「什么都没扫到」，结论正好反了；列出来并在行上标注「已被绑定」，比藏起来有用。
  这些行**照常列出但点不动**（点下去必然失败）。
- **原生**：`LeScanSetting` 的 ScanType 从只加 `SINGLE` 改成**能加的全加上**
  （`SINGLE / SINGLE_QR / NORMAL / THING_BEACON / MESH / SIG_MESH`）。万一设备报的是别的
  类型，只加 SINGLE 就什么都扫不到，而页面上看起来和「设备没开机」一模一样。
  这一版 SDK 没有的名字只打一行日志、不拦路；一个都匹配不上才抛。

### 4. 页面上标注清楚

- **常驻状态行**（等宽字体、可长按复制）：搜索方式（蓝牙／AP 已屏蔽）、蓝牙可用性、
  扫描进行中及已扫秒数、扫到几台（其中几台已绑定）、过滤：无。
- **原生日志框**：AP 屏蔽期间**只要有日志就画**，不再等到失败——这一轮「扫描起没起来、
  报了什么」本身就是要交付的结论，成功那次的日志同样要能截图。
- **行内小字**：蓝牙 / 信号 / 是否已绑定 / 固件支不支持读 Wi-Fi 列表 / pid。
- **失败建议按路径分流**：`_connectFailureHint` 加 `viaBle`。两条路的失败原因完全不重合，
  串台的建议比没有建议更糟——早先蓝牙失败时会劝用户「等系统的 Wi-Fi 扫描限制缓过来」，
  而蓝牙这条根本不碰 Wi-Fi 扫描，照做只是白等。
- **搜索结论分流**：`_bleOnlyOutcome()`。原来那套结论（限流、没扫到网络、iOS 列不出来）
  讲的都是 Wi-Fi 扫描，而这轮根本不发 Wi-Fi 扫描，原样走下去会给出与事实无关的话。

## 验证结果

- **本机没有 Flutter / Dart / Android / Kotlin 工具链**，analyze / test / 编译 / 真机
  **全部未执行**。
- 静态自检：改动文件括号配平（与 HEAD 相比 Δ 持平；`ai` 那类插值嵌套引号会骗过粗暴
  计数，已改用"先抠 `${...}` 再剥字符串"的口径）；`tools/kt_dangling_refs.py` 通过。
- 用例：搜索页整文件 `setUp` 里把 `apEnabled` 开回来，**保住既有 AP 覆盖**；另加两条
  验屏蔽后的行为（热点一行不列 + 状态行写清楚；扫到什么列什么、已绑定的列出但点不动）。
  失败页加一条「屏蔽后蓝牙失败也不给改用热点」。state 层「已绑的不列」那条显式把
  `showUnfilteredBleScan` 关掉——过滤那套逻辑将来还要用。

## 未完成项与风险

- **整轮未真机验证。** 这一版的目的就是上真机取结论，最需要看的三件事：
  ① 蓝牙到底扫不扫得到花盆（状态行 + 列表就是答案）；② 扫到的话
  `supportWifiList` 是真是假；③ 配网走不走得通、失败码是什么。
- 扫描类型放开之后，附近**别的**蓝牙设备也可能出现在列表里。这是有意的（要的就是
  "扫到什么列什么"），取结论时按 pid / uuid 辨认花盆那一台。
- 结论出来后要么把 `apEnabled` 翻回 `true`（设备不支持蓝牙，回到 AP），要么把
  `showUnfilteredBleScan` 关掉（蓝牙可用，恢复正常过滤）。**两个开关都不该长期停在
  排查态。**
