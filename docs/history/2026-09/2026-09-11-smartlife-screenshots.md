# 2026-09-11 智能生活配网截图分析：它走的是涂鸦「新流程」

## 材料

产品提供两张智能生活 Android 端的配网截图（选完设备之后）：
`docs/配网1.jpg`、`docs/配网2.jpg`。

## 图里看到什么

### 配网1 —— 进度页「正在连接设备…」

副标题「手机尽量靠近要添加的设备」，下面一张卡片列出**整条计划**（只有第一行带转圈，
说明当时正跑第 1 步）：

```
正在尝试建立连接…        ← 转圈中
设备寻找可用Wi-Fi
设备正在连接路由器…
设备激活中
设备即将上线
```

### 配网2 —— 「选择Wi-Fi」页（**决定性的一张**）

- 标题「选择Wi-Fi」，副标题「**选择设备工作Wi-Fi并输入密码**」，右侧还有「找不到Wi-Fi？」
- 列表标题「**可用Wi-Fi**」，右上角「刷新」
- 每一行：SSID + **锁图标** + **信号强度格数**（格数各不相同）

## 结论：这是 `queryDeviceConfigState` 的返回，不是手机扫到的列表

「锁图标 + 信号格数」正对应涂鸦 `WifiInfoBean` 的三个字段
（`ssid` / `rssi` / `sec`，`sec != 0` 即加密），而「设备**工作** Wi-Fi」「设备寻找可用Wi-Fi」
这两句措辞说明列表来自**设备视角**——是设备扫到的，不是手机扫到的。

⇒ **智能生活走的是涂鸦「热点配网新流程」**：
`newOptimizedActivator` → `queryDeviceConfigState`（连上设备、让设备扫 Wi-Fi、把列表带回来）
→ 用户选网络并输密码 → `startActivator` 下发凭据。

顺序是：**选设备 → 建立连接 → 设备扫 Wi-Fi → 用户选网络+输密码 → 配网**。

## 这修正了两条我们此前的判断

1. **不是 EZ。** 此前根据产品在 iOS 上的观察（「选了一下 WIFI 不是设备，输密码就去配网」）
   推断智能生活默认走 EZ 快连——从这两张 Android 截图看，它走的是新流程 AP。
   （iOS 上的观感相似是因为新流程同样"只让用户选 Wi-Fi、不让用户选热点"。）
2. **设备扫到的 Wi-Fi 列表是要展示的。** 此前产品口径是「不需要读设备能看到的网络，
   只用手机当前连着的」，我们据此把 `queryDeviceConfigState` 的返回收下不展示。
   截图显示智能生活**正是把这份列表给用户选**——这也解释了它为什么不需要"手机必须先连在
   目标 Wi-Fi 上"这类前提。

## 「系统弹框能不能改成自己的页面样式？」——不能

那个「要与智能花盆搭配使用的设备 / 取消 / 连接」由**系统进程**渲染（`WifiNetworkSpecifier`
的入网授权 UI），在我们应用之外。App **既改不了它的样式，也替换不掉它**。
截图里这两页**是智能生活自己的页面**，不是被改造过的系统框——它们出现在流程里的位置也不同
（一个是"正在连接设备"的进度页，一个是选网络页）。

所以"把系统框做成自己页面的样子"这条路不存在。真正的问题仍然是：**智能生活的
`queryDeviceConfigState` 为什么能连上设备热点而不弹框，而我们的同一个调用会 45 秒超时。**
候选解释仍是那几个（该热点在手机「已保存的网络」里因而自动重连 / 我们调用时设备已退出配网
模式 / SDK 初始化上还有差异），需要在**刚断电重启过**的设备上复测才能分辨。

## 本轮动作

产品指示「切到 AP 模式吧」：`PairingModeSwitch.current` 默认改回 `PairingMode.ap`
（页面上的开关保留，EZ 随时可切回去试）。测试用例的 `tearDown` 同步改为还原成 `ap`。

## 遗留

- 下一步值得试的是**照截图把新流程补齐**：`queryDeviceConfigState` 成功后**把设备扫到的
  Wi-Fi 列表展示给用户选**（而不是收下不展示），进度页也按那 5 步显示。前提是
  `queryDeviceConfigState` 能连上——这一条必须先在**刚上电**的设备上验证。
- 需要产品确认：是否接受"选网络这一步从设备扫到的列表里选"（这与此前"只用手机当前连着的
  网络"那条口径不同，但截图证明智能生活就是这么做的）。
