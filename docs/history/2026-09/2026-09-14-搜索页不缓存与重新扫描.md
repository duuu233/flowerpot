# 搜索页：设备名不闪、不缓存扫到的设备、重新扫描真的重扫

> 文档类型：Historical Change Record
> 日期：2026-09-14
> 环境：SSH（本机无 Flutter / Dart / Kotlin 工具链）
> 分支与起始版本：main / `116a213`
> 范围：`lib/src/state.dart`、`lib/src/tuya/tuya_repository.dart`、搜索页、`AppRoutes` / `FlowerpotApp`、Android `MainActivity.kt`、`test/`
> 当前权威文档：`docs/PRODUCT_RULES.md` §1.5、§2；`AI_CONTEXT.md` 双模动线

## 背景与目标

产品三条反馈（原话摘要）：

1. 搜索出设备时名称会闪一下，先显示一串字符再显示名称——**等最终要呈现的字出来再展示**；
2. 关掉设备再去搜，**还是会搜出设备**——按真实情况搜，不要缓存；
3. 「还没搜索到设备」时下面那一大段改成「请确认设备处于配网状态后，点击重新扫描」，插图换成
   `assets/images/pairing_failure_illustration.png`；并核查**重新扫描和前面的扫描逻辑是否一样**
   ——反馈点了重新扫描扫不到设备。

## 根因

### 2 与 3 是同一处：`startBleDiscovery` 开头那句 `if (_bleScanning) return true`

- **扫到的设备从来不清**：`_bleDevices` 挂在全局 `FlowerpotState` 上，和 App 活得一样久。
  搜到过一次的设备，关机之后再进搜索页照样在列表里（不是涂鸦 SDK 或系统在缓存）。
- **原生扫描到时（默认 60 秒）停了，Dart 不知道**：原生 `onScanStop` 一直在发
  `bleScanStopped` 事件，Dart 侧没有任何订阅，`_bleScanning` 永远是 true。于是「重新扫描」
  调到 `startBleDiscovery` 时直接被上面那句 return 掉，**原生根本没有重新开扫**。
  页面上雷达照转、文案照写「搜索附近设备...」。
- 顺带：搜索窗口 3 分钟而原生扫描 60 秒，后两分钟是在假装搜索；从「连接 Wi-Fi」页退回来时
  扫描已经停了（点「连接」时停的），列表是那一刻的旧结果，也没有任何东西重开。

### 1：09-12 修过一次，修法本身会闪

09-12 把「先画广播标识 `设备 uuid23119e…`」改成「先画 `正在识别设备…`」。行先出来、字后定，
产品看到的仍然是字换了一次。

## 变更内容

1. **`startBleDiscovery` 每次都是全新一轮**：还在扫就先停，清空 `_bleDevices` 与回调计数，再开。
   接上 `bleScanStopped`（新增 `TuyaRepository.bleScanStops`），原生到时 / SDK 自停时把
   `bleScanning` 置回 false。`uuid → 云端产品名` 表跨轮保留（只决定叫什么，不决定在不在）。
2. **Android `onScanStop` 只替当前这一轮上报**（`bleScanner === self`）：重开时先停旧的再开新的，
   旧代理的结束回调可能晚到，照发会把新一轮标成已结束；Dart 主动停扫的那次也不报。
3. **停扫认主人**（`stopBleDiscovery(owner:)`）：失败页「返回搜索设备」是 `pushReplacementNamed`，
   新搜索页压在老的上面；从新页退回时老页重开一轮，而新页 `dispose` 要等退场动画结束才跑，
   不认主人就会把老页刚开的这一轮掐掉。
4. **断链路不再挂在"还在扫"后面**：`disconnectBleDevice` 原来写在 `if (!_bleScanning) return`
   之后，以前 `_bleScanning` 恒为 true 所以每次都断；现在它会如实变 false，不挪出来就会漏断。
5. **搜索页**：
   - 进页面 / 「重新扫描」/ 回前台（没在扫时）/ 从上层页面退回（`RouteAware.didPopNext`，
     新增 `AppRoutes.routeObserver` 挂在根 Navigator 上）/「重新检测」都走 `_scan()`；
   - 回前台与退回的自动重开有门槛：正在扫、本页不在最上层、正在连某台、本轮还在准备
     （授权框本身会触发 resumed）、AP 开着时都不重开；
   - 轮次号 `_round`：旧一轮的 `_startSearchWindow` await 回来发现已被顶掉就收手，不叠定时器；
   - BLE 扫描时长 = 搜索窗口（3 分钟）；
   - **名字未定的设备整行不画**（`_bleFound` 过滤 `productInfoPending`），撤掉「正在识别设备…」；
     云端产品名查询加 5 秒超时，超时退回广播名，避免设备一直不出现；每查完一台就通知一次；
   - 「还没搜索到设备」：一句「请确认设备处于配网状态后，点击重新扫描」，插图换失败图、不画
     扫描线；AP 那条（`_outcome` 的 `_stalled`）同一套标题、文案、插图。
6. 测试：状态层两条（全新一轮 / 停扫认主人）；搜索页四条（名字回来前不画行、名字超时退回广播名、
   40 秒没搜到的文案插图与重新扫描真的重开、从「连接 Wi-Fi」页退回重开）；既有 AP 用例的文案断言同步。

## 关键决策

- **不缓存的边界**：清的是"扫到了哪些设备"；`uuid → 产品名` 不清。后者清掉只会让每轮都多等一次
  云端往返（名字未定时整行不画），而它与设备在不在无关。
- **不做轮内过期**（设备在一轮扫描中途关机、N 秒没新广播就移出列表）：`setRepeatFilter(false)`
  下 SDK 是否真的按广播间隔重复回调没有真机证据，贸然加过期可能让开着的设备一闪一闪。
  需要时先看排查态状态行里「SDK 回调 N 次」是否随时间增长。
- AP 那条（`PairingGate.apEnabled = false`，仍屏蔽）的回前台 / 退回行为**不变**：它的真扫受
  4 次 / 2 分钟配额约束，自动重开会白烧配额。
