# 2026-09-10（晚）搜索页：进页面先免费读缓存，等权限落定再开窗口与真扫节奏

## 背景（用户反馈）

1. 初次加载进来要授权，用户来不及点设备；希望**等授权完再触发真实搜索**。
2. 不是初次加载时，希望**等页面加载完或稍微延迟再触发**，让设备能马上被搜出来；
   「现在错过前面 2 次搜索，后面每次都要等 32 秒太久了」。
3. 配网时那个「要与智能花盆搭配使用的设备 / 取消 / 连接」弹框能不能不要、自动按连接。

环境：home / `/pgdata/pg/dh/flowerpot`，分支 `main`，起始提交 `449d911`。

## 诊断：1 和 2 是同一个根因

`scanWifi` 在原生侧是**要权限的**（`MainActivity.kt` 的 `needsWifiPermissions` 名单里
有 `pairWifiDevice` / `scanWifi` / `apQueryDeviceWifi` / `apStartPairing`），首次进入会弹
系统授权框，而原生的做法是把这次调用**挂起**（`pendingPair`）、等 `onRequestPermissionsResult`
再执行。于是改之前：

- 进页面立刻起 3 分钟 `_deadlineTimer` ⇒ **授权那几十秒白白吃掉窗口**；
- 第一次取数就是 `probeWifi()`（真扫），它被挂在权限框后面 ⇒ 用户点「允许」的那一刻
  才真正发出，而 32 秒的节奏也从那时才起算。算下来授权越久、前面越空。

至于「每次都要等 32 秒」——32 秒是 Android 配额（前台 4 次 / 2 分钟）允许的最快**稳态**
节奏，不能再快；但**进页面那一下本来不必花配额**：读系统扫描缓存不受配额限制，而系统
自己、设置页、别的应用一直在扫，缓存里往往已经有设备热点了。

## 改动

`lib/src/features/devices/presentation/device_search_page.dart`

`_scan()` 拆成两段，新增 `_startSearchWindow()`：

```
_scan()                     取消旧定时器、复位状态、雷达转起来
_startSearchWindow()
  ├ prepareForPairing()     云端预取（不在权限门禁名单里，互不影响）
  ├ ① probeWifi(refresh: false)   ← 免费；首次进入的权限框挡在这一步
  │    命中就 _maybeAutoOpen()，一次 startScan 都不用发
  └ ② 权限落定后才开始：_deadlineTimer（3 分钟窗口）
       + _pollTimer（1 秒读缓存）+ _runScan()（32 秒一次真扫）
```

要点：

- **让挡在权限框前面的那一次是「读缓存」而不是「真扫」。** 读缓存不占扫描配额，
  所以用户点「允许」之前一次真扫都不会被浪费。
- **窗口与节奏都从授权之后才起算**，不再被授权时间吃掉。
- 非首次进入时这一步几乎不耗时，缓存里已有热点的话**设备在进页面瞬间就出现**。
- 预热那次失败不下结论（权限被拒等）：紧接着的真扫会给出权威结果与原因。
- ⚠️ 注释里写明了**不要为了快在开头塞两次真扫**——那是 0/6/46/86s 那版的做法，已被
  证明会把配额押在设备还没上电的时刻，反而让「先进页面后开机」要等 86 秒。

## 第 3 条：那个弹框删不掉

「要与智能花盆搭配使用的设备 / 取消 / 连接」是 **Android 系统**的入网授权框，
`WifiNetworkSpecifier` + `requestNetwork` 在 Android 10+ 上必弹，**没有任何 API 能抑制
它或代替用户点「连接」**。这一条 2026-09-10 已向涂鸦求证并实测确认过（对方第一轮给的
`ThingSmartHotspotCredentialKit` 经查在两个官方 Maven 仓库与它自己给的文档里都不存在，
第二轮改口「未公开发布」）。

现状已经做到的：手机**已经连在该热点上**时（上次配网留下的、或用户自己在系统设置里连
过）直接跳过 `requestNetwork`，不会白弹；弹框只在用户点了「开始配网」之后出现，是流程
里预期的一步。

唯一能把它降到「一次性」的公开路子是 `WifiNetworkSuggestion`（首次用通知授权一次，之后
系统自动连匹配的网络）。**代价是连接时机由系统决定、不可控**，而配网要求「此刻就连上」，
所以没有直接改——需要产品决定是否接受这个代价。
