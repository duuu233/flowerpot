## 一、规格书读出来的两条硬事实

本机没有 `pdftoppm`，用纯标准库解出 PDF 的 ToUnicode CMap 再解码文本（脚本用完即删，
未入库）。两条与配网直接相关：

### 1. 模组**确实是 Wi-Fi + BLE 双模**，蓝牙 LE 5.4

> Wi-Fi（b/g/n/ax）+ 蓝牙（LE）双模 IoT 模组
> • 支持蓝牙 **LE 5.4** 标准 • 支持蓝牙低功耗 1 Mbps 和远距离模式（125 Kbps）
> • 发射功率 +6 dBm • 接收灵敏度 −97 dBm

⇒ **硬件支持蓝牙配网，这条不用再问设备方**。

### 2. ⚠️ 「蓝牙配网」和「热点模式配网」是**两个独立的工作状态**

功耗表里两者分行并列，各有各的电流与指示灯状态：

| 工作状态 | 说明 |
| --- | --- |
| **蓝牙配网** | 模组处于蓝牙配网状态 |
| **热点模式配网** | 模组处在热点配网状态 |
| 弱网连接状态 | 指示灯快闪 |
| 网络连接状态 | 指示灯常亮 |
| 网络断连状态 | 指示灯常灭 |

**这很可能就是真机扫不到的原因**：设备上电后进的是**热点配网状态**（它确实在拉
`SmartLife-xxxx` 热点，我们一直扫得到），而在那个状态下**未必同时广播 BLE**。

⇒ **要问设备方的问题变成了两条具体的**：① 设备上电后默认进哪个状态？② 怎么切到
「蓝牙配网状态」（长按？特定次数上下电？还是固件要改默认）？两种状态的指示灯分别是
什么样，好让测试同学肉眼确认。

## 二、按 pid 认花盆（产品 pid：`yciq4kssu1fv8umn`）

不过滤扫描时附近可能有一堆别的涂鸦设备，花盆混在中间要人一行行找。现在：

- **pid 匹配 `TuyaConfig.productId` 的置顶**（同组内仍按信号排），行上标 `★ 本产品`；
- 状态行单独一句 **「本产品（yciq4kssu1fv8umn）：扫到 N 台，已置顶 / 未扫到」**
  ——这一行就是「到底有没有搜到花盆」的答案。

pid 与固件烧录的 PID 严格一致，是唯一可靠的判据：广播里的名字常常是空的，mac 每台都不同。

## 三、云端补产品名（`getActivatorDeviceInfo`）

产品给的思路，解包核对**确实存在**：
`IThingDeviceActivator.getActivatorDeviceInfo(productId, uuid, mac, IThingDataCallback)`。

BLE 广播里常常没有名字，页面上一行只有 `mac + pid + rssi`，人没法判断哪台是花盆。
拿 pid 去云端换回产品名之后，列表才真的能"看出有没有"。

⚠️ 这是**云端往返**，所以：按信号从强到弱**只查前 20 台**（`_productInfoBudget`）、
每台**只查一次**（查空也占位，否则每条扫描回调都会重试同一台）、并发用
`_productInfoInFlight` 挡住。行上在查到之前显示「产品名查询中…」，免得用户以为
"这台就是没名字"。

## 四、同一批里**没有采用**的东西

产品连续贴来几段 AI 生成的示例，其中这些在 7.5.1 全模块 **0 命中**（已解包核对）：
`ActivatorService` / `ActivatorMode.BLE` / `BLEActivator` / `IDiscovery` / `DiscoveryMode` /
`IDiscoveryListener` / `IBluetoothDevice.getProductId()` / `startConfigBLEWifiDeviceWithUUID` /
`ThingBLEAdvModel`。前者属于**设备固件侧 TuyaOS（TKL）**的命名，后两个是 **iOS** 的写法。
`ACCESS_BACKGROUND_LOCATION` 与前台服务只在**后台扫描**时才需要，本项目前台扫，不加。

**能用的那两条都用了**：`getActivatorDeviceInfo`（本轮实现）、`deviceType` / `config_type`
（`ScanDeviceBean` 早已回报，行上可见）。
