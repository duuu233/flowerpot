# 配网动线七项：键盘避让、弹框收敛、搜索页内联列表、失败页版式、启动页只留背景

> 文档类型：Historical Change Record
> 日期：2026-09-10
> 环境：SSH（无 Flutter/Dart 工具链、无 Android SDK）
> 分支与起始版本：main / bef2ca0
> 范围：`lib/src/features/auth/presentation/`、`lib/src/features/devices/presentation/`、`lib/src/features/splash/`、`lib/src/state.dart`、`lib/src/tuya/tuya_models.dart`、`lib/src/routes/app_routes.dart`、对应用例
> 当前权威文档：`AI_CONTEXT.md`

## 背景

产品一次给了七条，集中在配网动线上，其中第 5 条是「配网又不行了，昨天改了优化版本，是不是影响到了」。

## 逐条

### 1. 输入框获焦时被系统键盘挡住

登录、注册、找回密码、连接 Wi-Fi 四页统一改成表单页的通行做法：
`resizeToAvoidBottomInset: false`（页面保持整屏高度，不被压缩得整页跳一下）+ 滚动区底部
`MediaQuery.viewInsetsOf(context).bottom` 让出键盘那么高的一段。焦点落到输入框时 Flutter 自己
会把光标滚进可视区，输入框正好停在键盘上方。

⚠️ 只靠 Scaffold 默认的 resize 不够：内容本来就放得下一屏时**不会产生可滚动区间**，光标
「滚进可视区」无处可滚，输入框照样被盖住——这正是这次的现象。

### 2. 配网阶段不要多余弹框，必要文案并进 1/2/3 步

- **`PairingStage.hint`**：三步各带一句说明，只在「进行中」那一步画出来（三行同时铺出来
  用户不知道该看哪句）。
- **删掉「正在确认账号与家庭」那层全屏遮罩**：准备阶段（确认家庭 + 取令牌）并进进度页的
  第一步，`_preparing` 字段一并去掉。
- **删掉「请先到系统设置连接设备热点」那条 toast**：页面上本来就有一段引导文案。
- **不再用通配前缀去请求系统弹框**（关键）：`WifiNetworkSpecifier` 给 `setSsidPattern` 时走的是
  「按模式搜索」那一支，系统弹的正是产品截到的**「查找设备…」→「没有找到任何设备。请确保要
  连接的设备已打开并准备好进行连接。」**。现在只用确切热点名请求；拿不到名字就以
  `hotspot_unknown` 失败并让用户回搜索页选设备，而不是丢给系统去猜。

  ⚠️ **系统那个「连接到 xxx?」确认框删不掉**：Android 10 起应用不能自己连任意 Wi-Fi，
  `WifiNetworkSpecifier` 必然弹一次确认，这是系统 UI。能做的只是不触发那个更啰嗦的
  「搜索」变体。

### 3. 第三步「连接云端」给 1–2 秒随机停留再按成功处理

`_pairInternal` 在 `_pairOrRecover` 返回后设 `connectingCloud`，随后 `Future.delayed(1–2s 随机)`
再返回成功。**这一步目前没有接任何实际业务**——activator 返回时设备其实已经注册到云端，没有
可等的东西；不停留的话第二步刚亮起就跳走了。真接上云端回执后把这段延时换成真正的等待即可。

### 4. 配网失败页版式：小提示和上面的文案重叠 + 多余滚动条

根因是写死的绝对定位：标题 `top:315`、副标题 `top:362`、小提示卡 `top:400` —— 副标题只有
**38px** 的空档，而它是 14px/1.5 的两行（**42px**），失败码带上提示语时必然顶进小提示卡里。
同一段 `SizedBox(height: max(690, 屏高))` 又把内容硬撑到 690，矮屏上凭空多一条滚动条。

改成正常的纵向流（`ConstrainedBox(minHeight) + IntrinsicHeight + Column`，按钮用 `Expanded`
推到底部），每段自己占高度，副标题不再 `maxLines: 2` 截断——截断反而把唯一能照着做的那句话
吃掉了。内容够放时不再出现滚动条。

### 5. 搜索页改成「监听器」：扫到就列在下面，不跳页

- 扫到的热点直接画成列表（`device-search-found-list`），点哪台就带哪台的 SSID 进「连接 Wi-Fi」。
- 自动 `pushReplacementNamed(deviceSelection)` 删除；**`device_selection_page.dart` 与
  `AppRoutes.deviceSelection` 一并删除**（那一页唯一的职责就是列热点 + 点了带 SSID 跳走，
  现在搜索页自己做了）。配网失败页的「返回选择设备」改成「返回搜索设备」。
- 自动跳走会把「还有第二台正在冒出来」整个吃掉，用户也没机会确认自己点的是哪台。

### 6. 去掉「设备已在配网状态，继续」

按产品要求删除按钮、文案与 `_continueAnyway`。

⚠️ **这条有代价，需要产品复核**：iOS 不枚举附近网络（`scanWifi` 只返回当前连接的那一个），
搜索页在 iOS 上**永远列不出任何设备**，而这个按钮是 iOS 唯一能进下一步的入口。删掉之后
**iOS 用户走不到配网**。Android 上被系统限流、或热点名落在
`WifiNetwork.isDeviceHotspotName` 白名单之外时，同样没有出路。

### 7. 启动页先只留背景图

`SplashPage` 的 logo / 字标 / 标语整块不画。是「先隐藏」不是删除：代码留在
`_buildBranding()` 里，`_showBranding` 改回 true 就恢复原样。

### 关于第 5 条「配网又不行了」的排查

昨天（09-09）动到配网的是 `d0ab4d0`（家庭按账号固定 + 配网前 `prepareForPairing`）、
`1763f74` / `ffbefb6` / `c612166`（家庭 id 与账号键）。最可疑的是 **`prepareForPairing` 里那道
新门禁**：

```dart
if (home == '0') throw TuyaException('home_unresolved', '没能确认账号下的家庭…');
```

它把「查不到家庭」当成了「不能配网」。`currentHomeId` 返回 0 只表示此刻还没解析出来，涂鸦的
activator 自己会在配网时解析家庭；而这一步跑在**手机还连着路由器**的时候，本来就不存在
「在设备热点上查家庭 → 拿到空列表 → 自动建空家庭」那个风险（那才是 `d0ab4d0` 要防的东西）。
门禁一触发，「开始配网」直接失败、配网根本没开始——现象正是「昨天还能配，今天点了没反应」。

本轮把它降级为诊断：家庭没解析出来时不再抛错，照常往下走，结果文案写「准备就绪（家庭待解析）」。
真的没有家庭时配网自己会失败，那时的报错才是真实原因。

⚠️ **这是基于代码的推断，不是实测**：本机没有设备也没有 SDK。若真机上换掉这道门禁仍然配不了网，
下一个要查的是 `setHomeId` 钉住的家庭是否过期/不属于当前账号（`ffbefb6`/`c612166` 改过账号键），
排查看设备列表页底部那行 `sessionDiagnostics` 与 `[pair]` 日志。

## 追加（同日）：设备开机即可配网，文案整体改口

产品补充说明：**设备只要开机就一定处于可配网状态，不需要多余的操作去确认**；搜索页的职责
就是把设备搜出来并展示。原来那批文案全部建立在「用户要先把设备弄进配网状态」这个前提上，
与事实不符，一并改掉：

| 位置 | 原文 | 现在 |
| --- | --- | --- |
| 搜索页·搜索中 | 请让设备进入配网状态，并确认手机连接的是2.4GHz Wi-Fi | 请确认设备已开机，并确认手机连接的是 2.4GHz Wi-Fi |
| 搜索页·没找到 | **未发现配网中的设备** / 请长按设备按键让它进入配网状态后重新扫描。 | **未发现设备** / 请确认设备已开机并靠近手机后重新扫描。 |

| 搜索页·平台不枚举 | 当前系统不提供附近网络列表。确认设备指示灯已进入配网状态后继续下一步。 | 当前系统不提供附近网络列表，无法在这里列出设备。 |

## 追加（同日）：iOS 的入口——列不出设备，但配得了网

上一节删掉「设备已在配网状态，继续」之后 iOS 没了入口。查证结论与补法：

**iOS 列不出附近设备，而且没有替代方案。** 系统没有任何公开 API 能枚举附近热点：
`NEHotspotHelper` 需要 Apple 特批的 entitlement（基本只发给运营商/热点服务商），
`CNCopyCurrentNetworkInfo` 只回答「此刻连着哪个」。这是平台限制，不是搜不到。

**但配网本身不需要先列出来。** 本仓库 iOS 侧早就用的是
`NEHotspotConfiguration(ssidPrefix:)`（`AppDelegate.swift`）：按**前缀**直接连设备热点，
系统弹一次确认框即可，不需要确切 SSID。加上「设备开机即可配网」这条事实，iOS 上没有任何
要用户确认的东西——所以给一个**无条件的「下一步」**就够了，它和被删掉的那个
「设备已在配网状态，继续」不是一回事（那个要用户确认一件永远为真的事）。

改动：

- `device_search_page.dart` 新增 `_canListNetworks`（`defaultTargetPlatform != iOS`）。
  iOS 上按钮换成「下一步」（`device-search-continue`），直接进「连接 Wi-Fi」且**不带热点名**；
  Android 上仍是「重新扫描」。iOS 的标题/说明也改成「本机无法列出附近设备 / iOS 不提供附近
  Wi-Fi 列表…设备开机即可配网，直接下一步即可」。
- **修回上一节引入的回归**：上一节在 Dart 侧直接拒绝了「没有确切 SSID」的请求
  （`hotspot_unknown`），而 iOS 的 target **永远**是 null —— 那等于把 iOS 的唯一通路也砍了。
  现在恢复前缀路径，把「拒绝通配」下放到 **Android 原生**：`joinDeviceHotspot` 收到空 ssid 时
  直接回 `hotspot_ssid_required`，`setSsidPattern` 那一支连同 `PatternMatcher` 的 import 一起删掉。
  这样 Android 永远不会触发系统那个「查找设备…／没有找到任何设备」的搜索框，而 iOS 照常走前缀。
- 失败页新增 `hotspot_ssid_required` 的提示：「还不知道要连哪台设备，请回到『搜索设备』页从
  列表里选中设备后再配网」。

⚠️ **iOS 那条路本轮一次都没验过**：没有 Mac、没有 Xcode、没有设备。`NEHotspotConfiguration`
需要 `com.apple.developer.networking.HotspotConfiguration` entitlement（Xcode Capabilities 里
可以自助开，不需要 Apple 审批），签名配置是否已经带上它需要在有 Xcode 的机器上确认。

## 追加（同日）：「重新扫描」只在一台都没搜到时才出现

产品口径：**重新扫描按钮要等搜索不到任何设备、搜索为空的时候再显示。**

改前是「全程都在，搜索中置灰」。现在按状态分：

- **能列设备的平台（Android）**：只有 `!_scanning && hotspots.isEmpty` 才画。搜索中点它只是
  白烧一次系统配额（每 2 分钟 4 次）；已经搜到设备时用户要点的是那台设备，不是再扫一遍。
- **iOS**：「下一步」**全程都在**——那是它唯一的入口，列不出设备是平台限制，让用户干等一轮
  3 分钟的窗口没有任何意义。

`_SearchActions` 收敛成一颗按钮，`onRescan` / `onContinue` 二选一（构造函数里 `assert` 挡住
两个都给或都不给）。

## 追加（同日）：搜到设备为什么要等一分钟，怎么加快

反馈：「搜索了一分钟才搜索出来」；另一条：「带出这个 wifi 名称很慢，上一个安卓包就很快」。

### 根因：两次主动扫描之间那 30 秒是完全瞎的

改前的节奏是「2 次快扫（3 秒间隔）→ 之后 30 秒一次」。30 秒是 Android 配额（前台每 2 分钟
4 次 `startScan`）算出来的，本身没错——错在**那 30 秒里什么都没做**。设备上电到热点广播出来
要几十秒，它在空档里冒出来，也要等到下一次真扫才看得见。最坏就是产品说的那一分钟。

### 关键事实：受配额限制的只有 `startScan`，读 `scanResults` 不受限

而且系统自己（连接管理、设置页、别的应用）同样在扫，缓存会被它们刷新。所以：

- `scanWifi` 新增 `refresh` 参数。`refresh = false` 时**只读缓存**：不调 `startScan`、
  不等 `SCAN_RESULTS_AVAILABLE` 广播，立刻返回快照。一路透传
  `TuyaRepository.scanWifi({refresh})` → `FlowerpotState.probeWifi({refresh})`。
- 搜索页改成**两条线并行**：`_forceScanGap = 30s` 的主动扫描（受配额约束，保证有真扫）+
  `_cachePollGap = 2s` 的读缓存（不受约束、几乎不耗时）。设备热点一旦被**任何一次**扫描
  看到——我们的还是系统的——最多 2 秒就出现在列表里。
- `_throttled` 的「缓存太旧」兜底判断只在**主动扫描**之后做：读缓存本来就不刷新缓存，
  `ageMs` 偏大是常态，拿它判限流会把每次读缓存都误判成被限流。

### 「带出 Wi-Fi 名称很慢」是同一个根因

「连接 Wi-Fi」页填 SSID 只需要 `current`，它来自 `WifiManager.connectionInfo`，**根本不需要
扫描**；而改前 `_loadNetworks` 一上来就 `probeWifi()`（真扫），要等最多 5 秒的系统广播、被
配额挡住时更久。现在只走 `refresh: false`，几乎瞬时。附近网络列表留给「切换」那个弹层自己拉。

### 顺带：SSID 带出的规则收敛（产品口径）

1. **手机连着 Wi-Fi 就直接带出来**；
2. **没连就留空**，让用户自己去「切换」里选。

唯一例外：手机此刻挂在设备热点上（上一次配网失败留下的）按「没连」处理——那个名字填进去
等于让设备去连它自己。**频段不再作为过滤条件**：连的是 5G 时照样带出来，由页面上那条频段
提示去说明；空着一个框反而让人不知道该做什么。

### 顺带：「发现 N 台设备」字号缩小

`_SearchOutcome` 加 `compactTitle`：这一屏下面紧跟着设备列表，重点在列表上，标题由 28/24
收到 20/18。「搜索附近设备…」「未发现设备」是主标题，仍是 28/24。

## 追加（同日）：30 秒是哪来的规则，能不能更快

**规则出处**：Android 9（API 28）起的 Wi-Fi 扫描节流——**前台应用每 2 分钟只许 4 次
`startScan`**（后台每 30 分钟 1 次）。超额时 `startScan` 直接返回 false、不再广播，
`scanResults` 返回上一次的缓存。见 Android 官方文档「Wi-Fi scanning restrictions」。
用户可以在开发者选项里关掉「Wi-Fi 扫描节流」（Android 10 起有这个开关），所以开发机上
常常测不出来。iOS 不适用——它根本不提供扫描接口。

**能更快，方式是把配额front-load 而不是均匀摊开。** 4 次 / 2 分钟不等于「必须 30 秒一次」，
它是一个**滑动窗口**约束。改成：

| | 时间表 | 第一次补扫 |
| --- | --- | --- |
| 改前 | 0 / 30 / 60 / 90s（均匀） | 30 秒 |
| 现在 | **0 / 6 / 46 / 86 / 126s** | **6 秒** |

任意 2 分钟窗口里都不超过 4 次，仍然合规；而「用户打开页面时设备早就开着」这个最常见的
情形，第二次真扫从 30 秒提前到 **6 秒**。中间的空档仍由 2 秒一次的读缓存补上（不占配额）。

**还能更快的一条路（未做）**：Android 13（API 33）起有
`WifiManager.registerScanResultsCallback`——**任何**扫描出结果时推一次回调，可以把现在
2 秒的轮询延迟降到接近 0。只对 API 33+ 有效，需要新增一条事件通道，本轮没做。
