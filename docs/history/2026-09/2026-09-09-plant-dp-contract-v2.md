# 植物 DP 契约改版：116 变植物 id、162 变「弹不弹窗」

> 文档类型：Historical Change Record
> 日期：2026-09-09
> 环境：SSH
> 分支与起始版本：main / fa54740
> 范围：`TuyaConfig` DP 表、`tuya_models`、`FlowerpotState`、设备列表页、设备详情（首页）、设备设置页
> 当前权威文档：`AI_CONTEXT.md`

## 新契约

| DP | 旧 | 新 |
| --- | --- | --- |
| 116 `plant_variety` | 字符串标识符（后台 `tuYaRemark`） | **植物 id**：`-1` = 盆里没有植物，`0..N` = 具体植物，数值等于管理后台植物管理里的「涂鸦标识 ID」（`0` 是通用植物） |
| 162 `plant_confirm` | 数值 0 正常 / 1 异常 / 2 确认 / 3 忽略，App 会写 2、3 | **两态、只上报**：`0` 不弹窗、`1` 弹引导窗。App 不再写这条——下发 116 之后固件自己改回 0 并立即上报；116 为 -1、或用户关掉自动检测时固件同样报 0 |

## 变更内容

### 数据层

- `PlantConfirmState` 收敛为 `hidden(0)` / `prompt(1)`，`fromDp` 只认 1，其余一律不弹。
- 新增 `PlantVariety`：`none = -1`、`parse`、`hasPlant`、`isMissing`。
- `FlowerpotState`
  - `hasPlant`：先看 116 是不是 -1（明确没有），再看本地缓存；`plantMissing` 直接读 116。
  - `plantGuidePending`：162 == 1。
  - `reportedPlantName`：按当前 116 在目录里取名字，供引导窗显示。
  - `_plantKey`：植物标识归一化——能解析成整数就按整数比，解析不出才退回小写字符串。**老固件报的 `tuYaRemark` 标识符仍然能匹配**，新旧数据可以并存。
  - 删除 `answerPlantConfirm`（App 不再写 162），新增 `confirmDetectedPlant`：把设备当前上报的植物 id **原样回写** 116，能解析出植物时顺带下发分类 161。
  - 设备上报 116 = -1 时清掉 `_plantOverrides` / `_plantedDevices`（`SmartPlanterDevice.plant` 是非空字段，不动那个对象，界面一律用 `plantMissing()` / `hasPlant()` 判断）。

### 交互

- **设备列表页**：删掉「没有植物就先送去选植物」这道门禁（需求第 6 条），只保留离线拦截。
- **设备详情页（首页）**：进页面先补植物资料，再看 162——报 1 就弹「发现新植物」引导窗，不再叠加「有没有植物」「自动检测开没开」这些条件（固件已经保证这些情况报 0）。
  - 引导窗（**植物 id = 1..N**）：标题「发现新植物」，正文「已检测到 xxx 植物，请确认植物。」（名字按 116 从后端目录读，读不到写「新植物」），按钮「确认」/「选择植物」，下方两条提示（「1、选择植物请确保与花盆植物一致」「2、忽略检测结果，可前往设置关闭植物自动检测」），返回键关掉则什么都不发、下次进页面还会弹。
  - 引导窗（**植物 id = 0，通用植物**）：单独一支——固件只认出「有植物」但认不出品种，后台也不再为 0 建植物数据，没有可确认的对象。正文换成「已检测到通用植物，请选择并确认植物。」，**按钮只留「选择植物」**，其余（标题、两条提示、返回键行为）与上一支相同。
  - 「确认」→ `confirmDetectedPlant`（回写 116）；「选择植物」→ 跳植物选择流程，由那条流程下发。
- **116 = -1 的界面**：首页正中画不带植物的设备图（`smartPlanterDevice`，忽略后台图片）；「今日养护」整行换成惊叹号 + 「未检测到植物，请将植物种入花盆。」（`Key('home-care-notice')`，不轮播、不显示标题）；设备设置页的「植物」入口点了只提示同一句话，不进选择页。

## 关键决策

- 匹配用「能解析成数字就按数字比，否则按字符串」而不是硬切数字：后台数据改造和固件升级不会同时到位，硬切会让老设备一进详情页就变成「无植物」。
- 116 = -1 时不清 `device.plant` 对象：那是非空字段，详情页多处直接读；清掉要改一大片空安全，风险大于收益。界面判断统一走 `plantMissing()`。
- 引导窗不做二次确认：新契约里「确认」只是回写设备自己报的 id，不像旧的 162=2 那样会让设备换植物，误触成本低。

## 验证结果

- 本机（SSH 开发机）**没有 Flutter/Dart SDK**，`flutter analyze` 与 `flutter test` 均未执行。只做了静态自检：改动文件括号配平、无残留的 `PlantConfirmState.mismatch/confirmed/ignored` 与 `answerPlantConfirm` 引用、`home_page` 去掉已不再使用的 `tuya_models` import、`device_list_page` 去掉不再使用的 `plant_picker_page` import。
- 测试已同步（未运行）：`home_plant_confirm_test.dart` 整份改写为新交互 5 例；`device_list_page_test.dart` 把「没植物就跳选择页」改为「直接进详情页」；`state_backend_integration_test.dart` 新增「116 报 -1 就是没有植物」。

## 未完成项与风险

- **必须在有 Flutter SDK 的机器上跑 analyze/test**，并用真实设备验证：162=1 弹窗、确认后固件是否把 162 改 0 并回报、拔掉植物后是否报 -1。
- 依赖后端配合：管理后台植物管理的「涂鸦标识 ID」要改成与固件一致的数字。**`ID = 0` 的通用植物由后台删除、不建数据**，App 对 0 走专门的「请选择并确认植物」文案，不去目录里找它。在后台数据改造完成前，1..N 也会因为目录里匹配不到数字 id 而拿不到植物名，引导窗会显示成「已检测到新植物」。
- 需求里的「关闭自动检测后固件仍报 162=0」「下发 116 后固件立即回报」属于固件侧，App 这边只是不再自己兜底。
