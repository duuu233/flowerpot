# 真机搜索不到设备：`neverForLocation` 把扫描结果过滤掉了

> 文档类型：Historical Change Record
> 日期：2026-09-11
> 环境：SSH（本机无 Flutter / Android 工具链）
> 分支与起始版本：main / `95fcfc6`
> 范围：`AndroidManifest.xml`、Android 桥接、`lib/src/tuya/tuya_models.dart`、仓库层、`lib/src/state.dart`、搜索页、`test/`

## 现象

上一版（只走蓝牙、不过滤）真机**一台设备都搜不到**。产品转述涂鸦口径：Android 6.0+ /
Android 10（API 29）都支持蓝牙双模配网，只需按版本适配权限——

- **≤ API 29**：`ACCESS_COARSE_LOCATION` / `ACCESS_FINE_LOCATION` + `BLUETOOTH`、
  `BLUETOOTH_ADMIN`，**定位权限为必需**（系统强制要求用于 BLE 扫描）；
- **≥ API 31**：可选仅用 `BLUETOOTH_SCAN`（带 `neverForLocation`），无需定位权限，
  **除非需扫描 iBeacon 类广播**。

## 根因（最可能的那条）

清单里 `BLUETOOTH_SCAN` 带着 `android:usesPermissionFlags="neverForLocation"`。

那个标志的作用是向系统保证「本应用不会用蓝牙推断位置」，换来的是 Android 12+ 免申请
定位权限；**代价是系统会过滤扫描结果**——凡是可能被用来推断位置的广播（iBeacon 那一类
厂商自定义数据）都会被剔掉，应用**根本收不到**。

涂鸦那句「**除非需扫描 iBeacon 类广播**」说的正是这件事，而待配网设备广播的恰恰是这类
厂商数据。于是：**不报错、不回调、静默为空**，页面上和「设备没开机」完全分不开。

第二条同源的坑：**系统的「定位服务」开关**（不是权限）。Android 6～11 强制要求它打开，
而我们 12+ 又去掉了 `neverForLocation`，所以同样受它影响。关着时扫描同样静默返回空。
它不是权限、申请不来，只能检测出来告诉用户。

## 变更内容

### 1. 权限（按涂鸦给的版本口径重排）

- 清单：`BLUETOOTH_SCAN` **去掉 `neverForLocation`**；`BLUETOOTH` / `BLUETOOTH_ADMIN`
  保持 `maxSdkVersion="30"`（normal 级，装机即授予）；`ACCESS_COARSE/FINE_LOCATION` 保留。
- 运行时申请：
  - **≥ API 31**：`BLUETOOTH_SCAN` + `BLUETOOTH_CONNECT` + **`ACCESS_FINE_LOCATION`**
    （去掉标志之后定位就成了必需）；
  - **API 23–30**：`ACCESS_FINE_LOCATION`（必需），另一并请求 `COARSE`（部分 ROM 还看它）。

### 2. 把每一道门都检测出来并报上去

`bleProbe` 现在回 `locationOn` / `scanPermission` / `locationPermission` 三项，
`BleAvailability.usable` **六项全开才为真**。少判任何一条的后果都一样：扫描静默为空，
而页面上显示「附近没有设备」——**把"我们这边没配好"说成了"设备有问题"，排查方向正好反**。

搜索页据此分出三条独立结论：缺权限 / 定位服务关着 / 蓝牙关着，各自给能照着做的一句话。

### 3. ~~新增「系统原生 BLE 扫描」作对照~~ —— **当日撤回**

产品明确要求：**能用涂鸦 SDK 实现的，就不要自己实现**；搜索只走涂鸦 SDK 的
`startLeScan`，不用系统原生 `BluetoothLeScanner`。下面这一节是撤回前的设计，留作记录；
代码已在同日 `e6e84d6` 之后的提交里整个删掉（原生桥接、模型、仓库、状态、页面、mock、用例）。

取而代之：**涂鸦 SDK 扫到的设备按信号强弱列前 50 台**（`FlowerpotState.bleListLimit`），
状态行同时报「一共几台、列了几台」，每行小字带 rssi / 是否已绑定 / `supportWifiList` /
pid / **mac / uuid**（广播里常常没有名字，只能靠这两样和设备方对）。不过滤 + 扫描类型全开
之后，附近的涂鸦设备可能不止一台，按信号排序想找的那台几乎必然在最前面。

#### 撤回前的设计（仅记录）

涂鸦的 `startLeScan` 只回报**它认得的涂鸦协议广播**。扫不到时有两种完全不同的可能，
而页面上看起来一模一样：

1. 设备**根本没在广播**（没上电／已退出配网状态／固件不支持 BLE）；
2. 设备**在广播，但不是涂鸦要的格式** ⇒ 这是固件的事，得设备方去改。

所以加了一条 `BluetoothLeScanner` 的**无过滤**扫描（`startRawBleScan`），与涂鸦那条同时
开，只做对照、不参与配网。每条广播带上 mac / 名字 / rssi / **厂商 id / service uuid**。

页面上两个数目并排显示，并在「扫了一段时间还没有」时直接给结论：

- 原生 > 0 而涂鸦 = 0 ⇒「附近有蓝牙广播，但没有涂鸦设备」——手机这边的扫描是通的，
  问题在广播内容，把页面截图给设备方；
- 两边都是 0 ⇒「连系统原生扫描也一条都没收到」——设备多半没在广播。

这正是这一轮要交付的东西：**给设备方一个能照着改的结论**，而不是「搜不到」。

## 关键决策

- **宁可多要一个定位权限，也不要静默过滤。** `neverForLocation` 省下的那一个授权框，
  代价是一个查不出来的空结果——这一轮吃的就是这个亏。
- **原生扫描只做对照，不做配网路径。** 产品口径是「优先使用集成的 SDK」，配网仍然全部
  走涂鸦的 `IMultiModeActivator`。
- **老桥接缺字段时按"没问题"处理**：三个新字段 `fromMap` 缺省 `true`，免得桥接没升级的
  机器上凭空报一个「定位没开」把人带偏。

## 验证结果

- **本机没有 Flutter / Dart / Android / Kotlin 工具链**，analyze / test / 编译 / 真机
  **全部未执行**。
- 静态自检全绿：`tools/dart_string_check.py`（274 个文件）、`tools/kt_dangling_refs.py`、
  括号配平持平。
- 新增 `test/ble_availability_gates_test.dart`：六道门逐条验、老桥接缺字段的兼容口径、
  桥接明确回 false 时要认出来。

## 未完成项与风险

- **`neverForLocation` 是不是真凶，要真机才能确认。** 判据很明确：装上这一版后，
  ① 授权框里应当多出「定位」；② 页面状态行会逐项显示每道门；③ 原生扫描那一行的数目
  就是分水岭。
- 去掉 `neverForLocation` 之后，上架时 Google Play 会要求说明定位权限用途（本应用是
  「用于蓝牙配网扫描附近设备」）。国内商店不受影响。
- 原生扫描**不带过滤**，附近所有 BLE 设备都会被计入那个数目——它只用来回答"有没有广播"，
  不要拿它当设备列表。
