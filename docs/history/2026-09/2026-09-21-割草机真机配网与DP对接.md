## 背景与目标

产品：「现在割草机的设备已经就位，后面也配置了产品 ID，检查下是否支持配网流程，静态数据先不管它」，
随后追加「顺便对接下 DPID，按真实的对接」。

09-18 那两轮只做了静态页和「点一下把 DPID 写进日志」，记录里明写「割草机的 DP 表、后端接口、配网方式本轮一概
没碰，也没有任何预留」。

## 核查：原来哪几处会把真机割草机挡住

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | 搜索页 `_isOurProduct` | 只认花盆的两个 ID（`yciq4kssu1fv8umn` / `ehbx83xdh9jkmxvz`），扫到割草机也**不列** |
| 2 | 设备列表 `_openDevice` | 配上之后割草机出现在 `state.devices` 里，点进去是**花盆详情**（整页读花盆 DP） |
| 3 | `MowerDevice._deliver` | 只写日志 + 本地回显，**一条 DP 都不发**；只读 DP 靠模拟面板 |
| 4 | DP 上报 | 所有设备快照都按花盆解（`SmartPlanterDevice`），割草机 DP 号 101–119 与花盆重叠、含义全不同；DP116（割草机是升级状态）还会被当成植物 id 去后端查 |
| 5 | 「我的」页「设备设置」 | 用 `selectedDevice`，配网成功会把新设备设成选中——配的是割草机就会带进花盆设置页 |

配网本身（BLE 扫描 ScanType 全开、`IMultiModeActivator` 双模配网、原生 `getDevices` 不按产品过滤）对割草机
**没有障碍**，前提是割草机是 Wi-Fi + BLE 双模模组（协议 V2.2 §10 预留了「蓝牙本地控制」，模组带 BLE）。

## 变更内容

1. **搜索页**：`_isOurProduct` 认 ① 花盆两个 ID ② `MowerDp.productId` ③ 后台 `getBasicData.deviceIdList`
   里的全部产品 ID（`startBleDiscovery` 开扫时 `unawaited(loadBasicData())`）。
2. **分流**：`FlowerpotState.isMowerDevice`（设备 `productId == MowerDp.productId`）。设备列表点割草机 →
   `AppRoutes.mowerHome` + `MowerHomeArguments(deviceId)`；`_listenForDeviceUpdates` / `_applyDeviceUpdate`
   对割草机只更新列表那一行（在线、名字），跳过花盆处理，另经新的 `mowerReports` 流分发。新增
   `selectedPlanter`，「我的」页设备设置改用它。
3. **仓库**：`TuyaRepository.rawDps(deviceId)`——设备快照里的原始 DP，按 DP 号取，不经过花盆功能点表。
   `TuyaRaw.hex` 生成 raw 下发值（十六进制串，SDK 自己转 base64，与纪念日 154 同一口径）。
4. **`MowerDevice` 接真机**（`bind(state, owner:, deviceId:)` / `release`，外壳 `MowerHomePage` 管）：
   - 真机时 `_deliver` / `_deliverRaw` 经 `FlowerpotState.publishMowerDps`（同花盆的 `_publishDps` 离线门禁，
     不占 `_guard` 忙锁）发给设备；内部 `_queue` 串行，时间同步 106 → 107 → 108 → 114 的顺序不乱；
   - 上报：绑定时从快照整份解一遍，之后按 `mowerReports` 只解本条报文带的 DP；整包快照（没有逐条 DP）
     全刷但跳过还在等回显的；bool / value / enum（字符串或序号）/ raw（hex，兼容 base64）都认，认不出不动原值；
   - **超时回弹**：下发后 5 秒（`echoTimeout`）这条 DP 没上报，按设备快照画回去（协议 V2.2 §1「设备校验不通过时
     不回显，App 控件约 3~5 秒后超时回弹」）；同一条 DP 再发一次，旧的那次不再回弹；
   - 下发失败：画回设备值，并经 `failures` 流由外壳弹提示（离线：「割草机已离线，指令没有发出去」）；
   - 真机「没报过」的初值不编数：计划空周、五区 0%、电量 0、时区按手机；
   - 静态演示（不带 deviceId）行为不变：只写日志、本地回显、模拟 DP5；模拟面板真机时不开。
5. **编解码**：`MowerZoneCodec.decode`、`MowerTimezone.indexOfCode`（`UTCA`/`UTCB`，也认序号）、`MowerDp.enumOf`。
6. **用例**：新增 `test/features/mower/mower_live_test.dart`（10 条：快照解码、空计划、真机下发与顺序与 hex、
   演示不下发、5 秒回弹、回显不回弹、离线失败提示与回弹、割草机上报不走花盆、`selectedPlanter`、搜索页认割草机）；
   `mower_dp_codec_test.dart` 加 4 条解码；`device_list_page_test.dart` 加 1 条（点割草机进割草机页面并带设备 ID）；
   `MockTuyaRepository` 加 `rawDps` / `rawDpsByDevice` / `publishedDps` / `publishError`。

## 关键决策

- **按设备 `productId` 认割草机，用常量 `MowerDp.productId`**：后台 `deviceIdList` 只是一串 ID，分不出哪个是
  哪款；产品 ID 本来就是 09-18 起就有的常量。搜索页那一步额外认 `deviceIdList`，是为了后台再加产品时能扫出来。
- **单例 + 绑定**，没有改成按 deviceId 分实例：同一时间只开一套割草机页面，十来个页面都读 `instance`，
  改成多实例要动每一页；绑定 / 解绑由外壳一处负责。
- **失败提示放在外壳**：页面调用的 setter 都是同步的，改成逐个 await 要动所有调用点；外壳在二级页压上来时仍活着，
  一个订阅就覆盖全部页面。
- **静态数据不动**（产品原话）：名称 / 型号 / SN、静态入口两条、没有 DPID 的功能提示都原样。

## 未完成项与风险（真机第一轮要看的）

1. **搜索页扫不扫得到**：割草机 BLE 广播里的 pid 若既不是 `mz7g3yzaufvoh4ls`、也不在后台 `deviceIdList` 里
   （花盆就是这样：广播 `ehbx…`、平台 `yciq…`），列表里不会出现——把 `PairingGate.showUnfilteredBleScan`
   翻成 true 看它报的 pid，补进后台或常量。
2. **设备列表认不认得出**：同理，配上后 `DeviceBean.getProductId()` 若不是 `mz7g3yzaufvoh4ls`，会被当成花盆。
   消息调试板（割草机「消息通知」页）会列出账号下每台设备的 pid。
3. **模组是不是双模**：配网走的是 `IMultiModeActivator`（Wi-Fi + BLE）；若割草机是纯 Wi-Fi（只能 AP / EZ）或纯
   BLE，这条路配不上，需要另接。
4. **DP3 枚举序**（09-18 记录里的遗留）：xlsx 说明列与枚举列表不一致，本文件按枚举列表 smart=1；模式整体错开一位
   就是这里。
5. 设备对「值没变的下发」回不回报：不回的话 5 秒回弹会画回同一个值，看不出差别，但日志里会多一行「回弹」。
6. iOS：BLE 扫描与双模配网在 iOS 桥接上都没接，iOS 上配不了割草机（花盆同样）。
