## 一、最终跑通的那条路（照这个复现）

### 发现

`ThingHomeSdk.getBleOperator().startLeScan(LeScanSetting, ThingBleScanResponse)`
→ `onResult(ScanDeviceBean)`。`LeScanSetting` 里 ScanType **能加的全加上**
（SINGLE / SINGLE_QR / NORMAL / THING_BEACON / MESH / SIG_MESH），`setRepeatFilter(false)`。

### 配网（**这一步是最后跑通的关键**）

用 **`IMultiModeParallelActivator`**，不是 `IMultiModeActivator`：

```
ThingHomeSdk.getActivator().newMultiModeParallelActivator()
  → config(MultiModeActivatorConfig{ssid, pwd, token, gid=homeId, timeout})
  → appendDevice(ScanDeviceBean)            ← 把扫到的 bean 整个交回去
  → addMultiModeParallelListener(listener)
  → startConfigWifi()
```

listener：`onStartConfig(String)` / `onSuccess(DeviceBean)` / `onError(String, String, String)`。

⚠️ **为什么必须是这一套**：另一条 `IMultiModeActivator.startActivator(MultiModeActivatorBean, …)`
要**手工拼出整个 bean**（二十多个字段），拼漏一项就在 SDK 内部 NPE，而混淆过的栈帧
（`pqppqpd.bdpdqbp:21`）看不出漏了哪一项。并行这条把 `ScanDeviceBean` 整个交回去、
字段由 SDK 自己取，**没有"拼"这一步，也就没有拼漏的可能**。

## 二、路上踩过、都要保留的坑

| 坑 | 症状 | 处置 |
| --- | --- | --- |
| `BLUETOOTH_SCAN` 带 `neverForLocation` | Android 12+ 系统**过滤掉**广播，静默扫不到 | 清单里去掉该标志，12+ 同时申请定位 |
| 探测抢在授权框被回答之前 | 首次进页面报「缺定位权限」，**退出重进就好** | 先 `ensureBlePermissions()` await 掉，再 `probeBle()` |
| 系统「定位服务」总开关关着 | BLE 扫描**静默返回空**，与「没有设备」分不开 | 单独检测并单独提示（申请不来，只能让用户去开） |
| 仓库层把 uuid 为空的**静默丢掉** | 页面显示「一台都没扫到」，其实是我们扔了 | 一条不丢；去重键 uuid → mac → address → id |
| 配网失败后**没断开 BLE 链路** | **之前搜得到、之后再也搜不到**（BLE 外设连接中不广播） | 每条退出路径 `disconnectBleDevice`，`stopActivator` ≠ 断开 |
| `mac` 为空、地址在 `address` 上 | 真机实测 `mac=''`、`address='D8:FC:92:F4:89:88'` | 两边互相补齐 |
| 混淆栈帧只报类名 | 只看到 `NullPointerException`，推不出任何东西 | `describe()` 带上第一帧 `com.thingclips`/`com.common` 的栈；`startActivator` 单独 `runCatching` 隔离，分清是 SDK 内部还是我们传参 |

## 三、真机实测到的设备特征（这一款）

```
ScanDeviceBean{id='uuid23119e1d4a2b66fc', name='', providerName='SingleBleProvider',
data='null', configType='config_type_wifi', productId='ehbx83xdh9jkmxvz',
uuid='uuid23119e1d4a2b66fc', mac='', address='D8:FC:92:F4:89:88',
deviceType='404', isbind=false, flag=776, rssi='-38'}
```

- `uuid` **带字面前缀 `uuid`**，不是拼错，SDK 原样如此，别去"清理"它；
- `mac` 空、`address` 才有值；
- `deviceType=404` / `configType=config_type_wifi` / `providerName=SingleBleProvider`；
- `flag=776`（bit 3/8/9），`CombosFlagCapability.SCAN_WIFI` 未置 ⇒ `supportWifiList=false`，
  **这一款固件不支持回报 Wi-Fi 列表，输密码只能手输——是正常的，不是故障**；
- `productId` 报的是**广播 ID**（`ehbx83xdh9jkmxvz`），不是平台产品 ID
  （`yciq4kssu1fv8umn`）。两者是两个字段，见 `TuyaConfig.broadcastId`。

## 四、跑通之后的收口（同日）

- `PairingGate.showUnfilteredBleScan` 置 **false**：列表回到**只列本产品且未绑定的**；
- **认设备以后台 `/Client/Product/getProductList` 的 `broadcastId` 为准**（产品口径
  「根据后台的接口配对一下」），本地 `TuyaConfig` 那两个常量兜底。这样后台新增产品，
  App 不用改代码、不用发版就能认出来；
- 页面回到 UI 图：行上只留「信号 −xx dBm」，设备标识 / 能力位 / SDK 原样输出、常驻状态行、
  原生日志框**全部收进排查态**——把开关翻回 `true`，那一整套立刻回来。

⚠️ **AP 仍然屏蔽中**（`PairingGate.apEnabled = false`）。蓝牙这条已跑通，是否恢复 AP
作为回落由产品决定；代码原样保留，翻开即可。
