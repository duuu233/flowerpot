| 比对项 | 值 | 09-12 之后还顶用吗 |
| --- | --- | --- |
| `TuyaConfig.productId` | `yciq4kssu1fv8umn` | 顶用不上——设备广播里不是这个 |
| `TuyaConfig.broadcastId` | `ehbx83xdh9jkmxvz` | **就靠它认出这款花盆** |
| 后台清单的 `broadcastId` | 现在是 `yciq4kssu1fv8umn` | 和广播值对不上，基本不顶用了 |

所以**这款花盆的搜索不受影响**（本地常量兜着）；受影响的是「后台新增产品、App 不发版就能
认出来」那条路——后台那个字段现在存的是平台产品 ID，而设备广播里带的仍然是广播标识。要恢复

代码没改逻辑，只把 `TuyaConfig.broadcastId` 和 `_isOurProduct` 的注释改成了现在的事实，并标

## 5. 需水状态页为什么没有历史记录

## 6. DP 162 要能重复弹

触发依据前后换过三次，两个坑都记在 `home_page.dart` 的注释里：

1. 最早「只要 pending 就弹」——162 在用户处置前一直是 true，页面每重建一次就重弹一次，
   点任何下发按钮都会冒弹窗。

   一直是 true，于是再也不会弹第二次。
3. 现在按**上报次数**触发：

- `DeviceUpdate` 新增 `changedDps` —— **这一条报文里真正带了哪几个 DP**。设备快照是历史 DP
  合并后的样子，光看 `device.plantConfirm` 分不出「162 这次报了 true」和「162 上次报过、这次
  报的是温度」。
- `FlowerpotState._notePlantGuideReport` 只在报文带了 162 且值为 true 时把
  `plantGuideSignal(deviceId)` +1，并在日志框记一条「第 N 次」。

- ⚠️ 计数必须在 `_applyDeviceUpdate` **之后**再加：计数一变页面就重建并去读
  `plantGuidePending`，先记数的话页面会拿着上一版状态判定「不用弹」，把这次上报白白消耗掉。

新增两条测试：`设备再报一次 162=true 就再弹一次`、`162 还是 true 但这条上报没带 162，不重复

## 追加：162 的到货路径补全 + 确认时打出植物 ID + 植物列表 loading

### 1. 162 再放宽一条到货路径

上一版只认「报文里带了 162」（`DeviceUpdate.changedDps` 含 162），那是 `onDpUpdate` 那条路。
但原生侧还有一条：`onDevInfoUpdate` 会把**整包设备快照**发上来，事件里没有逐条 DP，
`changedDps` 是空的——走这条路时计数不会加，弹窗也就不会来。

现在两条都认：

| 到货路径 | 判据 |
| --- | --- |
| `onDpUpdate`（报文带 DP） | `changedDps` 含 162 |
| `onDevInfoUpdate`（整包快照） | 162 **由别的值翻成** prompt（记 `_lastPlantConfirm` 前后对比） |

反过来，**整包快照里 162 本来就是 true** 不算——那不是一次新的上报（例如设备列表刚拉回来），
进页面那次检查已经负责弹了。日志里会写明这次是哪条路径触发的：
`上报 ← DP162 植物确认=true（第 2 次，整包快照翻转）`。

⚠️ **有个上限说清楚**：涂鸦只推 DP **变化**。如果固件在 162 已经是 true 的情况下再写一次
true，云端很可能不产生新的 `onDpUpdate`，App 就无从得知。要做到「每次都弹」，固件那边
得真的翻转一次（0 → 1）。App 侧能做的已经做满。

### 2. 点「确认」时日志直接写出下发的植物 ID

`_publishDps` 本来就会打 `下发 → {116: xxx, 161: y}`，但那一行读起来不直白。
`confirmDetectedPlant` 里加了一条：`确认植物 → DP116=<标识符>，<植物名>`；目录里没有这一株
时写成 `（目录里没有这一株，只下发 116）`。

### 3. 添加植物的列表加 loading

`PlantPickerPage` 在等 `getProductPlantList` 的那几秒里画的是「没有搜到植物」的空态——
看着像后台一株都没配，其实只是还没回来。加了 `loadingPlants`：

- 进页面即为 true（首帧之前赋值，不用 setState）；
- `_loadPlants` 的 **`finally`** 里收掉——成功、`ApiException`、后端没开都要收，否则会一直转圈；
- 加载中画 `_PlantCatalogLoading`（固定 316 高，约等于两行卡片，避免 loading 消失时页面猛跳），
  底部「确认添加 / 确认选择」按钮同时禁用。

## 追加：两个按钮都显式把 162 写回 false

产品：「涂鸦那边会有延迟，现在每次点击『选择植物』和『确认』的时候，都多传一个 dpid=162
的改为 false，帮它这个值初始化一下。也就是你说的要真的翻转一下。」

这正是上一条留下的那个上限的解法：**涂鸦只推 DP 变化**，162 一直停在 true 的话，固件再写
一次 true 不产生新上报，App 无从知道设备又要求弹窗了。由 App 主动写回 false，下一次 true
就是一次真正的翻转。

先核了一遍功能点表——`docs/智能花盆test(yciq4kssu1fv8umn)_09_12.xlsx` 里
**162 弹窗提醒 `plant_present` 是「可下发可上报（rw）」**，App 写它是合法的。
（这推翻了代码里 09-09 留的那句「只由设备上报、App 不再写这条」。）

- 「确认」：`_publishPlantSelection` 的那一帧里带上 `162: false`，和 116 / 161 一起发。
  顺手修了返回值——原来用 `dps.length > 1` 判断「带上了 161」，现在 162 每次都发，那个
  判断会恒真，改成直接看 161 到底进没进 map。
- 「选择植物」：跳转前先单独发一次 `162: false`（`resetPlantGuideFlag`），外面套同一层
  loading 挡住重复点击。失败不拦路——用户照样能去选植物。
- 写完把**本地**设备状态落成 hidden，弹窗不会因为读到旧快照再冒一次。

### ⚠️ 一个容易写错的地方：本地重置不能污染「上一次设备报的值」

`_lastPlantConfirm` 记的是「上一次**从设备收到**的 162」，专门用来认出整包快照里的翻转。
如果把 App 自己写下去的 false 也记进去，就会出现这种误判：写完 false、固件还没回 162=0
之前，随便来一条电量上报（整包快照里 162 仍是 true）都会被算成「设备又要求弹一次」——
直接退回「点任何按钮都冒弹窗」的老毛病。所以 `_notePlantGuideReset` 只改本地设备状态，
不碰这个 map。

三条相关测试跟着改：「确认」那条从断言「不写 162」改成断言 `162 == false`；
「选择植物」和「通用植物」两条从断言「什么都没发」改成断言只发了 `{162: false}`。
