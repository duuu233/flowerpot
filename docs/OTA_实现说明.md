# 固件升级状态监控（花盆 / 割草机）

## 分段耗时诊断 2026年10月20日

App 继续使用涂鸦SDK传输、安装和进度监听，没有自行切分固件或强制差分开关。新增 `OtaTimingTrace` 只帮助下一次真机定位约2分钟耗时，不能据此宣称实际提速已完成。对外一页说明见 [优化进展及OTA联调说明](reports/2026-10-20-ota-optimization-brief.pdf)。

### 如何取证

1. 使用调试构建（`APP_DEBUG_TOOLS=true`，省略时默认开启）；`APP_DEBUG_TOOLS=false` 用户包不创建计时记录、不输出这些日志。保持设备通电及正常网络，开始前记录App版本、固件源/目标版本、组件、平台实际下发包类型和大小。
2. Android 联调时从 `adb logcat -s flutter` 筛选 `[ota-timing]`。每次App发起或接回任务生成递增 `attempt`；并行设备按此编号分组，不含设备ID、URL、账号或Token。
3. 对比本App与智能生活时，必须保持同设备、同源/目标版本、组件与网络；重复测试应由设备方提供可复现相同升级路径的测试条件，不能拿已升级设备的“检查更新”时间对比。

| event | App侧含义 |
| --- | --- |
| start | 本次调用原生升级接口前；接回已有任务时只是App观察起点，不是设备实际升级起点 |
| start_reply_timeout | 30秒内启动方法未返回，仅记录，不据此判失败或再次启动 |
| first_progress | 第一次收到1–100的有效正百分比，重复进度不重记 |
| stage_preparing / stage_upgrading / stage_waitingWake / stage_installing | 第一次收到对应的SDK阶段枚举；没有原生阶段时不推测 |
| installing | 合并后的App状态首次进入安装（阶段6或产品98%判据），附真实百分比 |
| signal_failed / signal_success | 状态层第一次收到该类终态输入，可能来自SDK、启动异常或设备DP，不单凭此行认定固件结果 |
| version_verification | 安装阶段模糊失败转为版本核验的起点 |
| fresh_version_report | 本次首次收到合法的新鲜版本报告，不保证等于目标版本 |
| target_version_match | 本次新鲜版本与目标匹配且进入安装判据，能够完成兜底；如版本先到，此节点在安装阶段复核时记录 |
| result_success / result_failed | App最终确认结果；确认后释放本次计时，不接受晚到状态改变终态 |
| local_clear | 用户重查等导致本地任务清除；不会取消设备升级 |

每行提供 `elapsedMs`（相对App观察起点）及 `sincePreviousMs`（相对上一条首次里程碑）。同一里程碑仅首次记录，重复状态不移动基线。时间来自App接收事件时刻；系统校时和SDK上报延迟可能影响读数，不能当作设备内部下载、校验、写入、重启的精确时长。设备方仍需提供内部时间线。设备移除、清除或退出会话时一并释放；没有新增后台定时器、重试或额外SDK查询。

### 联合验收

至少各3次可比较升级，记录中位耗时与异常次数。先确认最终版本和界面结果一致，再按首次进度、进入安装、设备内部节点和App确认结果划分耗时；实际差分状态以平台下发包及设备运行证据为准。`diff_ota`、`tuya_iot_dev_upgd_progress_rept` 按设备所用SDK核实，不能从App未调用推定未开启。现阶段不承诺两分钟可缩至某个秒数。

## 1. 新版本监控（拉取）

**调用**：Android 优先 `newOTAServiceInstance(devId).getFirmwareUpgradeInfo()`，旧 SDK 保留 `newOTAInstance/getOtaInfo`；iOS `getFirmwareUpgradeInfo`（`state.checkFirmware` → `tuya_repository.dart` → 原生层）。

**判定**：SDK 按组件返回记录，优先取 `upgradeStatus == 1` 的待装版本，否则识别 2 / 5（已有升级 / 等待唤醒）。同一条记录保留目标版本、当前版本、组件类型和升级方式。新版本为空或等于当前版本时没有可展示更新。已有任务标记 `inProgress`，不亮新版本红点、不弹新升级提醒；手动检查可重新挂接监听与查询，不重复下发启动命令。

**触发时机**（没有定时器，全是事件触发）：

| 触发 | 花盆 | 割草机 |
| --- | --- | --- |
| 停在设备页上：路由变化或状态刷新时检查，**同一台设备 1 分钟内只问一次**（`FirmwareReminderHost`） | ✓ | ✓ |
| 进入设置页、「其他设置」页，各静默查一次 | ✓ | — |
| 点升级入口（`runFirmwareUpgrade`）时，之前没查到新版本就当场再问 | ✓ | ✓ |
| 网络异常弹窗点「重试」 | ✓ | — |

**在线门禁（2026-10-14）**：离线不查询、不显示缓存红点、不弹普通/强制提醒；已有自动提醒离线关闭。手动确认和异步检查返回后重新核对SDK在线值，状态层启动OTA前再拦截；已开始升级仍保留原回调/终态维护。

**结果去向**：小红点，以及按升级方式弹的提醒框（提醒升级 / 强制升级 / 检测升级只亮红点）。正在升级且没卡住时，不再弹提醒框。割草机的普通/强制提醒还需最新 DP117 明确为 `charging`（1）或 `full`（2，已充满）；0/未上报/无法解析不弹，但仍保留新版本红点，后续充电或已充满上报会重新评估。花盆不使用割草机的充电判据。

## 2. 升级中状态监控（推送）

### 2.1 链路

逐层调用的方法见 [附录 A](#附录-a发起升级与进度实现步骤)。

```
发起升级（原生层只回答「已发起」）
  → SDK 的 OTA 监听回调（Android 另每 8 秒查询 SDK 当前进度）
  → 原生层发事件 {deviceId, ota:{status, percent, stage, message}}（事件通道）
  → tuya_repository.otaUpdates
  → state._applyOtaProgress（合并、记录时间）
  → 进度弹层 / 功能行 / 小红点
```

发起时 App 先把状态置为 `running 0%`，并记下目标版本号。OTA 实例一直留着引用（Android 放在 `otaInstances`，iOS 放在 `upgrading`），升级结束才释放；否则监听会被回收，进度条会停住不动。退出登录时统一释放。Android 同时维护本次任务标识和组件类型，拒收旧任务、其他设备或组件的结果；结束时取消查询。

### 2.2 回调 → 状态

| Android（旧 `IOtaListener` 兼容路径，7.5.1） | iOS（设备 delegate） | 转成 |
| --- | --- | --- |
| `onProgress(type, percent)` | `firmwareUpgradeProgress` | `running` + 百分比 |
| `onStatusChanged(code, type)` | 无 | `running` + 阶段码（只转下表中的码） |
| `onSuccess` | `deviceFirmwareUpgradeSuccess` | `success` |
| `onFailure` / `onError` | `deviceFirmwareUpgradeFailure` | `failed` + 失败原因 |
| `onTimeout(type)` / `onFailureWithText(type, code, bean)` | 不适用 | `failed` + 超时提示 / bean 的正文（无正文取标题，再用默认提示）；随后释放实例 |

Android 现优先使用 `registerDevOTAListener` 的 `firmwareUpgradeStatus`，回调与 `getUpgradeProgress` 快照均经 `TuyaOtaServiceBridge` 解码：3 成功、4 失败、7 超时；1 / 2 / 5 / 6 / 13 / 14 / 100 为进行中阶段。旧 `onStatusChanged` 也补齐 3 / 4 / 7，不能只等独立成败回调。百分比 -1 或超出 0–100 表示无可用值，沿用旧值。弱信号 5005 显示原因，不自动代替用户确认。

阶段码（涂鸦 SDK 7.5.1 `DevUpgradeStatusEnum`）：

| 码 | 含义 | 界面 |
| --- | --- | --- |
| 1 / 13 / 14 / 100 | 就绪、排队、云端或本地准备 | 固件准备中 |
| 2 | 升级中 | 固件升级中；有有效进度才显示 N%，否则不定进度动画 |
| 5 | 等待设备唤醒 | 等待设备唤醒 |
| 6 | 固件已下载到设备 | 固件安装中 |

### 2.3 合并规则（`_applyOtaProgress`）

- 本次升级的第一个已确认终态（成功或明确失败）生效。安装阶段SDK失败/超时先转 `running + verifyingVersion` 核验版本，不提前形成不可纠正的失败；准备/下载阶段错误仍失败。已确认结论之后，迟到进度或相反结果丢弃。
- 百分比和阶段码往往分开到达，缺哪个就沿用上一次的值，不会把进度条打回 0。
- 百分比和阶段不倒退；只有状态、阶段或有效百分比实际改变才刷新「最后推进时间」。重复快照不延长停滞阈值。
- **成功**：熄灭小红点，版本号显示为目标版本。**明确失败**：清掉目标与核验状态，弹层显示失败原因。**安装待核验**：保留目标、本次版本、真实进度与安装阶段；SDK原始错误仅作诊断，页面显示「正在确认升级结果」。

### 2.4 界面怎么读

- `FlowerpotState.canStartFirmwareUpgrade` 共用充电判据：根据产品 ID，仅割草机从目标设备最新 `mowerDps` 快照解析 DP117，充电中 `charging`（1）或已充满 `full`（2）均放行，整数、数字字符串及枚举名使用同一解析。自动提醒弹出前检查，读取期间路由/弹层/会话变化时不弹旧提醒。
- 手动检查可在任何充电状态查看版本；确认框完全退场后再次读取充电状态，未满足时提示「请回桩进行ota升级」，不启动、不显示进度，入口 loading 由 finally 清理；`confirmed: true` 同样检查。运行中的升级先重开进度，不按新发起条件拦截。

- 提醒/确认框与进度框顺序显示。普通提醒通过 `showAppDialog(waitForDismissal: true)` 等待退场完成，强制提醒与 `showFirmwareUpdateDialog` 等待其 `ModalRoute.completed`；结果返回不代表 overlay 和遮罩已经移除。
- 花盆保持进入「其他设置」再确认版本的流程；割草机切到设置栏后等待共用升级流程结束，避免确认框出现前重新提醒。确认按钮重复点击只处理第一次，不额外 pop 下层页面。

- 未收到有效进度且无升级阶段时显示准备中；SDK 明确报告阶段 2 时显示升级中，无百分比就用动画，不伪造 0%。有效 1–97% 显示升级中 N%；≥98% 或阶段码 6 显示安装中。走到 98% 时仍先停留 0.9 秒。
- 正常运行时进度弹层不可关闭；超过停滞阈值后显示「暂未收到升级进度」，允许「关闭窗口」。关闭只退出界面，不取消设备升级、不改成功/失败、不自动重试。「其他设置」功能行和割草机设置红点共用状态。

### 2.5 兜底

- **成功判定兜底（版本号 DP）**：设备上报的版本号等于这次升级的**目标版本**（涂鸦检测升级返回的新版本号，不是设备当前版本号），就按升级完成处理，进度弹层换成「升级完成」。花盆看 DP148，割草机看 DP112。
  - **只在「固件安装中」这一段判断**：仍在升级中，且进度 ≥98% 或涂鸦报了阶段码 6。准备中、下载中（<98%）、已失败、已成功都不判断。
  - 和涂鸦成功回调**并存**：任何一方先满足就跳到成功页，后到的一方不再改变结论。
  - 条件：本次升级发起后真正收到版本号 DP（`changedDps` 与 `reportedDps`），并且 `_pendingOtaVersion` 有值；比较时忽略前面的 `V/v`。不从设备列表或整包历史快照认定成功。
  - 版本先到：只记录到 `_reportedOtaVersion`，准备/下载阶段仍不成功；后续 SDK 进度进入安装阶段时重验。后来的不同版本替换先前记录，空值/非字符串本条版本上报清除记录。
  - 开始、清理/重试、成败收尾、退出登录、解绑或移除设备时清除本次记录，不跨升级使用。
  - 实现：`_confirmOtaFromDeviceReport` → `_confirmOtaByReportedVersion` 记录，`_confirmOtaByPendingReport` 判断；`_applyOtaProgress` 也触发重验。
- **安装阶段错误待核验（2026-10-20）**：SDK错误到达时，前一状态已经是安装阶段且本次目标非空，保留为 `running + verifyingVersion`。DP148/112本次真实上报匹配目标可成功，SDK成功也可成功；错DP、旧快照、空/非字符串或不同版本不判成功。DP116=7/20与明确预检失败不走此例外。启动方法答复前已进入安装而后报超时，也应进入核验进度，不能同时弹入口失败。
- **核验等待**：从首次安装错误算2分钟，重复错误/百分比/阶段不重置；到时仅显示「暂未确认升级结果」，不合成失败或成功。不额外启动计时器/后台网络请求，沿用进度窗口每秒重绘与状态时钟。窗口可关闭且不清目标，之后实际匹配版本仍可确认；手动确认清理重查、新任务、明确终态、退出账号或解绑清核验信息。核验期间不自动重复弹升级提醒。
- **花盆 DP168**：当前协议为手动亮度，已不作为 OTA 结果，不参与成功/失败收尾；旧 `ota_result` 解释已移除。当前成功依据仍为 SDK 与安装阶段 DP148 版本兜底，按产品 ID 与割草机 DP 区分。
- **停滞提示**：准备阶段 `otaPreparationTimeout` 为 2 分钟，升级/唤醒/安装 `otaStallTimeout` 为 10 分钟，均从最后一次真实推进起算。弹层每秒检查，即使 SDK 完全无回调也能提示并允许关闭。阈值不是成功延迟、设备超时或失败结论。再次进入时可确认清理本地进度、重新检查 SDK；若 SDK 返回已有任务，只挂接监听，不重复启动。
- **启动方法长期未答复**：Dart 等待 30 秒后仍保持进行中并进入进度窗口，等待后续事件/停滞提示；不假定成功、失败或重发命令。
- **割草机 DP116 `ota_status`**：本 App 发起的升级仍在进行时，本条实时 DP116 `"7"`（非待机拒绝）或 `"20"`（包校验失败）直接置 `failed`，弹层结束等待并可关闭。不要求割草机页面打开；只取 `reportedDps` 的本条值，无升级、其他状态、旧快照或花盆同号 DP 不收尾。同条同时有错误与目标版本时先认失败。原割草机页面的提示流保留，DP116 不参与百分比。

## 3. 状态存在哪

全部只存在内存里（`state.dart` 的 `_availableFirmware` / `_otaProgress` / `_otaUpdatedAt` / `_otaVerificationStartedAt` / `_pendingOtaVersion` / `_reportedOtaVersion`），不落盘。启动调用前先建立目标、进度与本次记录；即时回调不会被调用返回后的 0% 覆盖。启动抛错也结束本次等待。

## 4. 花盆与割草机的差异

**升级入口的逻辑和交互已统一**（`features/devices/presentation/firmware_upgrade_flow.dart` 的 `runFirmwareUpgrade`，花盆「其他设置 → 固件版本更新」和割草机「设置 → 设备升级」都调它）：

| 情况 | 两边一致的行为 |
| --- | --- |
| 正在升级（没卡住） | 重新打开进度弹层 |
| 停滞（准备 2 分钟、其他阶段 10 分钟无真实推进） | 当前窗口提示并可关闭；再次进入时确认重新检查，已有 SDK 任务仅重新挂接 |
| 设备离线 | 提示「花盆已离线，无法检查固件」或「割草机已离线，无法检查固件」，不跳页 |
| 问云端 / 发起升级期间 | 入口那一行转圈，同时挡住连点（`isCheckingFirmware`） |
| 有新版本 | 弹「检查更新」框（当前版本 → 新版本），确认框完整退场后发起升级、打开进度弹层；割草机此时还需 DP117=charging 或 full，否则提示回桩 |
| 升级提醒弹窗点「立刻更新」 | 提醒框完整退场后跳到设置页（花盆「其他设置」，割草机「设置」栏），再弹「检查更新」框；切换期间不重弹提醒 |

剩下的差异都来自设备本身：

| 项 | 花盆 | 割草机 |
| --- | --- | --- |
| 主动提醒 / 发起充电条件 | 沿用原规则 | 提醒及强制提醒允许 DP117=charging（1）或 full（2，已充满）；手动确认后按最新 DP117 同样判断，未充电或未知提示回桩 |
| 当前版本号 | DP 148 `firmware_version` | DP 112 `fw_version`（如 `"1.1.3"`） |
| 版本 DP 都没报时 | 退回 SDK 的 `verSw` | 同左 |
| 设备侧升级状态上报 | 无独立结果DP；DP148版本安装阶段兜底，168为亮度 | DP116 `ota_status`（本次实时拒绝/失败可收尾） |
| 进设置页静默查新版本 | 设置页、「其他设置」页各查一次 | 只靠提醒弹窗的检查（割草机各页都算设备页） |

## 5. 现状缺口

- **发现新版本慢 1～2 分钟**：云端 OTA 记录本身有滞后，加上 App 自己 1 分钟的节流。
- **设备重新上线、版本号 DP（花盆 148 / 割草机 112）变化，都不会触发重查新版本**。要缩短上面的延迟，App 侧可以从这里补。
- **App 重启后内存进度丢失**：Android 手动检查已识别 SDK 返回的 `upgradeStatus = 2 / 5` 并重新挂接；不保证 SDK 永远返回任务，也未实现启动时无条件自动恢复。iOS 保持原行为。
- **本轮已修复**：Android 超时/文本失败回调、提前版本上报漏验和割草机 DP116 只提示这三项已修复，见 §2 及[修复记录](history/2026-10/2026-10-12-mower-ota-terminal-fixes.md)。实际 4–5 分钟耗时根因仍待真机时间线。

- iOS 不转发阶段码，只有百分比和成败。
- 涂鸦 App SDK 有没有「新版本可用」的推送接口，还没解包核对。
- 固件方清单里的「订阅 DP112」：对**割草机**成立——DP112 `fw_version` 是它上报的当前版本，设备重新连上云端时会报一次，App 目前只拿它显示版本，还没用它触发重查新版本（即上面第二条）。花盆的 112 是空气温度，花盆对应的是 DP148。

## 6. 差分 OTA 与升级耗时排查

### 6.1 手机 App 与设备固件的职责

Android 当前使用 Home SDK 7.5.1，Expansion SDK 7.8.0；优先 `newOTAServiceInstance → getFirmwareUpgradeInfo → registerDevOTAListener → startFirmwareUpgrade`，SDK 回调加每 8 秒 `getUpgradeProgress` 快照兜底，旧接口仅兼容无 Service 的 SDK。查询不下载、不重启升级，待装任务通过 SDK `canUpgrade` 预检后才发起；已有任务只挂接。App 没有自写升级包下载、Flash 擦写或传输分片逻辑，`onProgress(type, progress)` 取最后一个数字作为进度，符合当前 AAR 签名。

`tuya_iot_dev_upgd_progress_rept`、`tuya_iot_upgrade_gw_notify`、`FW_UG_S.diff_ota`、`download_buf_size` 属于设备 TuyaOS/联网模块固件接口，不是 Android Home SDK 的配置。本仓库没有割草机固件源码；在 App 源码中找不到它们，不能证明设备未启用差分或未上报进度。

设备侧 `notify=TRUE` 表示 SDK 自动上报进度，`FALSE` 表示应用层负责上报。“应用层”在这些文档里指设备上的应用程序。不能仅为提速关闭自动上报；切换后必须由设备代码完整、可靠地上报。详见[官方 Wi-Fi SDK 指南](https://developer.tuya.com/en/docs/iot-device-dev/tuya-common-wifi-sdk?id=K9glcmvw4u9ml)。

差分升级要求固件具备能力、平台生成适用于起始和目标版本的差分包，并在部署中启用差分。`fw->diff_ota` 是升级信息中的标识，不能在手机端赋值 TRUE 就把全量包变成差分包。未找到“智能生活对所有设备默认差分，SDK App 默认全量”的通用依据，见[官方差分升级流程](https://developer.tuya.com/en/docs/iot/firmware-upgrade-operation-guide?id=K93ixsft1w3to)。

### 6.2 60 秒与现有等待逻辑

[官方网关联网 SDK 文档](https://developer.tuya.com/en/docs/iot-device-dev/tuya-gateway-link-sdk-development-manual?id=K9ducoah42rl2)的子设备升级章节描述了 App 收到进度会重置 60 秒计时器；[机器人设备 OTA 文档](https://developer.tuya.com/en/docs/iot-device-dev/robot_ota_upgrade?id=Kd93o3vid2fkk)也提到默认超时及平台配置。这些是特定方案的行为说明，不能代替本割草机的模组、SDK 与 PID 配置核实，也不能证明存在自动重试。

本 App 源码没有 OTA 超时后自动重新 `startOta` 的循环。准备 2 分钟/其他阶段 10 分钟的停滞提示阈值与 98% 处 900ms 的显示停留不会强制让升级持续 4–5 分钟。安全完成判定、失败回调漏接与真实下载/烧录耗时必须分开核查。

### 6.3 比较两款 App 的最小实测

测试应对齐同一设备、起始/目标版本、固件组件、平台部署、包类型/大小及网络条件。重复对比需要有受控恢复起始版本的测试方式，不能拿连续两次不同升级任务直接作速度结论。

| 时间点 | 需记录的证据 |
| --- | --- |
| 点击/发起 | App 构建、Home SDK 版本、起始和目标版本；发起次数 |
| SDK 接受启动 | `startOta` 返回、错误回调、组件类型 |
| 首次及后续进度 | 时间戳、`onProgress` 原始参数、`onStatusChanged` 原始参数 |
| 下载/安装 | 设备日志中的包大小/差分标识、下载完成、校验和擦写耗时 |
| 重启/重新连云 | SDK 在线变化、本条 DP112 内容/时间、DP116 错误值 |
| 完成/失败 | SDK 成败/超时回调、Dart OTA 事件与界面终态时间 |

Android 终态回调与 DP 时序处理已补齐，下一步记录真机时间线；若设备约 1 分钟已安装并上报目标版本，而弹层到 4–5 分钟才收尾，排查 App 桥接和 DP112 时序。若设备本身下载较慢，核对平台实际下发全量/差分包、模组传输路径及两款 App 的 SDK；若下载相同而安装慢，由固件团队核对校验/Flash/重启连云。升级 SDK 或增大设备下载缓存都应有兼容性和实测依据。

截至 2026-10-20 仍未取得真机时间线，不能认定现场停滞唯一根因或宣称物理升级已提速。Service API、状态含义和快照接口依据[涂鸦官方固件升级文档](https://developer.tuya.com/en/docs/app-development/otaupdate?id=Ka6ki8la8wnr9)，并以本机实际 7.5.1 AAR 核对签名；本轮修复与验证见[准备阶段修复记录](history/2026-10/2026-10-19-mower-ota-preparing-recovery.md)。最初核查见[检查记录](history/2026-10/2026-10-12-mower-ota-audit.md)，后续 App 代码修复及验证见[修复记录](history/2026-10/2026-10-12-mower-ota-terminal-fixes.md)。

### 6.4 当前App是否开启差分：2026-10-20核查结论

基线 `main/56ed25d`。10月19日 `9770867` 的 Android OTA 三份原生文件至当前没有变化；Home SDK 7.5.1 / Expansion 7.8.0 未改。应用可执行源码未找到 `tuya_iot_dev_upgd_progress_rept`、`FW_UG_S` 或 `diff_ota`，仓库未包含割草机设备固件工程。此结果只证明本App未直接调用/设置，不能推断设备内部SDK是否上报，或升级任务实际使用全量/差分。

| 用户问题 | 当前App事实 | 仍需设备/平台证据 |
| --- | --- | --- |
| 是否调用 `tuya_iot_dev_upgd_progress_rept` 监控进度 | 未直接调用。这是设备向云端**上报**进度的C接口；App用 `registerDevOTAListener` 接收，另每8秒 `getUpgradeProgress` 查询。 | 确认所用设备SDK/OTA方案；自动上报配置，或手动上报调用与真实日志。不能要求所有方案必须手动调用同名函数。 |
| 是否配置 `fw->diff_ota = TRUE` | App没有此结构体/赋值，不能在手机代码开启它。设备升级回调的 `FW_UG_S.diff_ota` 描述升级信息是否为差分。 | 对应模组/MCU/Bootloader是否支持、当前→目标版本差分包与部署开关、设备实际收到的标识与包大小。 |

因此本轮结论是**设备实际差分状态未知**，不是“未开启”或“已经开启”。昨天改的是进度接收、恢复和界面等待；没有替设备接入差分，也没有强制全量下载。`upgradeType` 提醒/强制/检测、`upgradeMode` 通用/PID类型均不应直接当作差分标志。

固件团队最小核验：提供本设备OTA回调里的 `tp`、`sw_ver`、`file_size`、`diff_ota`，以及实际下载字节数/包类型；若对应方案使用 `notify`，说明取值与自动/手动上报路径并给时间线；平台核对起始版本、目标版本、组件、差分包生成与“是否支持差分”。不要把完整下载URL、设备标识或密钥写入共享日志。`notify=TRUE` 由设备SDK上报，FALSE改为设备应用层负责，不可为提速盲目关闭。确认差分能力和有效包之前，不硬改收到的 `fw->diff_ota`。

依据：[App固件升级接口](https://developer.tuya.com/en/docs/app-development/otaupdate?id=Ka6ki8la8wnr9)、[设备Wi-Fi SDK进度上报](https://developer.tuya.com/en/docs/iot-device-dev/tuya-common-wifi-sdk?id=K9glcmvw4u9ml)、[TuyaOS升级信息结构](https://developer.tuya.com/en/docs/iot-device-dev/tuyaos-gateway-ota?id=Kc34sycce62if)、[平台差分升级流程](https://developer.tuya.com/cn/docs/iot/firmware-upgrade-operation-guide?id=K93ixsft1w3to)。后两项按实际设备方案适用性核验，不把网关示例当成本割草机内部实现证明。

### 6.5 2026-10-20 本轮复核

固件查询、启动、包下载/传输和安装由涂鸦SDK与设备执行；App仅桥接SDK、合并真实进度及维护页面，没有自建固件下载器、差分算法或自动重试启动循环。保留旧SDK的官方OTA接口兼容路径，不额外实现另一套传输。Android仍用现有Home7.5.1/Expansion7.8.0，未升级依赖；iOS仍用现有ThingSmartDevice接口。

花盆DP148、割草机DP112均已从本次实时上报与SDK检查返回的目标版本比较，不是当前版本；版本先到会保留证据，安装阶段到达后重验，完成弹层同SDK成功共用。沿用产品§4.14已确认的安装阶段要求（98%或阶段6），本轮没有取消该约束。准备阶段即使先报匹配版本也不能直接完成；DP168为亮度，不再是OTA结果。本轮OTA状态回归覆盖这两种产品、先后时序、错误DP、旧快照和终态保护；没有进行真实设备升级。

差分支持仍按§6.4边界：App使用SDK原生升级链路，不设置`fw->diff_ota`，也不自行下载全量包覆盖SDK选包。设备团队确认SDK具备能力是前提说明，当前实际任务是否使用差分仍需平台包/部署及设备运行证据，不能从App代码断言已启用。

## 附录 A：当前实现调用链

### A1. 入口

`runFirmwareUpgrade` 统一花盆与割草机入口。先检查已有本地进度，正常运行或重启离线时重开进度，不清本次目标；核验超时显示中性重新检查确认，取消仍保留。新查询/启动继续检查在线状态与充电条件，停滞后仅在用户确认时清理并重新查询。SDK 返回已有任务时跳过新升级确认和充电预检，只挂接；新任务仍等待版本确认弹框完整退场，并按最新 DP117=charging 或 full 放行。离线提示及原提醒路由规则保留。

### A2. 状态与仓库层

`FlowerpotState.upgradeFirmware` 先建本次目标和 running 状态，再调用 `TuyaRepository.startFirmwareUpgrade(id, targetVersion:, componentType:)`。本地已有进行中任务拒绝重复下发。方法答复最多等 30 秒，超时只转入等待事件。`FirmwareUpdate` 带同组件版本、`componentType`、`inProgress`；后者不作为新版本提醒。

### A3. Android 发起及监听

`otaInstance` 优先创建 Service，注册监听后重新查固件，按目标版本与组件筛选。仅 `upgradeStatus=1` 且预检允许时调用 `startFirmwareUpgrade(listOf(selected))`；2/5 仅监听。每 8 秒 `getUpgradeProgress` 补漏，查询失败记录原因，不重启任务。未观察到当前任务推进前不接受首个缓存终态快照；本地准备 100 不足以证明它是本次任务。回调/快照过滤设备及组件；每次尝试标识防迟到回调，首个终态生效后释放实例并取消查询。旧 SDK 保留 `setOtaListener/startOta`。

### A4. 事件合并与界面

事件通道仍为 `{deviceId, ota:{status, percent?, stage?, message?}}`，无新通道。Repository 忽略无效百分比，状态层合并阶段和单调百分比，重复快照不刷新推进时间。阶段 2 不再被 0% 错误显示为准备中；无有效数值使用动画。弹层每秒检查停滞；正常运行不可关闭，安装待核验或停滞可关闭但不取消设备任务，核验超时不伪报设备升级失败。

### A5. 完成与边界

iOS 原生 API 和设备固件未改。SDK与设备DP逻辑并存，第一份已确认终态生效；安装阶段SDK报错保留目标等待版本核验，不提前锁定失败。割草机实时 DP116=7/20 判失败，DP112/花盆 DP148 必须是本次真实上报且安装阶段匹配目标才补判成功，不能用旧版本快照、准备计时或方法返回推定成功。花盆 DP168 为手动亮度，不参与 OTA 收尾，见 §2.5。退出登录/销毁释放监听与查询。
