# DP121 `schedule_current` · 新增「计划类型」· App 对接说明（V1.0）

> **面向 App / 平台开发。** 只说：你会收到什么、字段怎么理解、UI 怎么处理、哪些坑必须避开。
> **不涉及设备内部实现。**
> 完整 DP 定义见 `Grass_Master_Automower_DP协议对接_V3.0.md` §3.8。

---

## 1. 一句话变更

DP121 原来只告诉你"这单活从几点干到几点"，现在**多一个 `t` 字段**，告诉你：

> **这单活是「定时计划」触发的，还是用户「手动启动」的。**

| 项 | 内容 |
|---|---|
| 变更 | DP121 的 JSON 新增 `t` 字段（计划类型） |
| 兼容 | **纯新增字段**，老 App 忽略它即可继续工作；新 App 遇到老设备要把"缺字段"当 `0` |
| 设备生效版本 | **MCU_VER ≥ 1.3.5**（当前量产 1.3.4 **不带** `t`） |
| 你需要改的 | ① 解析多读一个 `t` ② 判断"计划变化"时把 `t` 加进去 ③ 按 `t` 切换文案 |

---

## 2. 平台配置（必须确认）

| 项 | 值 |
|---|---|
| DP 号 | **121** |
| 标识符 | `schedule_current` |
| 数据类型 | **string（字符型）** |
| 传输方向 | **只上报（ro）** —— 设备 → App，**App 不要下发**（下发会被拒 `68`）|
| 订阅 | App 必须**订阅**这个 DP，否则收不到 |
| **数据长度上限** | **必须 ≥ 64 字节**（老载荷 50 字节，新载荷 56 字节；若平台配的是 50，会被截断成非法 JSON）|
| 面板显示 | 建议设为**不在 App 面板显示**（否则设备页会显示一串裸 JSON）|

---

## 3. 数据格式

载荷是**一段放在 string 里的 JSON 文本**（不是 JSON 类型，需要你自己解析字符串）。

```json
{"st":1761451200,"et":1761465600,"now":1761454500,"t":1}
```

| 字段 | 类型 | 含义 | 无计划时 |
|---|---|---|---|
| `st` | u32 | 计划开始时间（**UTC 秒**）| `0` |
| `et` | u32 | 计划结束时间（**UTC 秒**）| `0` |
| `now` | u32 | **本帧构建瞬间的设备 UTC 秒**（即使无计划也照发，供你校准时钟偏差）| 正常发 |
| `t` | u8 | **计划类型**：`0` / `1` / `2`，见下表 | `0` |

### 三种典型载荷

```json
// A. 定时计划正在执行
{"st":1761451200,"et":1761465600,"now":1761454500,"t":1}

// B. 用户手动启动（按"工作时间"开的 2 小时窗）
{"st":1761451200,"et":1761458400,"now":1761454500,"t":2}

// C. 无计划（空闲 / 已完成 / 已终止 / 未到时段）
{"st":0,"et":0,"now":1761454500,"t":0}
```

---

## 4. `t` 取值含义

| `t` | 含义 | 什么时候会收到 | UI 建议 |
|---|---|---|---|
| `0` | **无计划 / 未知** | 空闲、计划已完成、计划被取消、当前时刻不在计划时段内、**或设备版本太老没有这个字段** | 不显示计划行，剩余归 0 |
| `1` | **定时计划** | 用户在 App/面板配置的割草计划到点，设备自动开始干活 | 显示"计划任务" + 计划时段 |
| `2` | **手动计划** | ① 面板按键启动 ② App 远程启动（DP3=smart）③ 定点割草（DP3=spot） | 显示"手动任务"，剩余 = `et − now` |

### 两个可以直接依赖的契约

1. **只要剩余 > 0，`t` 一定是 `1` 或 `2`，绝不会是 `0`。**
   （无计划时设备会把 `st/et/t` 一起归零 ⇒ 剩余必然为 0）
   ⇒ 你可以放心用"剩余==0 提前 return"来跳过类型判断。

2. **`t` 不会每帧抖动。**
   它只在"这一单活换成了另一种性质"时才变。所以「`t` 变了」可以当**一次性事件**用（刷新标题、写一条操作日志、埋点），不会刷屏。

## 5. 推荐处理流程

```
收到 DP121 帧
  ↓
解析 st / et / now / t          // t 缺失(老固件) ⇒ 按 0，不要报解析失败
  ↓
剩余 = max(0, et - now)          // 无计划时 et=0 ⇒ 剩余 0
  ↓
判断"计划是否变化"：对比 (st, et, t) 三元组   // ← 关键，见 §6
  ↓
if (剩余 == 0) {
    显示"今日计划";              // 无计划/已完成/未到时段/老固件，全部走这里
    return;
}
switch (t) {
    case 2: 显示"手动计划"; break;
    case 1: 显示"今日计划"; break;
    default: 显示"今日计划"; break;   // t=0 理论上到不了这里，兜底用
}
   ↓
之后本地每秒递减剩余；收到新帧才重置基准
```

**两句话总结**

- **倒计时优先**：剩余为 0 就显示今日计划，不问类型。
- **只有"手动"需要靠 `t` 识别**，其余一律显示今日计划 —— 所以对你们来说 `t` 等价于一个 bool。

> 协议仍保留 `t=0` 这个取值（设备确实会发），目的是让**机器日志、云端历史、以后做"手动 vs 自动作业时长统计"**能拿到真实值。App 分支可以不用它。

---

## 6. ⚠️ 判断"计划是否变化"必须用 `(st, et, t)` 三元组

这是本次最容易踩的坑。

### 为什么不能用 `(st, et)`

**手动启动和定时计划完全可能撞出相同的时间段。**

> 例：定时计划 08:30–10:30 正在跑；
> 用户**正好 08:30** 也在面板按了启动，工作时长设 2 小时 ⇒ 设备发出的**新帧 `st/et` 和上一帧一模一样，只有 `t` 从 1 变成 2**。

如果你按 `(st, et)` 判断"计划没变、不刷新"：

- 界面会**一直显示"今日计划"**，而不是"手动计划"；
- 而且**永远纠正不过来** —— 设备 60 秒的兜底重报发的还是同一帧 `(st, et)`，你的去重逻辑同样会认为"没变化"。

### 正确做法

| 对比项 | 是否算"计划变化" |
|---|---|
| `now` 变了 | ❌ 不算（每帧都在变）|
| `st` 或 `et` 变了 | ✅ 算 |
| **`t` 变了** | ✅ **算**（本次新增要求）|
| 四个字段全同 | ❌ 不算 |

## 7. 什么时候会收到（便于你安排刷新与超时）

设备**不会**按倒计时周期发帧（否则一天 8 万多帧）。它只在下面 4 种情况发：

| # | 时机 | 说明 |
|---|---|---|
| 1 | **App 打开 / 设备连云 / 你主动查询（0x08）** | 会拿到当前完整快照 |
| 2 | **计划变化** | 新建 / 换计划 / 手动启动 / 终止 / 完成 |
| 3 | **设备时钟被跳变** | 校时 / 改时区 / 夏令时 |
| 4 | **兜底重报** | 有计划时 **60 秒**一帧；无计划时 **300 秒**一帧 |

### 因此你必须做

- **本地倒计时**：只用 `et − now` 算一次基准，之后本地每秒递减，收到新帧才重置。
  （绝对不能只显示静态数字，会越走越不准）
- **不要指望"每秒一帧"**：两帧之间最长可能间隔 60 秒（有计划）或 300 秒（无计划）。
- **断网/丢帧期间倒计时照常走**：载荷是**绝对时间戳**，不是相对秒数，所以本地递减是安全的。

### 两个"数据会冻结"的窗口

| 窗口 | 现象 |
|---|---|
| **设备升级固件期间** | 所有 DP 静默，DP121 也停发；升级结束/重启后自动恢复上报 |
| **设备开机自检期间** | 同上，自检完成前不发帧 |

⇒ UI 在这些窗口里应保留上一次有效值（不要清空），并可由 DP116 判断"是否在升级"来切换提示。

## 8. 兼容性

| 组合 | 行为 | 你要做什么 |
|---|---|---|
| **新 App + 新设备（≥1.3.5）** | 载荷含 `t` | 正常按 §5 处理 |
| **新 App + 老设备（≤1.3.4）** | 载荷**没有 `t`** | **把"缺字段"当 `t=0`**，走"剩余==0 → 今日计划"分支。**绝不能当解析失败** |
| **老 App + 新设备** | 载荷多一个 `t` | 标准 JSON 解析会忽略未知键 ⇒ 行为与现在一致。⚠ 若你用的是**定长下标**或**字符串精确匹配**解析，必须改成按 key 取值，否则会崩 |
| 平台长度上限仍是 50 | 新载荷 56 字节被截断 | **必须把 DP121 长度上限改到 ≥64**，否则收到的是非法 JSON |

## 9. 场景速查：这种状态下我会收到什么

| 设备状态 | `剩余` | `t` | 你应该显示 |
|---|---|---|---|
| 定时计划正在割草 | >0 | `1` | 今日计划 + 倒计时 |
| 手动启动正在割草 | >0 | `2` | 手动计划 + 倒计时 |
| 定时计划**进行中**暂停 → 继续 | >0 | `1` | 今日计划（性质不变）|
| 定时计划**进行中**急停 → 继续工作 | >0 | `1` | 今日计划 |
| 定时计划**已被取消**后 → 继续工作 | >0 | `1` | 今日计划（**恢复沿用原性质**）|
| 手动计划**已被取消**后 → 继续工作 | >0 | `2` | 手动计划（**恢复沿用原性质**）|
| 手动启动被拒（低电/雨天/盖子）后 → 继续工作 | >0 | `2` | 手动计划 |
| 计划完成 / 被取消 | 0 | `0` | 今日计划 |
| 计划存在但**当前不在时段内**（未开始或已结束） | 0 | `0` | 今日计划 |
| **绕边割草中** | 0 | `0` | 今日计划（见下方说明）|
| 设备关机 / 关机充电 | — | — | 保留上次值或显示离线态 |

> **关于绕边**：绕边割草不产生"计划"对象，所以绕边期间 DP121 一直是 `t=0`。
> 若你要显示"绕边中"，请读 **DP5（工作状态）** 或 **DP111（故障/状态位域）**，不要指望 DP121。

### 一个需要注意的细节：恢复后的时段可能和配置表不同

"继续工作"时，如果原计划已被取消，设备会**重新算一个时段**（按"工作时间"从当前时刻起算，且不超过当天 24:00）。

所以你可能看到：`t=1`（定时计划），但 `st/et` 和 **DP101 里配置的那个定时窗对不上**。

- 这是**正常的**：`t` 表达的是"这单活的性质"，不是"窗口是否等于配置表"。
- 若你要判断"当前是不是就按配置的计划在跑"，请拿 `st/et` 去和 **DP101** 的计划表比对。

### 跨午夜说明

**手动计划和定时计划都不跨午夜**（结束时间最晚到当天 24:00）。
⇒ 每天倒计时必然会归零、自动回落到"今日计划"，不会出现"卡在手动计划一整夜"。

## 10. 常见问题（App 侧）

**Q1：`t` 和 DP3（工作模式）有什么区别？**
DP3 是"用户下发的意图"（smart / spot / goto_charge）。`t` 是"设备当前这一单活的来源"（计划触发 / 手动启动）。两者不对应：DP3=smart 既可能开出一单手动计划（`t=2`），定时计划自动开工时 App 根本不会下发 DP3。

**Q2：为什么我看到 `t=1` 但 `st` 和计划配置的时段不一样？**
见 §9 末尾"恢复后的时段可能和配置表不同"。

**Q3：`now` 有什么用？**
一是算剩余（`et − now`）；二是和 **DP114（设备时间）** 交叉校验设备时钟偏差。

**Q4：为什么两帧之间隔了一分钟？**
设计如此（不按倒计时上报）：有计划 60 秒、无计划 300 秒的兜底重报。**必须本地倒计时**。

**Q5：`t` 会不会在割草过程中突然从 1 变 2？**
会，但只在"这一单活确实换成了手动启动"时发生（例如用户在定时计划执行期间又手动启动了一次）。这时 `st/et` 通常也会跟着变，但**极端情况下可能撞成一样的值**——所以你的去重必须含 `t`（§6）。

**Q6：老设备收不到 `t`，我的 UI 会怎样？**
把缺字段当 `0`，所有计划都显示"今日计划"，即退化成改造前的体验。**功能不受影响**，只是分不出手动。

**Q7：`t=0` 但 `et > now` 会不会出现？**
**不会**。这是设备的契约：剩余 > 0 时 `t` 一定是 1 或 2。如果你的代码出现了这种组合，说明解析或本地状态有 bug，建议打日志。

## 12. 速查卡

```
载荷： {"st":u32,"et":u32,"now":u32,"t":0|1|2}

t = 0  无计划/未知（含"老固件没有这个字段"）→ 显示今日计划
t = 1  定时计划                              → 显示今日计划 + 倒计时
t = 2  手动计划（面板/App/定点）             → 显示手动计划 + 倒计时

剩余 = max(0, et - now)，本地每秒递减，收到新帧才重置
剩余 == 0 ⇒ 直接显示今日计划，不看 t
剩余  > 0 ⇒ t 一定是 1 或 2

去重键： (st, et, t)     ← 只看 (st,et) 会漏掉"类型切换"
兜底：   有计划 60s / 无计划 300s 一帧
窗口：   OTA 期间 & 开机自检期间停发，结束后恢复
```
