## 1–3. 工作时间倒计时（产品定稿）

**现状**：点「自动 / 定点」→ 安全确认 → 选时长（只能到当天 18:00）→ 先下发工作时间，再启动。设备**没有「剩余时间」这个数据点**，所以倒计时只能由 APP 自己按「设置时刻 + 设置时长」来算。

**定稿规则**

| 项 | 规则 |
| --- | --- |
| 显示位置 | **备选 B**：电量环下方的状态胶囊里，紧跟工作状态。最小单位是分钟，胶囊宽度放得下 |
| 展示形式 | 图标 + 剩余时间，精确到分钟，例如「⏱ 1小时59分」，不足 1 小时显示「⏱ 45分」 |
| 何时开始 | 设置了工作时间（下发成功）就开始显示 |
| 递减 | 按分钟动态递减 |
| 重新计数 | 只要重新设置工作时间，就按新时长从头跑，旧倒计时作废 |
| 暂停 | **不设暂停**：停止、急停、故障、回充、在桩等待都不影响，照常递减 |
| 隐藏 | **不设隐藏**：设置后一直显示，减到 0 后停在「0分」 |

**实现时要知道的边界**

- 倒计时完全由 APP 本机计算，与设备实际是否还在割草无关：设备中途停下、回充时，APP 照常递减。这是定稿口径，不是缺陷。
- 起点只记在本机：换手机、重装 APP，或别人从另一台手机设置的时间，这台 APP 无从得知，只能不显示（不能编时间）。要让各端一致，需固件新增「剩余作业时间」数据点。
- 「继续」（急停后恢复）不重新设置工作时间，所以不重新计数。

> 早先给出的「暂停 / 隐藏」三态建议，已按产品定稿取消。

## 4. 雨滴回充提示

**检查结果：未落实。**

- 首页回充时只显示「回桩中」，看不出是因为下雨；回到桩上后显示「在桩等待雨停」（这一条是对的）。
- 2026-10-12 那版做过一条「检测到积水，机器自动回充」，但它在**机器日志**里，而机器日志页面 **10-15 被换成了云端消息列表，从此不再显示**。所以用户实际看不到。

**设备能提供什么**：回充时，故障明细（DP111）里有「雨天」标志，V3.0 仍然保留这一位；另有事件码 45 / 145（积水发生 / 恢复）。

**文字从哪来（已确认）：涂鸦不会给「雨滴回充中」这句话。**

- 设备上报给涂鸦的只是**数据值**：
  - 工作状态（DP5）回充时报的是 `goto_charge`（值 4），不分低电、下雨、计划结束还是手动回桩；
  - 下雨原因只体现在故障明细（DP111）的「雨天」位，以及事件码 45 / 145。
  协议 V3.0 里没有「雨滴回充」这个状态值。
- 首页现在显示的「回桩中」「在桩等待雨停」等，是 **APP 把状态值翻译成文字**，不是涂鸦下发的文字。APP 目前也没有读取涂鸦平台上配置的功能点多语言名称。
- 能「涂鸦给什么就显示什么」的只有**消息通知页**：那里显示的标题和内容，就是涂鸦平台告警规则里配置的文字。平台若配了雨天告警，用户会在消息里看到平台写的那句话。

**产品定稿（2026-10-22）**

1. **在桩等待雨停 / 在桩等待充电**：按协议 V3.0 新对接的状态值显示——工作状态 10 = 在桩等待雨停、9 = 在桩等待充电（模式里只上报的 7 / 6 同义）。2026-10-22 已改为一值一词直接显示（已落实）。
2. **回桩**：按 DP 内容显示是雨滴回桩还是正常回桩；**文案 APP 不自定义，DP 给什么显示什么，不聚合**。

**按定稿落地时要知道的事实**

| 阶段 | DP 能说明什么 | 定稿下怎么显示 |
| --- | --- | --- |
| 回到桩上之后 | 工作状态本身就分雨滴（10）和正常（9） | 直接按状态值显示，已具备 |
| 回桩途中 | 工作状态只报 4（回充中），**不分原因**；雨滴只体现在故障明细的「雨天」位和事件码 45 | 「雨天」位在 → 雨滴回桩，不在 → 正常回桩 |

- 关于「DP 给什么显示什么」：DP 本身只上报**值**，不带文字。要做到 APP 不自定义文案，显示的文字得来自**涂鸦平台为功能点配置的名称**（各状态值的显示名），而不是 APP 写死的中文。
  - 需核实：涂鸦 SDK 能否取到平台为工作状态各值配置的显示名（APP 目前没有读取）。
  - 回桩途中「雨滴 / 正常」这两种说法，平台上没有对应的状态值可配名称。若要完全由 DP 给文字，需要固件把它做成状态值（例如工作状态新增「雨滴回充」），平台配好名称；否则只能由 APP 拼文字，与「不自定义」冲突。
- 早先列的三个方案中，定稿方向对应**方案 C**（文字来自平台配置）；在 SDK 能力与固件状态值确认之前，APP 不自行编写首页文字。

## 5. 陷坑脱困提醒

**检查结果：未落实。**

- 目前只有机器最终报「陷坑」故障时，才弹「机器被困，请移至平坦区域」。脱困过程中 APP 没有任何提示。
- 「机器陷入坑洼，正在脱困」这句话同样只在机器日志里（10-15 起不显示）。
- 另外，**V3.0 起故障明细（DP111）不再上报「脱困中」这一位**，旧做法即使恢复显示也收不到。

**设备能提供什么**：事件码 **41**（陷坑脱困开始）/ **141**（脱困结束）。另有事件码 31 = 陷坑困死，以及故障位图（DP18）里的「陷坑」位。

**建议**

- 收到 41：首页黄条显示「**机器陷入坑洼，正在脱困**」。
- 收到 141：黄条收起。
- 若随后报陷坑故障：照常弹「机器被困，请移至平坦区域」。
- 注意：事件码没有补发，丢一帧就漏一次提醒。黄条最好设一个超时自动收起，防止一直挂着。

## 6. 抬起 / 落地提醒

**检查结果：未落实；APP 从未在首页做过实时抬起提醒，「已落地」提醒也从来没有。**

- 首页黄条只读故障位图（DP18）。按 V3.0，那里的「抬起」位是「**抬起超时报警**」，要抬起一段时间后才报。所以抬起 1–3 秒就放下时，首页什么都不显示。这和固件说的「没动过、是打开的」并不矛盾：实时那一位固件一直在报，是 APP 没读。
- 覆盖情况：2026-10-12 那版的机器日志会显示实时的「机器被抬起」。10-15 消息页改回云端消息列表后，这个页面不再显示，相当于被覆盖了。首页黄条一直没有这条提示。
- 「设备已抬起 / 设备已落地」这两句在代码历史里从未出现过。

**设备能提供什么**

- 故障明细（DP111）里的实时「抬起」位（0x1000）：V3.0 专门保留了它，并写明「需要正在被抬起的实时提示就读这一位」，而且是变化立即上报。
- 事件码 **44 / 144**（抬起 / 恢复）。

**建议**

- 实时「抬起」位由无变有：首页黄条显示「**设备已抬起**」。
- 由有变无：显示「**设备已落地**」，几秒后自动收起。
- 抬起 1–3 秒就放下，同样先提示「设备已抬起」，再提示「设备已落地」。
- 事件码 44 / 144 作为同一提示的补充来源：两者谁先到用谁，不重复弹。
- 抬起超时后，设备会报「抬起」故障。这时按现有规则弹故障框，与上面的提示不冲突。

## 实施结果（2026-10-22）

| 项 | 实际效果 |
| --- | --- |
| 倒计时 | 自动 / 定点选好时长、工作时间下发成功即在状态胶囊显示「计时图标 + 剩余时间」，如「2小时0分」「1小时59分」「45分」；按分钟递减，到点停在「0分」不隐藏；停止、回充、在桩等待都照常走；再次设置按新时长重跑；「继续」不重计。终点只存在本机，换手机 / 重装 / 别的手机设置时不显示 |
| 抬起 / 落地 | 抬起立即提示「设备已抬起」；放下提示「设备已落地」，约 3 秒后收起。实时抬起位和事件码 44 / 144 谁先到用谁，不重复提示 |
| 陷坑脱困 | 收到 41 提示「机器陷入坑洼，正在脱困」；141 收起；若随后报陷坑故障（或事件 31 困死），收起并按原规则显示「机器被困，请移至平坦区域」；收不到 141 时 2 分钟后自动收起 |
| 黄条优先级 | 已关机 > 设备故障（DP18）> 抬起 / 落地 / 脱困提醒。抬起超时设备报的抬起故障照旧显示并弹框 |

- 进页面时设备正被抬着，会直接显示「设备已抬起」；进页面前就结束的事件不补提示。
- 当前未真机验证；事件码无兜底，丢帧时以故障明细（DP111）的下一次上报纠正抬起 / 落地。
