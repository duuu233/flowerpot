## 1. 口径

用户：「所有读取到的数据不做任何缓存、延时等机制，原始赤裸，及时展示在 APP 页面」。
范围包括**涂鸦 SDK 数据**和 **APP 后端接口数据**。

## 2. 现在每类数据怎么读

| 数据 | 来源 | 什么时候读、怎么显示 |
| --- | --- | --- |
| 设备 DP 实时值 | 涂鸦推送 | 到达即显示 |
| 设备清单 | 涂鸦云（家庭详情） | 登录、回前台、下拉刷新现拉；查询期间到的推送逐项叠加，不退回旧快照 |
| 在线状态 | 涂鸦推送 + SDK 设备模型 | 推送即显示；前台每 3 秒再对一次，补漏 |
| 割草机页面 DP | SDK 当前设备模型 | 进页现读，实时上报直接更新 |
| 固件新版本 | 涂鸦检测升级 | 每次点入口现问；提醒在进页、重新上线、版本变化时重查 |
| OTA 进度 | SDK 推送（Android 另有 3 秒兜底查询） | 收到当帧显示 **（本轮去掉 98% 停 0.9 秒）** |
| OTA 结果 | 现读 SDK 当前设备版本 | 进入安装、核验、推送、轮询时现读 |
| 设备型号 | 涂鸦 | 每次进页面现问 |
| 消息通知 | 涂鸦消息中心 | 进页拉；**收到推送立即拉，2 秒后再补拉一次（本轮）** |
| 植物资料 | 后端植物目录 | **进首页、设备换报 DP116、弹引导窗时现拉（本轮）** |
| 纪念日（自定义） | 后端 | **进页现拉；失败显示重试，不显示本机旧列表（本轮）** |
| 协议、隐私、平台邮箱、产品 ID | 后端基础数据 | **每次使用都现拉（本轮）** |

## 3. 本轮改了什么

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 消息页收到推送 | 先等 2 秒再拉 | 立即拉；2 秒后再补拉一次（云端入库可能比推送晚）；并发查询只让最后一次落到页面 |
| OTA 进度弹层 | 走到 98% 先停 0.9 秒再切「固件安装中」 | 收到当帧就按 SDK 阶段显示 |
| 植物资料 | 目录里已有就不拉；查不到的 ID 本次登录不再查 | 每次现拉；后台改了图片、名称，重进首页即更新 |
| 设备换报一株目录里没有的植物 | 继续显示上一株 | 显示「植物资料暂未获取」，补拉到就换上 |
| 纪念日（接了后端） | 先显示本机存的列表；拉取失败继续显示旧的 | 只显示本次拉到的；加载中显示加载，失败显示「纪念日加载失败」+ 重试 |
| 基础数据 | 拉到一次就复用（只有「我的」页强制重拉） | 协议页、「我的」页、开始扫描时都现拉 |

## 4. 保留的机制及原因

- **写入回显保护（用户确认保留）**：显示页亮度松手后最多 5 秒等设备回报；割草机下发后 5 秒内整包快照不覆盖该 DP；普通设置下发成功后先显示下发值。设备实际上报的 DP 照常即时显示。去掉会重新出现亮度滑块回跳。
- **轮询和补拉**（在线 3 秒、Android OTA 3 秒、消息 2 秒补拉）：都是「多读一次」，不推迟显示。
- **拉取失败时**：植物资料、基础数据保留本次登录上一次拉到的内容，页面不变空（协议页另有 App 内置文案兜底）；纪念日显示失败和重试。
- **历史曲线分帧缓冲**：设备一包只发一帧，日 7 帧、月 1～2 段，必须攒齐才能画。
- **家庭 ID 记忆**：只决定查哪个家庭，设备清单仍每次现问涂鸦。
- **配网第三步停 1～2 秒**：产品要求的流程感，与数据读取无关。

## 5. 未改、需要另行确认

- 花盆设备**从未上报过**某个 DP 时，传感器数值目前按 0、设置项按出厂默认显示（割草机电量已显示「—」）。这是「没有数据」怎么显示的问题，不是缓存；如需统一改成「—」请确认后另做。
- 后台从植物目录里**删除**某株，或改了它的涂鸦标识时，本次登录内旧条目仍可能匹配，重新登录后消失（目录接口分页，不能整表替换）。

## 6. 真机验收

1. **消息**：开着消息页让设备触发告警，推送到达后列表马上刷新；首拉还没有的，2 秒内补上。
2. **OTA**：升级进度走到 98% 时，弹层立刻显示「固件安装中」。
3. **植物**：后台改植物图片或名称，重进首页即显示新内容；设备换一株后台没配的植物时，显示「植物资料暂未获取」，不再显示上一株。
4. **纪念日**：断网进纪念日页，显示「纪念日加载失败」和「重试」；恢复网络点重试，显示后台最新列表。
5. **协议、邮箱**：后台修改后重新进页面即生效，不用重启 App。

## 8. 附：OTA 升级成功怎么判定

**结论：下面三条满足任意一条，就算 OTA 升级成功。** 另有两个前提：第 ②③ 条要看所处阶段，并且都要排除升级前就已经存在的版本（见下文「防巧合」）。

**目标版本**：用户点「立即更新」时，涂鸦检测升级返回的新版本号（例如 `1.1.3`），App 记为本次目标。三条都拿它比较，比较时忽略开头的 `V`。

| # | 成功证据 | 来源 | 什么时候算数 |
| --- | --- | --- | --- |
| ① | 涂鸦 SDK 回调「升级成功」 | Android OTA 服务状态 3 / iOS 成功回调 | 升级进行中随时算 |
| ② | 设备推送的版本号 DP = 目标版本 | 花盆 DP148、割草机 DP112；必须是本次升级开始后设备真正推上来的，不看列表里的旧值 | 正常进行中只在「固件安装中」（进度 ≥98% 或涂鸦阶段 6）判；提前到的先记下，进入安装中再比。SDK 报错转「正在确认升级结果」后，任何阶段都判；也受防巧合基线约束 |
| ③ | App 现读涂鸦 SDK 当前设备模型里的版本 = 目标版本 | 模型里的版本 DP（148 / 112）和 `verSw` | 阶段要求同 ②；另有防巧合基线 |

- 先到的为准：弹层显示「升级完成」，版本号更新、红点熄灭；之后再来的事件不改变结论。
- 以下情况仍直接判失败，同一条报文里带了目标版本也盖不过：发起前预检失败、固件已变化、5005 弱信号、割草机 DP116=7（状态不允许）或 20（校验失败），以及准备阶段零进度就失败。
- SDK 报错后核验 2 分钟仍没有任何证据，显示「暂未确认升级结果」，可以关闭窗口，这不算失败；之后读到目标版本仍会转为成功。

### 第 ① 条：监听涂鸦 SDK 的升级状态回调（主路径）

这就是涂鸦文档里「监听 OTA 状态变化回调，收到升级成功后提示用户」的做法，项目中花盆与割草机共用这条路：

1. **注册监听**：发起升级时，向涂鸦 SDK 注册这台设备的 OTA 状态监听。
2. **SDK 推送状态**：升级过程中，SDK 不断推送进度和阶段，最后推送成功、失败或超时。
3. **App 展示**：原生层转给 Flutter，底部进度弹层随之更新——进度显示「固件升级中 xx%」/「固件安装中」；**成功显示「升级完成」，同时更新版本号、熄灭红点**；失败或超时显示「升级失败」（已有升级进度的，先显示「正在确认升级结果」）。提示放在进度弹层里，不另弹提示框。

| 平台 | 使用的 SDK 回调 | 成功的判断 |
| --- | --- | --- |
| Android | 新版 OTA 服务的状态回调（`firmwareUpgradeStatus`），另有每 3 秒查询升级状态补漏；旧版 SDK 回落 `IOtaListener` | 状态 `3` = 成功（与涂鸦 `UpgradeStatus.Success` 同义），`4` 失败，`7` 超时 |
| iOS | 设备升级回调（`deviceFirmwareUpgradeSuccess` / `Failure` / `firmwareUpgradeProgress`） | 收到 `deviceFirmwareUpgradeSuccess` |

- **适用范围**：单台设备升级。涂鸦这类回调也支持批量 OTA，本项目没有批量升级功能。
- **为什么还要 ②③**：这条回调不保证一定送达——App 切后台、云端长连接断开重连、监听被系统回收时都可能丢。所以设备版本号推送（②）和现读 SDK 设备模型（③）作为兜底，三者先到为准。
- **待核实**：涂鸦文档示例里是带状态值的回调（如 `onOTAUpdateStatusChanged` + `Success`）。Android 已用这种按状态值判断的回调；iOS 目前用的是成功/失败分开的回调。当前 iOS SDK（7.8）是否另有按状态值回调、具体名称和签名，需要在装有 iOS SDK 的电脑上核对头文件后再决定是否切换。

### 第 ③ 条是什么意思

- **SDK 当前设备模型**：手机上的涂鸦 SDK 在内存里为每台设备维护一份最新状态（Android `DeviceBean`，iOS `deviceModel`），包括所有 DP 的最新已知值、在线状态和固件版本 `verSw`。SDK 通过云端长连接持续更新它。
- **② 和 ③ 的区别**：② 是等 SDK 把「DP148 变了」这件事**推**给 App；③ 是 App 不等推送，**主动问** SDK「这台设备现在在你这儿记的版本是多少」。读两个值：
  - 模型里版本 DP（花盆 148 / 割草机 112）的当前值；
  - `verSw`：涂鸦记录的设备固件版本。设备升级完重启、重新联网后，SDK 随设备信息刷新它。
- **为什么要有 ③**：推送会漏。App 切到后台、云端长连接断开重连、监听被系统回收时，设备已经装好重启，但 DP148 的推送没到 App；也有固件重启后只刷新 `verSw`、不单独推版本 DP。这时 SDK 模型里其实已经是新版本，现读一次就能补上，不会一直停在「固件安装中」或误报失败。
- **什么时候读**：进入「固件安装中」或核验时；这台设备有任何推送到达时（重新上线、DP、设备信息）；前台每 3 秒的在线轮询；重新打开升级进度时。只读手机本地的 SDK 模型，不发云端请求，也不给设备下发任何指令，不影响升级本身。
- **防巧合（②③ 都适用）**：发起升级时，先记下当时界面上的版本，以及现读 SDK 得到的版本 DP 和 `verSw`，作为「基线」。如果某个值在升级前就已经等于目标版本（例如多模组设备的 `verSw` 是另一个模组的版本、恰好同号，或设备本来就是这个版本），它不能当作成功证据。发起时现读 SDK 失败，第 ③ 条整体不用，只认 ①②。
- **边界**：SDK 模型是设备「最新已知」的状态，不是实时去设备上取。设备没联网、没上报时，③ 也看不到新版本。`verSw` 具体什么时候刷新，取决于涂鸦 SDK 和云端，需要真机确认。

### 三个例子

1. **正常**：进度 30% → 98%（固件安装中）→ 设备重启后推送 DP148=`1.1.3` → 满足 ②，升级完成。
2. **推送漏了**：安装中时 App 在后台，DP148 的推送没收到；回到前台后，3 秒轮询现读到 SDK 模型 `verSw=1.1.3` → 满足 ③，升级完成。
3. **SDK 先放弃**：96% 时 SDK 报超时 → 显示「正在确认升级结果」→ 设备装好后收到 DP148=`1.1.3`，或现读到 `1.1.3` → 升级完成；2 分钟都没有 → 显示「暂未确认升级结果」。

代码位置：`FlowerpotState._applyOtaProgress`（① 与失败转核验）、`_confirmOtaByPendingReport`（②）、`_probeOtaVersionOnce` / `_captureOtaBaseline`（③ 与基线）。原生读取入口为 `deviceSnapshot`（Android `getDeviceBean`，iOS `deviceModel`）。当前口径见 [PRODUCT_RULES §4.14](../PRODUCT_RULES.md) 和 [OTA 实现说明](../OTA_实现说明.md) 文首。
