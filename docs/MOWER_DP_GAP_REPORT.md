## 1. 整体模块流程

### 1.1 入口动线

```
搜索设备（涂鸦 BLE 扫描；认花盆两个 ID + mz7g3yzaufvoh4ls + 后台 getBasicData.deviceIdList）
  → 点「连接」→ 输路由器密码 → IMultiModeActivator 双模配网（和花盆同一条动线）
  → 设备列表：FlowerpotState.isMowerDevice（设备 productId == mz7g3yzaufvoh4ls）分流
       · 胶囊：在线 / 离线 / 已关机（DP113，FlowerpotState.isMowerShutdown）
       · 割草机离线也能点进去（进去才会尝试连蓝牙）；花盆离线照旧拦
  → AppRoutes.mowerHome + MowerHomeArguments(deviceId)
  → 外壳 MowerHomePage：进来 MowerDevice.instance.bind(deviceId)，退出 release；
       订阅 MowerDevice.failures 统一弹下发失败；底部导航 首页 / 割草计划 / 设置
```

### 1.3 下发链路

```
页面控件
  └─ MowerDevice.setSwitch / setMode / setSchedule / resetSchedule / setZones / setRain / setTimeSync / setLanguage
       ├─ 先本地回显（notifyListeners）
       ├─ _deliver / _deliverRaw：写联调日志（raw 同时打 hex 与 base64）
       └─ _publish：排队串行（保证时间同步 106 → 107 → 108 → 114 的顺序）
            └─ FlowerpotState.publishMowerDps（和花盆同一道离线门禁，不占忙锁）
                 ├─ Wi-Fi 在线（且主动探测没判不可达）→ ThingDevicePublishModeInternet（只有局域网通 → Local）
                 ├─ Wi-Fi 离线 → 蓝牙连着 / 先连一次连上 → ThingDevicePublishModeAuto（此时只剩蓝牙）
                 ├─ 都不通 → device_offline，不发
                 └─ 平台不支持通道查询（iOS）→ 普通 publishDps
                      └─ TuyaRepository.publishDpsWithMode → 原生 publishDps → 设备
结果：
  · 发出去了 → 等回显 5 秒（MowerDevice.echoTimeout）；这条 DP 没上报 → 按设备快照画回（协议 §1「超时回弹」，只记日志）
  · 没发出去 → 立刻画回 + failures → 外壳弹「割草机已离线… / 割草机已关机… / 指令没有发出去…」
```

### 1.4 上报链路

```
设备 → 涂鸦云 / 局域网 / 蓝牙
  → 原生设备监听（Android registerDevListener；iOS ThingSmartDeviceDelegate）→ Flutter 事件通道
  → FlowerpotState._listenForDeviceUpdates
       ├─ isMowerDevice → _applyDeviceUpdate 只更新列表那一行（在线、名字），不走花盆解析（植物 / 历史 / 引导窗）
       │     └─ 带 DP112 → _confirmOtaByReportedVersion（「固件安装中」阶段且 = 目标版本 → 升级完成）
       ├─ 带 DP113 → _noteMowerShutdownReport（已关机置位 / 清除）
       └─ mowerReports 流（deviceId + 本条报文带了哪些 DP）
            └─ MowerDevice._syncFromDevice → FlowerpotState.mowerDps（仓库 rawDps：按 DP 号取原始值）
                 ├─ _applyReported：bool / value / enum（字符串或序号）/ raw（hex，兼容 base64）；认不出不动原值
                 ├─ 从「等回显」里划掉这几条
                 ├─ DP116 = "7" / "20" → failures 弹提示
                 ├─ DP101 → 逐字节解析进日志 + 计划页底部临时窗口（联调设施）
                 └─ notifyListeners → 各页重画；控制页看到新故障位 → 「设备告警」弹窗
进页面时：bind 先摆「设备还没报」的中性初值（不编数），再把设备快照整份解一遍。
```

### 1.5 连接与在线

- **两个图标**：蓝牙 = 手机与设备蓝牙连着（`isBleLocalOnline`），Wi-Fi = MQTT / 局域网 / 云端任一在线；进页面自动连蓝牙，
  每 3 秒刷新，掉了后台重连（≥30 秒一次，不弹框）。
- **Wi-Fi 掉线 → 主动降级蓝牙**：涂鸦 `onStatusChanged` + 每 3 秒通道刷新 + 前台每 20 秒 `requestWifiSignal` 主动探测
  （连续 2 次没回应按离线）。**已关机（DP113）的离线是预期的**：不降级、不报掉线。
- **控制前蓝牙检查**（信号不弱于 -90 dBm 才下发）：代码在，`MowerBleGate.enabled` 默认关（2026-09-23 产品「暂时注释」）。

### 1.6 固件升级

- 入口、查新版本、确认、进度弹层、卡住提示、离线拦截：与花盆同一个 `runFirmwareUpgrade`；提醒弹窗与红点同花盆。
- 成功判定两条并存：涂鸦成功回调；DP112 在「固件安装中」阶段等于目标版本。DP116 只在拒绝（7）/ 失败（20）时弹提示。
- 细节见 `docs/OTA_实现说明.md`。

### 1.7 消息通知（不走 DP）

- 列表来自**涂鸦消息中心**（这台设备的告警档），推送由平台规则按 DP5 / DP13 / DP18 / DP117 / DP118 触发
  （`docs/涂鸦消息推送对接方案.md`）；DP111、DP112 是 string，平台不能配推送。
- 三栏按推送等级分：日志 = 通知、提醒 = 轻微、告警 = 严重；等级编码目前是推测值，见 M11。

## 2. 已经关闭的能力

「关闭」指 App 侧契约与代码按协议对齐；真机与跨平台验证单列在 §3 的 P0。

- **真机分流与配网**：搜索页认割草机产品 ID 与后台配置的全部产品 ID；设备列表按产品 ID 进割草机页面；割草机的上报不进花盆解析。
- **下发回显与超时回弹**：先回显，5 秒无上报画回设备值；失败立刻画回并提示；下发排队保证顺序。
- **DP101 / DP103 编解码**：88 字节计划（组 0 = 每天、组 1–7 = 周一到周日，小端分钟数）与 25 字节区域双向编解码；
  界面「日一…六」与 DP「周一…周日」的换算集中在 `MowerScheduleCodec`。
- **DP110 恢复默认计划**：确认后下发 true，App 不本地改，等设备上报的 DP101 刷新（协议 V2.3）。
- **DP113 关机上报**：已关机只在状态层判一次，列表、控制页共用；关机后的离线不当异常（协议 V2.5 §9.9）。
- **DP112 固件版本**：设备信息页的当前版本、OTA 成功兜底都读它；按产品 ID 区分，不与花盆 DP148 / 花盆 112（空气温度）混用。
- **DP18 故障**：首页黄条取位序最低的文案（0 = 正常隐藏）；出现新故障位弹「设备告警」，同一组故障只弹一次。
- **去掉全部假数据**：静态演示入口、稿子初值、模拟上报面板、写死消息都已删除，没报过的值不编数。
- **与花盆相同的功能照花盆**：改名、删除设备、帮助中心、固件升级及提醒、更多设备信息、消息通知列表，都调花盆那一套，只换产品 ID。

## 3. 还缺哪些

P0 是挡住发布或真机闭环的事；P1 是链路还差一段的能力；P2 需要产品或固件先给说法，代码改动本身不大。

### P0

#### M01 iOS 上割草机基本走不通
- **现状**：`ios/Runner/AppDelegate.swift` 的方法表只有登录、设备清单、AP 配网、`publishDps`、改名、解绑、OTA 等基础方法。
  没有 BLE 扫描与双模配网（iOS 配不上割草机，花盆同样）；没有 `deviceLinkState` / `connectDeviceBle` / `requestWifiSignal`
  （首页两个图标、降级蓝牙、被动离线探测都没有，下发退回普通 `publishDps`）；没有 `deviceMessages` / `startPushListen` /
  `deviceOperateLogs`（消息通知页在 iOS 上拿不到数据）。
- **缺什么**：按 Android 同名方法补 iOS 桥接；涂鸦 iOS SDK 的方法名先查文档或拆包核对，再写代码（`PRODUCT_RULES.md` §5.1）。
- **影响**：同一版本 App，iOS 的割草机从配网起就不可用。
- **证据**：`ios/Runner/AppDelegate.swift`（方法分发表）；`docs/history/2026-09/2026-09-21-割草机真机配网与DP对接.md` 未完成项 6；
  `lib/src/tuya/tuya_repository.dart`（`deviceMessages` 注释「本轮 iOS 桥接未接」）。

#### M02 蓝牙控制通道卡在固件
- **现状**：2026-09-23 真机日志 `bleChannel=false`、`getBleConnectAbility=0`，设备没有上报蓝牙连接能力；降级蓝牙的代码已写好，
  但真机上蓝牙连不上，Wi-Fi 一掉就等于离线拦下。控制前的「10 米内」蓝牙检查（`MowerBleGate`）默认关。
- **缺什么**：固件在 0x01 新功能设置命令里把 abv bit0 置 1，并支持双模并行通信（涂鸦答复）；之后真机验证降级链路，
  再由产品决定是否打开 `MowerBleGate`。
- **影响**：设备断网时 App 无法控制；「因安全要求必须在 10 米内控制设备」目前不生效。
- **证据**：`docs/PRODUCT_RULES.md` §4.10 蓝牙相关条目；`lib/src/features/mower/mower_device.dart`（`MowerBleGate`）；
  `lib/src/state.dart`（`publishMowerDps`）。

#### M03 平台功能点表与协议对不上，要重新导出核对
- **现状**：仓库里的平台导出（09_18）只有 20 条，**没有 110 / 112 / 113 / 116**；DP3 说明列还是删掉 `random` 之前的旧序。
  协议 V2.3~V2.5 陆续新增了 110 / 112 / 113（编号复用）。DP112 已由用户确认平台上有（2026-09-24），其余三条平台上建没建、
  类型是否与协议一致，仓库里没有依据。
- **缺什么**：从涂鸦平台重新导出功能点表放进 `docs/`，逐条对 V2.5（编号、标识符、类型、读写、枚举顺序）。
- **影响**：平台上没建的 DP，下发和上报一般都过不了云端（以真机日志为准）——恢复默认计划（110）、关机上报（113）、
  升级状态（116）可能整条不生效，而 App 侧看不出原因。
- **证据**：附录 B；`lib/src/features/mower/mower_dp.dart` 顶部注释。

#### M04 逐条 DP 的真机确认没有落档，用例也没跑过
- **现状**：2026-09-23 起真机联调（DP18 上报过 0、蓝牙通道有真机日志），但 DP3 枚举序、DP101 / DP103 回显、DP110 自复位、
  DP113 关机、DP112 升级兜底、DP116 等没有逐条的真机确认结论。本次核对的机器没有 Flutter 工具链，割草机相关用例
  （`test/features/mower/` 四个文件与 `test/state_ota_test.dart`）没有运行；各轮历史记录也都写着未跑。
- **缺什么**：在有工具链的机器上跑一遍 `flutter test`；真机按附录 A 逐条过一遍，结论回填到附录的「当前实现」列。
- **影响**：目前只能证明编解码与状态编排的写法符合协议，不能证明真机行为一致；最可能出问题的是 DP3 枚举序（错一位则模式整体错开）。
- **证据**：`docs/history/2026-09/2026-09-21-割草机真机配网与DP对接.md` 未完成项 4；`docs/history/2026-09/2026-09-23-割草机DP18按编号显示.md`。

### P1

#### M05 连接后不自动对时（DP114）
- **现状**：DP114 只在用户进「时间同步」页、DP106 开着、点保存时随 106 → 107 → 108 之后发出；进割草机页面（`bind`）和升级完成后都不发。
- **缺什么**：协议 V2.5 §9.1「连接后建议主动下发一次 DP114」、§6「升级固件后设备时钟基准可能偏移，App 连接后应主动下发一次」。
  可在 `bind` 读到快照、DP106 为 true 时补发一次（先确认产品同意在后台静默对时）。
- **影响**：设备时钟漂移后割草计划按错的时间执行，协议 §8 列的「计划设置后不生效」首要原因就是没对时。
- **证据**：`lib/src/features/mower/mower_device.dart`（`setTimeSync` 是 DP114 唯一的下发点）。

#### M06 DP111 明细没有去处，一类通知用户完全看不到
- **现状**：DP111 不解析，只在联调日志里原样打印。首页与告警弹窗只用 DP18 的 13 位。DP111 的通知层（circularize：碰撞、雨滴、
  低电、陷坑脱困、丢信号、刀盘电流分级、密草停顿、前上坡、状态卡死等 20 项）不在 DP18 里；它又是 string，平台不能配推送。
- **缺什么**：产品定去处——做「故障详情」页，或把通知层并进消息通知（本地生成），或明确不展示。定了之后在 `MowerDp` 加解析。
- **影响**：雨滴 / 低电 / 密草这类「设备为什么停了」的原因，用户在 App 里看不到。
- **证据**：协议 V2.5 §4.4；`docs/涂鸦消息推送对接方案.md` §1（DP111「只作 App 详情页数据源」）；
  `docs/history/2026-09/2026-09-18-割草机接DP与消息调试板.md`（「DP111、DP116、DP119 没有界面，本轮未接」）。

#### M07 指令被拒只回弹，不告诉用户为什么
- **现状**：设备拒绝时不回显、不给错误码（协议 §1），App 5 秒后把控件画回去，只记一条日志，界面上没有任何提示。
  另外「继续」（DP2=true）下发前不查 DP118 盖子，只有左三会查；开盖时点「继续」只会看到按钮弹回。
- **缺什么**：按协议 §8 的拒绝语义，用当前 DP5 / DP118 / DP18 推断原因给一句提示（如「盖子未关」「机器急停 / 报警未恢复」「不在待机」）；
  「继续」前补盖子预检（协议 §3.2：暂停中开盖会转急停）。提示文案要产品给。
- **影响**：用户会以为按钮坏了或网络问题，反复点。
- **证据**：`lib/src/features/mower/mower_device.dart`（`_armEchoCheck`）；`lib/src/features/mower/presentation/mower_control_page.dart`（`_toggleSwitch`）。

#### M08 DP112 只用来显示和兜底，不触发重查新版本
- **现状**：DP112 用于设备信息页的当前版本和升级成功兜底；设备重新上线、版本号变化都不会触发重查新版本。
  协议 §7.4 / §9.8 建议升级后「超时未收到先主动查询一次兜底」，App 现在靠 10 分钟无事件判「升级似乎已中断」。
- **缺什么**：收到 DP112 变化时刷新一次升级信息（红点 / 提醒）；升级超时前先主动查一次设备状态。
- **影响**：别处升过级（或刷回旧版）后，App 的红点与提醒要等下次拉取才更新。
- **证据**：`docs/OTA_实现说明.md` §5；`lib/src/state.dart`（`_confirmOtaByReportedVersion`）。

### P2

#### M09 DP119 工作时间没有界面
- **现状**：`MowerDp.operatingTime` 只定义了常量，不下发、不解析；稿子的设置页没有这一项。
- **缺什么**：产品定要不要放进设置页（1–24 小时，每次出桩作业时长上限；面板 Operating time 菜单同源）。
- **影响**：只能在设备面板上改；App 看不到当前值。
- **证据**：`lib/src/features/mower/mower_dp.dart`；`docs/UI/v2/割草机/割草机-设置.png`。

#### M10 没有「取消任务 / 回待机」入口（DP3 = standby）
- **现状**：「停止」发的是 DP2=false（暂停，保留任务现场），App 从不下发 `standby`。暂停后想放弃任务只能点「回归」；
  协议 §9.4 列的误启动取消、回桩途中原地停机、在桩等待时退出等待，App 都做不到。
- **缺什么**：产品定要不要加（例如暂停态下多一个「结束任务」）。代码只需调 `setMode(standby)`，`MowerMode.sendable` 已放行。
- **影响**：暂停后的机器会一直停在「已暂停」，直到用户点继续或回归。
- **证据**：协议 V2.5 §3.1、§9.4；`lib/src/features/mower/presentation/mower_control_page.dart`（四颗按钮）。

#### M11 消息通知的等级编码是推测的
- **现状**：三栏按推送等级分，但等级字段的编码涂鸦文档没写，现按 1 通知 / 2 轻微 / 3 严重推测，认不出的归「告警」；
  推送规则要在涂鸦平台上按 `docs/涂鸦消息推送对接方案.md` 配好才有消息。
- **缺什么**：真机上各触发一次三个等级的推送，定下编码后只改 `_levelCodes` 一处（花盆一起生效）。
- **影响**：编码猜错时消息会分错栏。
- **证据**：`docs/TUYA_CAPABILITY_AUDIT.md` 5.6；`lib/src/features/messages/device_messages_view.dart`。

#### M12 DP117「已充满」与「充电中」显示一样
- **现状**：`charging` 与 `full` 都画成「充电中」+ 闪电动效，稿子只有「充电中」一张。
- **缺什么**：产品定充满时要不要单独写「已充满」、闪电要不要停。
- **影响**：小；充满挂桩的机器会一直显示「充电中」。
- **证据**：`lib/src/features/mower/mower_ui.dart`（`MowerPowerState.charging`）。

#### M13 稿子与协议之间的空档
- 稿子画了、协议没有的（中文机器语言、雨后延迟 3 小时、硬件版本、SN、预计充满时间、时区「自动设置」、重新配网），
  以及协议有、稿子没画的（DP111、DP119、回待机、已充满），逐条见 §5。每条都要产品或固件给一句话：补 DP、改稿，还是保持现状。
