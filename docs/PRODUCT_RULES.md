## 1. 配网（规则最多，优先读完）

### 1.1 配网方式：**只有 AP 热点**（EZ 实测不支持，已屏蔽）

- 设备采用**涂鸦标准 AP 热点配网（AP-cfg）**。
- ⛔ **EZ / SmartConfig 快连：2026-09-11 已实现并真机实测——设备不支持，配不上，入口已屏蔽。**
  设备开发原先的说法「采用 AP-cfg，**没使用** EZ」就此坐实成"不能用"。
  `PairingModeSwitch` / `_PairingModeSelector` / `pairing_mode.dart` 已全部删除；
  `FlowerpotState.pairViaEz` 的方法体保留**仅作备查**（万一以后固件开了 EZ），
  **没有任何入口能走到它**。**不要再提议改用 EZ。**
- 同日产品提供的智能生活截图印证了方向：**它走的是涂鸦「新流程」AP**——连上设备 →
  让**设备**扫 Wi-Fi → 把**设备扫到的**列表给用户选 → 输密码 → 配网。
  不是 EZ 广播。见 `docs/history/2026-09/2026-09-11-smartlife-screenshots.md`。
- **不考虑**有线、蓝牙、二维码、子设备、NB-IoT、Matter、4G/蜂窝那些模式。

### 1.1.1 原口径（仍然适用的部分）

- 设备采用**涂鸦标准 AP 热点配网（AP-cfg）**；设备开发 2026-09-10 的原话是
  「**没使用** EZ/SmartConfig 快连」。⚠️ 此前据此写成「永远不考虑 EZ」，
  **2026-09-11 已修正**：「没使用」不等于「不能用」，涂鸦模组通常两种都支持、由固件配置决定，
  所以 EZ 进入测试（见 1.1）。桥接层的 EZ 路径（Android `EZ_MODE_NAMES` +
  `newEZWifiConfigDevActivator`）本来就完整，不再是死代码。
- **只做 Wi-Fi 配网。** 不需要 4G / 蜂窝那条激活路径，也不需要有线、蓝牙、二维码、
  子设备、NB-IoT、Matter 那些模式。（2026-09-10）
  > 已核查：代码里 `mode` 写死 `'ap'`，`THING_4G_GATEWAY` 只出现在注释的能力清单里，
  > 没有任何调用路径。桥接层里的 EZ 分支是死代码，不要切过去。
- 走涂鸦的**「热点配网新流程」**。固件前提 TuyaOS ≥ 3.6.1 已由设备团队确认满足。
  （2026-09-10）

### 1.2 配网全程**不出现系统入网授权框**——连热点由 SDK 内部完成

**（2026-09-11 定稿口径：新流程 = 把连设备这件事整个嫁接给涂鸦 SDK，不要弹框授权设备。）**

- 那个框（「要与智能花盆搭配使用的设备 / 取消 / 连接」）由 `WifiNetworkSpecifier` +
  `requestNetwork` 触发，Android 10+ 必弹、关不掉、不能由 App 代点。
- ⇒ **App 侧一次都不调它。** 连设备热点交给 SDK：
  `queryDeviceConfigState`（`apQueryDeviceWifi`）内部完成连接与设备状态查询，
  `startActivator`（`apStartPairing`）负责下发凭据。
- 依据：产品提供的智能生活截图（`docs/配网1.jpg` / `配网2.jpg`）证明它就是这么做的——
  五步进度 + 让用户从**设备扫到的** Wi-Fi 列表里选。

#### 当前动线上唯一允许调的 state 方法

`connectDeviceForPairing()` / `pairViaDeviceHotspot()` / `probeWifi()` /
`stopDevicePairing()` / `cancelPairing()` / `prepareForPairing()` /
`releaseDeviceHotspot()`。**这七个都不触达 `_joinHotspotForPairing`。**

⚠️ `pairViaHotspot()` 与 `connectDeviceHotspot()` 会调 `WifiNetworkSpecifier`，
**它们只作为 AP 原流程的回退路径存在，不得接进当前动线**；两处调用点的注释写了怎么切。

#### 顺带记住

手机若**已经保存过**该热点，设备一开机系统就自动重连——那是唯一"天然已连上"的情形，
与 App 无关。我们自己用 `WifiNetworkSpecifier` 连的那次不会被系统保存。

### 1.3 智能生活 App 只是参考，不照抄

- 产品给的智能生活进度串（设备连接建立成功 / Wi-Fi 配置已下发 / 设备连接路由器成功 /
  设备激活中 / 设备即将上线）是**参考**，说明"大致应该发生什么"。（2026-09-10）
- **我们页面展示的内容保持现状**，不按它改版。它的价值在于证明 SDK 会上报真实进度，
  据此把进度从"装的"换成真的。

### 1.4 动线：搜到 → 点该行「连接」→ 从**设备扫到的**网络里选 → 输密码 → 配网

**（2026-09-11 定稿，照智能生活的步骤，`docs/配网1.jpg` / `配网2.jpg`）**

| # | 页面 | 发生什么 | 用户要做什么 |
| --- | --- | --- | --- |
| 1 | 搜索设备 | 扫到设备，列出来，每行一颗「连接」；扫到后停止扫描 | — |
| 2 | 搜索设备（进度态） | 点「连接」⇒ `queryDeviceConfigState`：**SDK 连上设备 + 设备扫 Wi-Fi**。页面盖上五步进度卡，前两步在这里跑完 | 等着（可取消） |
| 3 | 连接 Wi-Fi | **自动弹出「可用Wi-Fi」列表——设备自己扫到的那份**（带信号格数与加密标记） | 选网络 |
| 4 | 连接 Wi-Fi | — | 输密码，点「开始配网」 |
| 5 | 配网进度 | `startActivator` 下发凭据；后三步由 `onStep` **真实驱动**（不是排出来的） | 等着 |

要点：

- **进度是五步，不是三步**：连接设备 / 设备找网络 / 设备连路由器 / 云端激活 / 设备上线。
  前两步来自 `queryDeviceConfigState`，后三步来自 `startActivator` 的 `onStep` 回调。
- **网络列表用设备扫到的那份**（`WifiInfoBean{ssid, rssi, sec}`）。设备能看见的才是它连得上的；
  而且这时手机已挂在设备热点上，手机自己也扫不出有用的东西。设备没给（老固件 `207207`）
  才退回手机扫到的。
- ⚠️ **UI 风格保持本项目现有的**（产品 2026-09-11：「UI 风格不用改，只是改步骤」）——
  步骤名沿用短标签，细节放在每步的说明里，不照抄智能生活的长句。
- **随时可切回 AP 原流程**（`223bdae^` 那版能配成的路径）：搜索页把
  `connectDeviceForPairing()` 换回 `connectDeviceHotspot(hotspotSsid:)`，配网页把
  `pairViaDeviceHotspot` 换回 `pairViaHotspot`。两条路径代码都完整保留，各自的调用点都写了
  注释指路。

### 1.4.1 无论怎么退出，都要把手机的 Wi-Fi 还回去

**（2026-09-10）** 用户点过某一行的「连接」之后，手机就挂在设备热点上、**真的没有外网**。
所以**每一条离开配网动线的路径都必须把网络还原**，不能把用户撂在一个没网的热点上：

| 退出方式 | 处理 |
| --- | --- |
| 配网中途点「取消配网」 | 中止 activator，一并解开网络绑定 |
| 配网失败 | 失败收尾里放掉热点连接与配网器 |
| 搜索页点过「连接」之后返回 | 页面销毁时放、切后台也放。本页自己不建连接，但 SDK 配网时可能把进程绑到设备热点上，解一次是保险 |
| **配网成功** | **也要放** —— 设备随即关掉自己的热点，进程若还绑在那个已消失的网络上，紧接着读设备列表就会失败（表现为「配网成功但读不到设备」） |
| 进了「连接 Wi-Fi」页又退回来 / 输到一半退出 | 页面销毁时放（不要只在"配网真的跑起来过"时才处理） |
| **App 被切到后台** | 放掉并把界面退回「点连接」之前的状态；真要配网时会重新连（已连则跳过） |
| App 被杀 | 进程专属连接随进程消失，系统自动切回，无需处理 |

⚠️ 唯一**不能**放的时机：配网正在跑（会掐断正在用的通道），以及连热点的系统确认框正显示
时（那时页面也处于 paused，放等于自己把刚发出的请求撤回）。

### 1.5 设备开机即可配网——**但有时限**

- **设备只要开机就处于可配网状态**，不需要长按、复位或任何确认动作。（2026-09-10）
- 所以端上文案一律只说「请确认设备已开机」，**不要**出现「长按设备按键进入配网状态」
  「确认指示灯闪烁」这类步骤；「设备已在配网状态，继续」这类按钮删掉。
- ⚠️ **修正（2026-09-10 晚，产品反馈）：设备静置一段时间会退出配网模式**，那之后它不再
  广播热点，扫多久都搜不到。所以「开机即可配网」只在**上电后的一段时间内**成立。
  由此定下的处理：
  - 真扫已经跑在系统配额上限（前台 4 次 / 2 分钟 ⇒ 32 秒一次），**没有"加快频率"可言**；
    这件事不能靠调扫描节奏解决。
  - **搜不到时要尽早把正确动作交给用户**：40 秒还一台都没有，就说明「设备静置后会退出
    配网状态，请断电重启」并立刻给出「重新扫描」——不要让他等满 3 分钟窗口。
  - 重启后热点一定在，下一次扫描就能看见，这比任何频率调整都有效。

### 1.6 配网过程中不要 App 自己的弹框

- 1/2/3 步骤里**不要任何 App 弹出框**（「查找设备…」「没有找到任何设备」这类一概不要）。
  必要文案**精简进步骤里**展示。（2026-09-10）
- 系统自己的框不在此列（那是系统行为，见 1.2 的处理方式）。

### 1.7 失败要能看出原因

- 配网失败时**必须能看出是哪一步、什么原因**，不能只给一句笼统文案。（2026-09-10）
- 失败码**无论认不认得都要显示**；认不得的给族级提示，不编造具体含义。
- 各步耗时单独一行显示——失败码只说"哪一类"，耗时才说"死在哪一步"。

## 2. 搜索设备页

- 职责就是**把设备搜出来并展示**，不承担任何"确认设备状态"的交互。（2026-09-10）
- 扫到的设备**直接列在页面下方**，不跳页；类似"开了一个监听"。
- 「重新扫描」按钮**只在搜索为空时**显示。（2026-09-10）
- ⚠️ **搜索页必须给涂鸦 SDK 留出扫描配额。**（2026-09-11）`startScan` 的配额是**按 UID 算**的
  ——SDK 就跑在我们进程里，和搜索页**共用** 4 次 / 2 分钟。原来 32 秒一次真扫会把配额用满，
  用户紧接着点「连接」时 SDK 想扫一次找热点却被限流，**在等一个永远不会来的扫描结果广播**，
  于是「连接设备」卡几十秒后超时。现在搜索页最多用 2 次 / 2 分钟（62 秒一次），另外 2 次留给
  SDK；空档由 1 秒一次的读缓存补（读缓存不占配额）。**不要把这个预留改回 0。**
- 「发现 X 台设备」的**字体要小一点**。（2026-09-10）
- **首次进入要授权时，等用户授权完再触发真实搜索**；不是首次进入就等页面加载完毕、
  或稍微延迟一点，让设备能马上被搜出来。（2026-09-10）
  > 为什么：Android 前台应用每 2 分钟只许 4 次真扫，授权那几十秒里发出去的都白扔。

## 6. 协作方式

- **先 pull 再改**；任务完成并验证后默认提交并推送（Hub 约定）。
- **文档不要来回乱改。** 结论写进 `AI_CONTEXT.md` 或本文件；试错过程写进
  `docs/history/`。不要在 `AI_CONTEXT.md` 里堆成一串自相矛盾的时间日志。（2026-09-10）
- **产品说过的要求要归纳到本文件**，不要让产品反复强调。（2026-09-10）
- 本机（dev box）没有 Flutter / Dart / Kotlin 工具链，所以 flowerpot 的改动**一律未经
  编译与测试**。报告时必须说明这一点，不得宣称通过。
- 既然编译不了，就**把编译器会替你抓的事自己抓一遍**（2026-09-10 被一次打包失败教训到）：
  1. **新引用的类型必须确认 import。** `FlowerpotState` 在 `lib/src/state.dart`，
     `FlowerpotScope` 在 `lib/src/app/flowerpot_app.dart`——两者是**不同文件**，
     只 import 后者拿不到前者（那次报错就是这个）。照已有页面（如 `device_list_page.dart`）
     的 import 清单抄。
  2. **删 import 之前先搜一遍还有没有人用**；删方法/字段之后搜一遍引用是否归零。
  3. **用最保守的语法。** 不写没法验证的新语法糖（带 `when` 守卫的模式 switch、
     记录模式解构之类）；`if` 链和局部变量一眼能看懂，也不会和 `Widget.key` 之类撞名。
  4. 改完做一次括号配平自检，并和 `git show HEAD:<file>` 的基线对比增量。
