## 1. 配网（规则最多，优先读完）

### 1.1 只有一种模式：涂鸦标准 AP 热点配网

- 设备采用**涂鸦标准 AP 热点配网（AP-cfg）**，**不支持 EZ/SmartConfig 快连**。
  **永远不考虑 EZ**，设备不支持。（2026-09-10，设备开发口径）
- **只做 Wi-Fi 配网。** 不需要 4G / 蜂窝那条激活路径，也不需要有线、蓝牙、二维码、
  子设备、NB-IoT、Matter 那些模式。（2026-09-10）
  > 已核查：代码里 `mode` 写死 `'ap'`，`THING_4G_GATEWAY` 只出现在注释的能力清单里，
  > 没有任何调用路径。桥接层里的 EZ 分支是死代码，不要切过去。
- 走涂鸦的**「热点配网新流程」**。固件前提 TuyaOS ≥ 3.6.1 已由设备团队确认满足。
  （2026-09-10）

### 1.2 配网全程**不得出现系统入网授权框**

**这是硬性要求，不是取舍。**（2026-09-10 提出，2026-09-11 再次确认：「系统框从始至终都不会
出现」「整个配网流程都没有系统框的弹出」）

- 那个框是「要与智能花盆搭配使用的设备 / 取消 / 连接」，由 `WifiNetworkSpecifier` +
  `requestNetwork` 触发，Android 10+ 上**必弹、关不掉、不能由 App 代点**。
- ⇒ **App 侧一次都不能调它。** 连设备热点交给涂鸦 SDK 在配网过程中内部完成（官方文档：
  「在配网过程中，SDK 会在指定时间内自动去连接 AP 热点」）。
- ⇒ 搜索页那颗「连接」**只是选定这台设备**，不做连接动作。

#### ⚠️ 不要再凭一次超时把 `joinDeviceHotspot` 加回来

2026-09-10 曾因为一次 `207220 / 失败 45073ms`（配网任务整体超时，全程无框、手机始终在
路由器上）判定「SDK 不会自己连热点」，据此把 `WifiNetworkSpecifier` 加了回来
（`39d29d6` → `78afe2a` → `a07820c`）。**那个判定是错的**：当时还不知道
**设备静置一段时间会退出配网模式**（见 1.5），那 45 秒里设备很可能早就不广播热点了——
超时与「SDK 会不会连」**无关**。

**复测必须用刚断电重启过的设备。** 否则同一个超时会把同一个错误结论再推一遍。
若用新上电的设备仍然超时，下一步是走涂鸦工单问清 `queryDeviceConfigState` 在 Android 10+
内部如何连 AP，**而不是**把那个 API 加回来。

#### 那么谁把手机连到设备热点上？

AP 配网要求手机**已经在设备热点上**。既然 App 不能调 `WifiNetworkSpecifier`，就只剩两条：

1. **手机自己自动连上**——该热点已在「已保存的网络」里（用户曾在系统 Wi-Fi 里连过一次）。
   这是**唯一"既无框又已连上"**的情形，也最可能是"以前都可以直接配网"的真正原因。
2. **用户在系统 Wi-Fi 里连一次**——我们把系统 Wi-Fi 面板拉到 App 上方
   （`Settings.Panel.ACTION_INTERNET_CONNECTIVITY`），用户点一下。这不是授权框，是选网络；
   而且**系统会保存它**，于是下一次就变成第 1 种情形、全自动。

所以产品动线是：**开始配网前先检查手机在不在设备热点上**（只读扫描缓存，不占配额）。
不在就**立刻**在「连接 Wi-Fi」页上说清楚并给出「打开系统 Wi-Fi 列表」——
**不要让用户空等 45 秒再收到一句 `207220`**。

#### 顺带记住

手机若**已经保存过**该热点（用户曾在系统设置里手动连过），设备一开机系统就自动重连、
不经过任何 App API——那是唯一"天然无框且已连上"的情形。我们自己用 `WifiNetworkSpecifier`
连上的那次**不会**被系统保存（进程专属的一次性连接），所以靠 App 连永远不会变成「记住了」。

### 1.3 智能生活 App 只是参考，不照抄

- 产品给的智能生活进度串（设备连接建立成功 / Wi-Fi 配置已下发 / 设备连接路由器成功 /
  设备激活中 / 设备即将上线）是**参考**，说明"大致应该发生什么"。（2026-09-10）
- **我们页面展示的内容保持现状**，不按它改版。它的价值在于证明 SDK 会上报真实进度，
  据此把进度从"装的"换成真的。

### 1.4 动线：搜到 → 点该行「连接」 → 输 Wi-Fi 密码 → 配网

**（2026-09-11 定稿）**

| # | 页面 | 发生什么 | 用户要做什么 |
| --- | --- | --- | --- |
| 1 | 搜索设备 | 扫到设备，**列出来，每行一颗「连接」**；扫到后停止扫描 | — |
| 2 | 搜索设备 | 点「连接」⇒ **只是选定这台设备**（等云端预取落地后跳页，不连热点） | 点「连接」 |
| 3 | 连接 Wi-Fi | SSID 已填好（搜索页带过来的当前网络名） | 选/确认 Wi-Fi，输密码，点「开始配网」 |
| 4 | 配网 | ① `queryDeviceConfigState`（**SDK 在这里连热点**）② `startActivator` 下发凭据 | 等着 |

**全程没有任何系统弹框**（见 1.2）。

要点：

- 取令牌 / 取安全配置 / 确认家庭由搜索页进页面时预取，并在跳页前 await——这三件都走云端，
  而配网一开始 SDK 就把手机切到设备热点、那时没有外网。
- 搜索页把当前 Wi-Fi 名带给下一页：配网一开始手机就离开路由器，之后读不到当前网络了。
- 中间步骤尽量减少等待，按最快、体验最好的方案实现。**不考虑 Android 9 及以下。**
- 文案不要照抄智能生活的「无 4G 信号或信号不佳」——**本设备没有蜂窝模块**。

### 1.4.1 无论怎么退出，都要把手机的 Wi-Fi 还回去

**（2026-09-10）** 用户点过某一行的「连接」之后，手机就挂在设备热点上、**真的没有外网**。
所以**每一条离开配网动线的路径都必须把网络还原**，不能把用户撂在一个没网的热点上：

| 退出方式 | 处理 |
| --- | --- |
| 配网中途点「取消配网」 | 中止 activator，一并解开网络绑定 |
| 配网失败 | 失败收尾里放掉热点连接与配网器 |
| 搜索页点过「连接」之后返回 | 页面销毁时放、切后台也放。本页自己不建连接，但 SDK 配网时可能把进程绑到设备热点上，解一次是保险 |
| **配网成功** | **也要放** —— 设备随即关掉自己的热点，进程若还绑在那个已消失的网络上，紧接着读设备列表就会失败（表现为「配网成功但读不到设备」） |
| 进了「连接 Wi-Fi」页又退回来 / 输到一半退出 | 页面销毁时放（不要只在"配网真的跑起来过"时才处理） |
| **App 被切到后台** | 放掉并把界面退回「点连接」之前的状态；真要配网时会重新连（已连则跳过） |
| App 被杀 | 进程专属连接随进程消失，系统自动切回，无需处理 |

⚠️ 唯一**不能**放的时机：配网正在跑（会掐断正在用的通道），以及连热点的系统确认框正显示
时（那时页面也处于 paused，放等于自己把刚发出的请求撤回）。

### 1.5 设备开机即可配网——**但有时限**

- **设备只要开机就处于可配网状态**，不需要长按、复位或任何确认动作。（2026-09-10）
- 所以端上文案一律只说「请确认设备已开机」，**不要**出现「长按设备按键进入配网状态」
  「确认指示灯闪烁」这类步骤；「设备已在配网状态，继续」这类按钮删掉。
- ⚠️ **修正（2026-09-10 晚，产品反馈）：设备静置一段时间会退出配网模式**，那之后它不再
  广播热点，扫多久都搜不到。所以「开机即可配网」只在**上电后的一段时间内**成立。
  由此定下的处理：
  - 真扫已经跑在系统配额上限（前台 4 次 / 2 分钟 ⇒ 32 秒一次），**没有"加快频率"可言**；
    这件事不能靠调扫描节奏解决。
  - **搜不到时要尽早把正确动作交给用户**：40 秒还一台都没有，就说明「设备静置后会退出
    配网状态，请断电重启」并立刻给出「重新扫描」——不要让他等满 3 分钟窗口。
  - 重启后热点一定在，下一次扫描就能看见，这比任何频率调整都有效。

### 1.6 配网过程中不要 App 自己的弹框

- 1/2/3 步骤里**不要任何 App 弹出框**（「查找设备…」「没有找到任何设备」这类一概不要）。
  必要文案**精简进步骤里**展示。（2026-09-10）
- 系统自己的框不在此列（那是系统行为，见 1.2 的处理方式）。

### 1.7 失败要能看出原因

- 配网失败时**必须能看出是哪一步、什么原因**，不能只给一句笼统文案。（2026-09-10）
- 失败码**无论认不认得都要显示**；认不得的给族级提示，不编造具体含义。
- 各步耗时单独一行显示——失败码只说"哪一类"，耗时才说"死在哪一步"。

## 2. 搜索设备页

- 职责就是**把设备搜出来并展示**，不承担任何"确认设备状态"的交互。（2026-09-10）
- 扫到的设备**直接列在页面下方**，不跳页；类似"开了一个监听"。
- 「重新扫描」按钮**只在搜索为空时**显示。（2026-09-10）
- 「发现 X 台设备」的**字体要小一点**。（2026-09-10）
- **首次进入要授权时，等用户授权完再触发真实搜索**；不是首次进入就等页面加载完毕、
  或稍微延迟一点，让设备能马上被搜出来。（2026-09-10）
  > 为什么：Android 前台应用每 2 分钟只许 4 次真扫，授权那几十秒里发出去的都白扔。

- SSID 带出规则：**手机连着 Wi-Fi 就直接带出来；没连就留空**，让用户自己去切换选择。
  （2026-09-10）
- 底部那段"系统会弹框询问是否连接…不必到系统设置"的解释**删掉**；整体间距收紧，
  **内容在首屏完整展示**。（2026-09-10）
- 输入框获焦时**手机虚拟键盘不能挡住当前输入框**，页面要按焦点动态往上移。（2026-09-10）

## 4. 通用 UI 口径

- **toast 不带来源前缀**（`接口-`、`APP-`、`涂鸦-`），直接输出内容。（2026-09-10）
- toast 文案**不要换行**——必要时调整最大宽度。（2026-09-10）
- 登录页手机号格式校验**只用 toast**，去掉 form 表单下面的提示文案。（2026-09-10）
- 启动页**只留背景图**，文案先隐藏。（2026-09-10）
- **首屏放得下优先于加滚动条**：内容放不下时先收紧间距（尤其是插图上下的留白），
  不要让用户滚动才看到关键按钮。（2026-09-10，配网页/失败页均提过）

## 6. 协作方式

- **先 pull 再改**；任务完成并验证后默认提交并推送（Hub 约定）。
- **文档不要来回乱改。** 结论写进 `AI_CONTEXT.md` 或本文件；试错过程写进
  `docs/history/`。不要在 `AI_CONTEXT.md` 里堆成一串自相矛盾的时间日志。（2026-09-10）
- **产品说过的要求要归纳到本文件**，不要让产品反复强调。（2026-09-10）
- 本机（dev box）没有 Flutter / Dart / Kotlin 工具链，所以 flowerpot 的改动**一律未经
  编译与测试**。报告时必须说明这一点，不得宣称通过。
- 既然编译不了，就**把编译器会替你抓的事自己抓一遍**（2026-09-10 被一次打包失败教训到）：
  1. **新引用的类型必须确认 import。** `FlowerpotState` 在 `lib/src/state.dart`，
     `FlowerpotScope` 在 `lib/src/app/flowerpot_app.dart`——两者是**不同文件**，
     只 import 后者拿不到前者（那次报错就是这个）。照已有页面（如 `device_list_page.dart`）
     的 import 清单抄。
  2. **删 import 之前先搜一遍还有没有人用**；删方法/字段之后搜一遍引用是否归零。
  3. **用最保守的语法。** 不写没法验证的新语法糖（带 `when` 守卫的模式 switch、
     记录模式解构之类）；`if` 链和局部变量一眼能看懂，也不会和 `Widget.key` 之类撞名。
  4. 改完做一次括号配平自检，并和 `git show HEAD:<file>` 的基线对比增量。
