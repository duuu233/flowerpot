# 产品口径与硬性要求

**这份文档的作用：把产品已经说过的要求固定下来，不需要反复强调。**

- 动手前先读这里。这里写的是**产品口径与硬性约束**（"必须怎样 / 绝对不要怎样"）。
- 技术事实（接口、签名、代码在哪）看 [`../AI_CONTEXT.md`](../AI_CONTEXT.md)。

## 1. 配网（规则最多，优先读完）

### 1.1 配网方式：**只有 AP 热点**（EZ 实测不支持，已屏蔽）

- 设备采用**涂鸦标准 AP 热点配网（AP-cfg）**。
- ⛔ **EZ / SmartConfig 快连：2026-09-11 已实现并真机实测——设备不支持，配不上，入口已屏蔽。**
  设备开发原先的说法「采用 AP-cfg，**没使用** EZ」就此坐实成"不能用"。
  `PairingModeSwitch` / `_PairingModeSelector` / `pairing_mode.dart` 已全部删除；
  `FlowerpotState.pairViaEz` 的方法体保留**仅作备查**（万一以后固件开了 EZ），
  **没有任何入口能走到它**。**不要再提议改用 EZ。**
- 同日产品提供的智能生活截图印证了方向：**它走的是涂鸦「新流程」AP**——连上设备 →
  让**设备**扫 Wi-Fi → 把**设备扫到的**列表给用户选 → 输密码 → 配网。
  不是 EZ 广播。见 `docs/history/2026-09/2026-09-11-smartlife-screenshots.md`。
- **不考虑**有线、蓝牙、二维码、子设备、NB-IoT、Matter、4G/蜂窝那些模式。

### 1.1.1 原口径（仍然适用的部分）

- 设备采用**涂鸦标准 AP 热点配网（AP-cfg）**；设备开发 2026-09-10 的原话是
  「**没使用** EZ/SmartConfig 快连」。⚠️ 此前据此写成「永远不考虑 EZ」，
  **2026-09-11 已修正**：「没使用」不等于「不能用」，涂鸦模组通常两种都支持、由固件配置决定，
  所以 EZ 进入测试（见 1.1）。桥接层的 EZ 路径（Android `EZ_MODE_NAMES` +
  `newEZWifiConfigDevActivator`）本来就完整，不再是死代码。
- **只做 Wi-Fi 配网。** 不需要 4G / 蜂窝那条激活路径，也不需要有线、蓝牙、二维码、
  子设备、NB-IoT、Matter 那些模式。（2026-09-10）
  > 已核查：代码里 `mode` 写死 `'ap'`，`THING_4G_GATEWAY` 只出现在注释的能力清单里，
  > 没有任何调用路径。桥接层里的 EZ 分支是死代码，不要切过去。
- 走涂鸦的**「热点配网新流程」**。固件前提 TuyaOS ≥ 3.6.1 已由设备团队确认满足。
  （2026-09-10）

### 1.2 系统 UI 只允许出现在「连接」那一刻

Android 10+ 上「把手机连到设备热点」这一步会弹一次系统入网授权框
（`WifiNetworkSpecifier`，关不掉、不能代点）。**涂鸦 2026-09-11 书面确认无绕过方案，
见 §4.0。**

产品口径：**统一收在搜索页那颗「连接」按钮上**——只在那一刻出现一次，之后的页面
（输密码、配网进度）**一个系统框都没有**。手机已经在该热点上时（上次留下的、或系统记住后
自动重连）**直接跳过，零点击**。

#### ⛔ 「连接热点」是 App 的活，不是 SDK 的——不要再删

1. 涂鸦官方回复原文：「App 调用系统 API 自动连接设备热点」；
2. 官方 AP 文档的定义：「……**但用户需要手动切换手机的 Wi-Fi 设置**」；
3. 涂鸦 2026-09-11 书面确认：文档里「SDK 会在指定时间内自动连接」**指的是设备端行为**，
   不是手机侧；
4. git：`223bdae^`（有这一步）能配网成功；`223bdae`（改成"指望 SDK 自己连"）之后
   **全是 `207220` 配网任务整体超时**；
5. 四次真机实测：失败时手机**始终留在路由器上**，SDK 从没把它切过去。

#### 取令牌必须在连热点**之前**

涂鸦的步骤表把「取 Token」排在连热点之后。**那样走不通**——连上设备热点手机就没有外网，
取不到云端的东西。所以搜索页进页面时就预取（`prepareForPairing`），
`pairViaHotspot` 第①步直接复用。

#### 既然关不掉，就别让它显得像出错

（涂鸦的建议也是"收口至显式引导"。）

1. **按钮正上方预告**（`device-search-consent-hint`）：「点「连接」后，系统会问一次是否连接
   设备热点，选「连接」即可。只在这一步问一次，后面输密码、配网都不会再弹。」
   手机已经在设备热点上时这行**不出现**——不会弹的框不要预告。
2. **等待时进度页副标题换成同一口径**（`pairing-progress-subtitle`）：系统框盖在进度页
   上面，用户点完「连接」框消失，这一页是他看到的第一屏，写清刚才那个框是正常步骤。
3. **在系统框上点「取消」不是故障**：失败文案给的是「重新点「连接」，在系统框里选「连接」
   即可」，不要把"断电重启"这种排障步骤推给他（`hotspot_join_cancelled` 单独一支）。
4. **只弹一次靠原生记账**：`boundHotspotSsid` + 还活着的 `hotspotCallback` 命中就原地复用，
   不再发 `requestNetwork`。离页/取消会按 §1.4.1 释放连接，那之后再连会重新问——这是对的，
   因为连接确实已经还给路由器了。

### 1.3 智能生活 App 只是参考，不照抄

- 产品给的智能生活进度串（设备连接建立成功 / Wi-Fi 配置已下发 / 设备连接路由器成功 /
  设备激活中 / 设备即将上线）是**参考**，说明"大致应该发生什么"。（2026-09-10）
- **我们页面展示的内容保持现状**，不按它改版。它的价值在于证明 SDK 会上报真实进度，
  据此把进度从"装的"换成真的。

### 1.4 动线：搜到 → 点该行「连接」→ 输路由器密码 → 配网（三步进度）

**（2026-09-11 定稿——"最稳定、最简洁"那一版）**

| # | 页面 | 发生什么 | 用户要做什么 |
| --- | --- | --- | --- |
| 1 | 搜索设备 | 扫到设备，列出来，每行一颗「连接」；扫到后停止扫描 | — |
| 2 | 搜索设备（进度态） | 点「连接」⇒ App 把手机连到设备热点上。**这里弹一次系统入网授权框**，全流程只此一次 | 在系统框里点「连接」 |
| 3 | 连接 Wi-Fi | SSID **已经填好**（搜索页在连热点**之前**抓到的路由器名，见 `PairingArguments.routerSsid`）；要换就点「切换」，列的是手机扫到的网络 | 输密码，点「开始配网」 |
| 4 | 配网进度 | `pairViaHotspot`：取令牌 → 连热点（已连则跳过，**不会再弹框**）→ 下发凭据 | 等着（可取消） |

要点：

- **进度是三步**：连接设备 / 发送Wi-Fi信息 / 连接云端。（曾按智能生活截图改成五步，
  那一版依赖涂鸦「新流程」的 `queryDeviceConfigState` + `onStep`，随那条路一起删了。）
- **正在执行的那一步画转圈**（loading 图标），已完成画对勾，等待中画序号。（2026-09-14）
- **第二步说明文案**：「正在把Wi-Fi信息同步给设备，请勿离开本页面」。（2026-09-14）
- ⚠️ **第三步「连接云端」是假的，但必须走个流程：SDK 回成功后停 1–2 秒随机再结束。**
  （2026-09-14 产品：「第三步假效果又没有了」）09-10 加过、09-11 以「最简洁」删掉
  （`a0aa3bf`），产品要回来了——**不要再以"纯装的"为由删掉**。
- **先连设备、后输密码**这个顺序保留：把那次系统框挪到用户刚点完设备、注意力还在这件事上
  的时候；也解掉了「手机挂在热点上就带不出当前 Wi-Fi 名」的矛盾——名字在连热点之前就抓好了。
- **只有一条配网路径**：`FlowerpotState.pairViaHotspot`。删掉的三条（EZ、涂鸦「新流程」、
  扩展 SDK `ThingActivatorCoreKit`）见 §1.1 与 §4.0，**不要再接回来**。

### 1.4.1 无论怎么退出，都要把手机的 Wi-Fi 还回去

**（2026-09-10）** 用户点过某一行的「连接」之后，手机就挂在设备热点上、**真的没有外网**。
所以**每一条离开配网动线的路径都必须把网络还原**，不能把用户撂在一个没网的热点上：

| 退出方式 | 处理 |
| --- | --- |
| 配网中途点「取消配网」 | 中止 activator，一并解开网络绑定 |
| 配网失败 | 失败收尾里放掉热点连接与配网器 |
| 搜索页点过「连接」之后返回 | 页面销毁时放、切后台也放。本页自己不建连接，但 SDK 配网时可能把进程绑到设备热点上，解一次是保险 |
| **配网成功** | **也要放** —— 设备随即关掉自己的热点，进程若还绑在那个已消失的网络上，紧接着读设备列表就会失败（表现为「配网成功但读不到设备」） |
| 进了「连接 Wi-Fi」页又退回来 / 输到一半退出 | 页面销毁时放（不要只在"配网真的跑起来过"时才处理） |
| **App 被切到后台** | 放掉并把界面退回「点连接」之前的状态；真要配网时会重新连（已连则跳过） |
| App 被杀 | 进程专属连接随进程消失，系统自动切回，无需处理 |

⚠️ 唯一**不能**放的时机：配网正在跑（会掐断正在用的通道），以及连热点的系统确认框正显示
时（那时页面也处于 paused，放等于自己把刚发出的请求撤回）。

### 1.5 设备开机即可配网——**但有时限**

- **设备只要开机就处于可配网状态**，不需要长按、复位或任何确认动作。（2026-09-10）
- 所以端上文案一律只说「请确认设备已开机」，**不要**出现「长按设备按键进入配网状态」
  「确认指示灯闪烁」这类步骤；「设备已在配网状态，继续」这类按钮删掉。
- ⚠️ **修正（2026-09-10 晚，产品反馈）：设备静置一段时间会退出配网模式**，那之后它不再
  广播热点，扫多久都搜不到。所以「开机即可配网」只在**上电后的一段时间内**成立。
  由此定下的处理：
  - 真扫跑在系统配额上（前台 4 次 / 2 分钟），只能**均匀铺满**，不能再密；
    这件事不能靠调扫描节奏解决。
  - **搜不到时要尽早把正确动作交给用户**：40 秒还一台都没有，就立刻给出「重新扫描」
    ——不要让他等满 3 分钟窗口。
    ⚠️ **文案 2026-09-14 产品改定**：标题「还没搜索到设备」，下面只有一句
    **「请确认设备处于配网状态后，点击重新扫描」**，上面的插图换成
    `assets/images/pairing_failure_illustration.png`（雷达扫描线不画）。原来那一大段
    「设备静置一段时间会退出配网状态……请给设备断电重启」**删掉，不要加回来**。
  - 重启后热点一定在，下一次扫描就能看见，这比任何频率调整都有效。

### 1.6 配网过程中不要 App 自己的弹框

- 1/2/3 步骤里**不要任何 App 弹出框**（「查找设备…」「没有找到任何设备」这类一概不要）。
  必要文案**精简进步骤里**展示。（2026-09-10）
- 系统自己的框不在此列（那是系统行为，见 1.2 的处理方式）。
- **例外：用户自己点「取消配网」时要二次确认**（2026-09-14 产品）。框里正文
  「当前设备正在配网中，确定是否取消？」，按钮「继续配网」/「取消配网」。这条是用户主动发起的，
  不属于上面说的「App 自己冒出来的框」。搜索页「连接设备」那一段的「取消配网」同样适用。
  > 实现上框画在进度页里（不是弹一条路由）：配网可能在框开着时结束，路由式弹框会被随后的
  > `pushReplacement` 替换掉，配网页反而留在成功页底下。

### 1.7 失败要能看出原因

- ⚠️ **2026-09-14 产品改口径：失败页上不再显示原因、失败码和各步耗时**（原话：「等待设备回应超时……
  然后重试（142）/ 令牌(复用) 0ms · 失败 19131ms」这段文案不需要了，删掉）。失败页只留设计稿那一句
  「设备未能成功连接到当前Wi-Fi网络」+ 小提示卡。**不要再加回页面上。**
- 下面这三条仍然成立，但**落点从失败页改成联调日志**（配网页跳失败页之前记一行 `配网失败 ✗ …`）：
  - 必须能看出是哪一步、什么原因，不能只有一句笼统文案；（2026-09-10）
  - 失败码**无论认不认得都要带上**；认不得的给族级提示，不编造具体含义；
  - 各步耗时单独一行——失败码只说"哪一类"，耗时才说"死在哪一步"。

## 2. 搜索设备页

- 职责就是**把设备搜出来并展示**，不承担任何"确认设备状态"的交互。（2026-09-10）
- 扫到的设备**直接列在页面下方**，不跳页；类似"开了一个监听"。
- 「重新扫描」按钮**只在搜索为空时**显示。（2026-09-10）
- **「重新扫描」和进页面是同一套扫描逻辑**，每次都是从零开始的一轮：原生扫描停掉重开、
  上一轮的结果清掉。（2026-09-14 产品反馈「点击重新扫描扫描不到设备」——当时蓝牙扫描
  60 秒到时停了，状态里还记着"在扫"，重新扫描被直接挡掉、根本没开扫。）
- **按真实情况搜，不缓存扫到的设备。**（2026-09-14 产品反馈「关闭了设备，去搜索还是会搜索出
  设备」）进页面、重新扫描、回到前台（没在扫时）、从「连接 Wi-Fi」页 / 失败页退回来，
  都重开一轮；列表里只出现**这一轮**真的扫到的设备。
  > 唯一留着的是「uuid → 云端产品名」这张表：它只回答"这台叫什么"，不决定"这台在不在"。
- **设备名要等最终结果出来再展示**，不许先画一串字再换成名字。（2026-09-12 提出，
  2026-09-14 二次明确）名字还在云端查的设备**整行先不画**，名字定下来连行带名字一起出现；
  「正在识别设备…」这种占位也不行（行先出来、字后定，照样要换一次）。查名字最多等 5 秒，
  查不到退回广播里的名字，不能让设备一直不出现。
- ⚠️ **搜索页的扫描配额：现在 4 格全给搜索页，真扫 32 秒一次（系统允许的上限）。**（2026-09-11 晚）

  `startScan` 的配额是**按 UID 算**的——涂鸦 SDK 跑在我们进程里，和搜索页**共用**
  4 次 / 2 分钟。09-11 白天「连接设备卡几十秒」就是这么来的：当时的动线里
  `queryDeviceConfigState`（涂鸦「新流程」）**必须自己扫描找热点**，搜索页把配额用满后它
  抢不到，在等一个永远不来的扫描广播、一直挂到超时。所以当天先预留 2 次（62s）、再降到
  1 次（42s）。

  **那条路当晚已整条删掉**（见 §1.4）。现在的动线里**再没有任何东西会在我们 UID 上
  `startScan`**：连热点要么走 `WifiNetworkSpecifier`（匹配网络由**系统进程**扫，不记我们
  UID）、要么走系统 Wi-Fi 面板（用户手动连）；`pairWifiDevice`（标准 AP）在手机已上热点后
  只跟 `192.168.176.1` 开 socket。所以预留降到 **0**，4 次 / 2 分钟 ⇒ **32 秒一次**，
  均匀铺满、不在开头扎堆。空档由 1 秒一次的读缓存补上（不占配额）。

  ⚠️ **将来若重新引入任何「SDK 自己扫描找设备」的配网路径，必须把
  `_quotaReservedForSdk` 改回 ≥1**，否则会重演「连接设备卡几十秒」。
- 「发现 X 台设备」的**字体要小一点**。（2026-09-10）
- **首次进入要授权时，等用户授权完再触发真实搜索**；不是首次进入就等页面加载完毕、
  或稍微延迟一点，让设备能马上被搜出来。（2026-09-10）
  > 为什么：Android 前台应用每 2 分钟只许 4 次真扫，授权那几十秒里发出去的都白扔。

## 4. 通用 UI 口径

- **toast 不带来源前缀**（`接口-`、`APP-`、`涂鸦-`），直接输出内容。（2026-09-10）
- toast 文案**不要换行**——必要时调整最大宽度。（2026-09-10）
- 登录页手机号格式校验**只用 toast**，去掉 form 表单下面的提示文案。（2026-09-10）

## 4.0 连热点：只有 `WifiNetworkSpecifier` 一条路，系统框**必出现一次**

### 这是涂鸦官方 2026-09-11 的书面结论，不是我们的取舍

原文：

> - Android 10+ 第三方 App **无法**通过 `WifiManager#connect()` 静默连接任意热点
>   （需 `NETWORK_SETTINGS` 系统权限，**不可申请**）；
> - **`WifiNetworkSpecifier + requestNetwork()` 是唯一可行路径**，但强制弹出系统授权框
>   （**无绕过方案**）；
> - 「SDK 自动连热点」仅适用于 TuyaOS ≥ 3.6.1 固件 + **智能生活 App（预置/白名单应用）**,
>   第三方 App 不具备同等能力；
> - 文档中「SDK 会在指定时间内自动连接」指**设备端行为**（如 `tkl_wifi_start_ap` 后自动
>   监听），**非手机侧静默连接**。
>
> 因此，对第三方 App 而言，**「零系统框」在 Android 10+ 上技术上不可行**。

⚠️ **「零系统框」这件事到此结案。** 不要再花时间找绕过方案，也**不要再以「SDK 会自己连」为
由删掉连热点这一步**——那句话说的是设备端，不是手机端（这正是 `223bdae` 那次返工的根因）。

### 我们真机上亲手跑死的两条路（别再试）

| 路 | 真机结果 |
| --- | --- |
| `WifiManager.connect(WifiConfiguration, ActionListener)` | 方法**存在**、调用**不抛异常**，但 `ActionListener` **一个回调都没来**；`addNetwork()` 返回 **-1**（系统拒绝保存网络）。12 秒内手机一直留在路由器上 |
| `WifiNetworkSuggestion` | `addNetworkSuggestions` 返回 **0 也没用**：Android 10 上**首次必须用户在通知栏点同意**，且「The platform **ultimately chooses** which access point to accept」——没有 API 能要求它立刻连。设备热点没有外网、手机正连着有外网的路由器，平台不会切。**代码已删**（留着只会在配网关键路径上白等十秒，而设备静置会退出配网模式，§1.5）。实现见 git `747d871` |

### 「零系统框」终审（2026-09-11 晚，产品拍板：不走）

零系统框在技术上**有一条路**：系统 Wi-Fi 面板（`Settings.Panel.ACTION_INTERNET_CONNECTIVITY`，
`da5a054` 的 `openWifiPanel`）+ 标准 AP `pairViaHotspot`。用户在浮起的系统列表里自己点
`SmartLife-xxxx`，没有授权框。**但不走**，产品原话选「保留一次系统框（推荐）」：

- 步骤更多（离开 App、在列表里找、点、等、回来），现版是点一下「连接」；
- 连接归**系统**持有，Android 10 判定"无互联网"后**可能中途把手机切回路由器**——随机
  `207220`。`WifiNetworkSpecifier` 是 App 持有请求，系统在请求期间保证不切走，这就是
  现版稳定的原因；
- 多半还会冒「此网络无法访问互联网」的系统通知，系统 UI 并没有真的消失。

⚠️ **产品记忆里"早期有一版全程没框、只是 Wi-Fi 名显示不对"（`78afe2a` 前后）从未配成过**：
那几版把连热点交给了涂鸦新流程，而它根本不连——没框和 `207220` 是同一件事。
详见 `docs/history/2026-09/2026-09-11-zero-dialog-verdict.md`。**不要再往回找。**

### 现在的实现

1. **捷径**（零点击）：已持有该热点连接、或手机本来就连在该热点上 —— 直接成功。
2. **`WifiNetworkSpecifier` + `requestNetwork`**，60 秒等用户操作；
   `onAvailable` → `bindProcessToNetwork`，`onUnavailable` → 报「热点不存在（设备可能已退出
   配网模式，断电重启再试）/ 用户取消 / 超时」。
3. 系统框的位置见 §1.2：**收在搜索页那颗「连接」按钮上，只出现一次**；之后选 Wi-Fi、输密码、
   配网进度**一个系统框都没有**。涂鸦的建议也是这个（「收口至显式引导页」）。

### 其它

- 已核实：`CHANGE_WIFI_STATE` / `ACCESS_WIFI_STATE` / `ACCESS_FINE_LOCATION` /
  `NEARBY_WIFI_DEVICES` 清单里**都已声明**，失败不会是权限缺失。
- 「失败不给兜底、把原因原样打到页面」这条**仍然有效**，而且正是靠它才拿到上面两条判定。

## 4.1 配网排障：先看事实，别先猜

**（2026-09-11 教训：第一版把两条"最常见原因"排在失败文案最上面，结果用户看到的全是猜测、
真正的诊断被挤到看不见的地方，反馈是「感觉不是这个问题」。）**

- 失败文案**事实在前、建议在后**：第一行就是
  `【错误码】涂鸦原文｜用时 Xms · 手机在「Y」(是否设备热点)`，建议缩成一行放最后。
  这段**长按可复制**。
- 三样事实各自回答一个问题：
  - **用时** —— 跑满超时 ⇒ SDK 一直没能和设备说上话；远小于超时 ⇒ 它有反应，问题在别处。
  - **手机当时连的网络** —— 还显示路由器名 ⇒ SDK 根本没把手机切到设备热点上。
  - **错误码** —— 207xxx 才说明设备回过话；笼统的超时码说明通道就没建起来。
- 原生侧 `apQueryDeviceWifi` 每一步都打日志，tag 是 **`FlowerpotTuya`**
  （`adb logcat -s FlowerpotTuya`）：
  `ap query: begin` / `activator=…` / `builder ok` / `wifi before` /
  `handed to SDK, waiting for callback` / `success|error … wifi now`。
  用来分辨三种完全不同的故障：**配网器没建起来**、**反射签名对不上**、
  **调出去了但回调永远不来**。

## 4.2.1 固件升级提醒：按涂鸦的「升级方式」走不同交互（2026-09-15 产品）

涂鸦平台上每个固件版本配一种升级方式，App 从 OTA 记录的 `upgradeType` 读（0 / 2 / 3，SDK 解包核对过）：

| 平台上的升级方式 | 平台说明 | App 交互 |
| --- | --- | --- |
| App 提醒升级（0） | 用户进入设备面板主动提醒，可以选择是否升级 | 弹框「检测到Vx.y.z新版本，确认是否升级」，**取消 / 立刻更新** |
| App 强制升级（2） | 升级提醒主动推送，用户无选择权利，必须升级 | 弹框「检测到Vx.y.z新版本，请升级后使用」，**只有立刻更新**，返回键 / 点遮罩都关不掉 |
| App 检测升级（3） | 不主动推送，用户主动检测才看得到 | 不弹，保持现有小红点 |

- **「立刻更新」= 跳到这台设备的「其他设置」并直接发起升级**，不再弹「检查更新」确认框（用户已经确认过）。
- **只在设备页监控**：设备详情及其下子页。**「我的」一侧、设备列表页都不监控**；搜索 / 配网动线也不弹。
  「其他设置」本身不弹（升级入口就在那一页）。
- 提醒升级点了「取消」，这次进设备面板不再弹；离开设备页再进来重新提醒。强制升级只要没升级、没在升级中，回到设备页就弹。

### 升级过程的状态：涂鸦没有「下载 / 传输 / 安装」三段（2026-09-15 核对，**不做**）

产品问能不能给「固件下载 / 固件传输 / 固件安装」几个状态，口径是「有就做，没有就不做」。核对结果（SDK 7.5.1 解包 +
涂鸦官方 Android / iOS 固件升级文档）：升级状态只有 **13 云端排队 / 14 云端准备 / 100 App 准备（仅蓝牙设备：连蓝牙、下载固件包）
→ 2 升级中（带进度 %）→ 6 固件已下载到设备 → 3 成功 / 4 失败 / 7 超时 / 5 等待唤醒（低功耗）**，
没有独立的「下载中 / 传输中 / 安装中」。Wi-Fi 设备的 2 是一整段进度，「传输」只存在于蓝牙直连升级。
所以升级进度仍是现在的「升级中 xx%」，**没有加三段式状态**。要做，得产品接受按上面这组真实状态重新定文案。

## 4.5 首页四个状态子页：一套逻辑，只是 DP 不同（2026-09-15）

首页（已绑定设备）下面的 **需水状态 / 光照状态 / 空气温度 / 相对湿度** 四个子页面，读数据是同一套写法，
区别只在 DP 号（依据 `09_12` 功能点表）：

| 页面 | 实时值 | 状态（没报时按 App 阈值兜底） | 历史曲线（日 / 周 / 月） |
| --- | --- | --- | --- |
| 需水状态 | 105 水位、106 土壤湿度 | 107 | 131–133 水位、134–136 土壤湿度 |
| 光照状态 | 109 照度 lux、110 PPFD | 108 | 137–139 **照度 lux** |
| 空气温度 | 112（倍数 1，÷10）、146 温度单位 | 113 | **功能点表里没有** |
| 相对湿度 | 114（倍数 1，÷10） | 115 | **功能点表里没有** |

- **每个状态页进页面都要在联调日志里记它读的 DP**：DP 号 + 标识符 + 设备原始上报值（没报写「未上报」，
  带倍数的同时写换算值）；有历史 DP 的页面再记这一页那几条历史 DP 的到货情况（字节数 / 解出点数）。
  新增状态页照做：在页面 model 上加 `reportedDps`，页面里调 `logStatusDps`。
- **光照历史图画的是 137–139 报的照度（lux），不是 DLI。** 功能点表里没有 DLI 历史 DP；
  2026-09-15 以前页面读的是 DLI，真机上这张图永远是「暂无 DLI 历史」，137–139 报上来也画不出来。
  要 DLI 曲线必须设备侧新增 DLI 历史 DP，或产品给定 lux→DLI 的换算口径——**App 不自己拍一个系数**。
- 空气温度、相对湿度**没有历史 DP**（同 §6 电池那条），没有设备历史包可画，不要当成对接问题排查；曲线只能靠下面
  说的实时推送攒。日志里会明写一行「功能点表里没有这项的历史 DP」。
- **报表（曲线）要跟着涂鸦推送实时动，往前移动**（2026-09-15 产品：「只要涂鸦推送了，你报表就是要实时动，
  就是往前移动那种效果」「不需要做特殊的处理，跟以前那些数据一样的渲染就行了」）：
  - 曲线和顶部读数一样**现读、现画**，推送一到就重画，不做「只刷本页」「值没变不动」之类的筛选。

### 5.1 外部给的 SDK API，**先拆包核实再写代码**

外部渠道（含"涂鸦回复"）给的调用示例里，已经出现过 **4 次**不存在的 API。所以规矩是：
**任何没在 `docs/reference/` 的官方文档里出现过的类名或方法名，先从 Maven 拉 AAR 拆包
核实，再动代码。**

核实办法（本机可做，不需要工具链）：

```bash
B=https://maven-other.tuya.com/repository/maven-commercial-releases/com/thingclips/smart/<artifact>/<ver>
curl -sfLO $B/<artifact>-<ver>.aar
unzip -q -o <artifact>-<ver>.aar && unzip -q -o classes.jar -d cls
strings -a -n 2 cls/path/To/Class.class | grep -E '^(on|get|set|is)?[A-Z_]'
```

⚠️ `strings` 默认只打印 **≥4 个字符**的串，`AP` / `EZ` 这种两字母枚举值会被漏掉，
**必须加 `-n 2`**（2026-09-11 差点因此误判 `ThingDeviceActiveModeEnum` 没有 `AP`）。

历史台账：

| 外部说法 | 核实结果 |
| --- | --- |
| `ThingSmartHotspotCredentialKit` | ❌ 不存在 |
| `WifiManager#connect()` 可静默连任意热点 | ❌ 是 `@SystemApi`，要 `NETWORK_SETTINGS` |
| `IThingOptimizedActivator.startAPConfig(ApHandlerBean, …)` | ❌ 官方文档里该接口没有此方法；`ApHandlerBean` 是 `resumeAPConfigWifi` 的参数 |
| `WifiManager#connectSta()` | ❌ Android 没有这个 API |
| 「`IThingOptimizedActivator` 本身不存在」 | ❌ **这条说法才是错的**——`docs/reference/tuya-ap-mode-android.md:129` 就是官方示例；同一条回复又承认 `queryDeviceConfigState` 是真接口，而它正是这个接口的方法，自相矛盾 |
| 「Flutter 场景下必须用 `ThingActivatorCoreKit`」 | ✅ **真的**，已拆包核对全部类名与方法签名，依赖现成 |

  - ⚠️ **这几个脚本都查不出类型错误。** 同一次打包还炸了两处类型问题，只能靠人看：
    ① `ApiClient.getJson` **已经拆过信封**（`retCode` 非 200 直接抛，返回的就是 `retData`
    本身），不要再 `json['retData']`——它的静态类型是 `Object?`，`[]` 根本没定义；
    ② `state.deviceById(id)` 只收 `String`，而 `plantMissing(id)` 收 `String?`，**同一个
    可空变量喂给两个签名不同的方法**就会炸。写之前先 `grep` 一眼目标方法的签名。
  - ⚠️ **括号数得再准也看不见引号。** 上面两个脚本各管一段，别拿其中一个当"全都查过了"。

    能拆成局部变量就拆。

    块里每一行都变成顶层裸文本，从那一行起刷几十条 `Expecting a top level declaration`
    ——而括号配平、符号残留这些检查**全都会通过**。
  - ⚠️ **用脚本删代码时，匹配串一律以 `\n` 开头**。那轮脚本保留 `s[:index+1]` 是为了在

    marker 的第一个字符，于是就有了上面那个 `//**`。
